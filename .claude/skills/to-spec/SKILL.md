这个 skill 把当前会话上下文和代码库理解合成一份 spec。**不要访谈老板**，只综合你已经知道的东西。

Spec 存放在 `docs/specs/` 下，文件名 `NNNN-slug.md`，编号扫该目录内最大号 +1（首个 spec 从 0001 起）。

## 处理流程

1. 探索仓库了解代码现状（如果还没做过的话）。全程使用项目术语表（`CONTEXT.md`）的词汇，尊重相关区域的既有 ADR。

2. 勾画出你打算在哪些接缝测试这个特性。优先用既有接缝，尽可能用最高层的接缝。如果需要新接缝，在你能做到的最高点上提议它们。代码库里的接缝越少越好——理想数量是一个。

   和老板确认这些接缝符合预期。

3. 用下面的模板写 spec，然后存进 `docs/specs/`。

<spec-template>

## 问题陈述

老板遇到的问题，从老板视角描述。

## 解决方案

问题的解决方案,从老板视角描述。

## 用户故事

一个**长长的**、带编号的用户故事列表。每条用户故事格式：

1. 作为<角色>，我想要<功能>，以便<收益>

<user-story-example>
1. 作为移动银行客户，我想要看到账户余额，以便我能更明智地决定消费
</user-story-example>

这个列表要极度详尽地覆盖特性的所有方面。

## 实现决策

已经定下的实现决策清单。可以包括：

- 要构建/修改的模块
- 那些模块中会改动的接口
- 开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 特定交互

**不要**包含具体文件路径或代码片段。它们很快就会过时。

例外：如果原型产出的代码片段比散文更精确地编码了某个决策（状态机、reducer、schema、类型形状），把它内联在相关决策下，简要说明它来自原型。只截取决策密集的部分，不要整段可工作的演示，只要关键位。

## 测试决策

已经定下的测试决策清单。包括：

- 什么是好测试的描述（只测外部行为，不测实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库里类似的测试）

## 超出范围

明确列出超出本 spec 范围的东西。

## 补充说明

关于本特性的其他补充说明。

</spec-template>

## Spec 的生命周期

**Spec 不是文档，是工单。** 它的读者是下一个 session 的助手，不是几个月后翻文档的人。活干完、验证通过后，Spec 就该删除。

交付说明里必须报告「已删除 spec docs/specs/NNNN-slug.md」。如果忘了删，下次动工前检查 `docs/specs/` 并清理已完成的 spec。
