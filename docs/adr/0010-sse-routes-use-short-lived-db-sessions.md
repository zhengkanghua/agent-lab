# 流式路由不用请求级数据库 Session

返回 `StreamingResponse` 的路由不许用 `Depends(get_db_session)` 那种请求级 Session；需要查库就注入一个持有 session 工厂的 Service，由它每次操作自己开一个 Session、提交、立刻关。原因是 FastAPI 的依赖清理时机：请求级 Session 要等响应彻底结束才归还连接，而流式响应的「结束」是流关闭之后，一次长对话可能几分钟，几个人同时聊就能把连接池占空——故障表现却和 Agent 毫无关系，是检索页开始报数据库不可用，排查方向从一开始就是错的。

## Considered Options

**照常用请求级 Session，把连接池调大。** 池大小是常量、并发数不是，调大只是把悬崖往后挪；问题是「占用时长和请求时长挂钩」，不是池子太小。

**在生成器里面用短 Session 查库。** 流一旦开始响应头就已发出，之后的失败只能是一个 SSE 事件而不能是 HTTP 状态码；归属校验失败本该是 404，会变成 200 加一个事件，前端得为同一件事写两条处理路径。校验必须在流开始之前。

**路由里照常拿 Session，手工在开始流之前 close。** 能 work，但这个纪律是隐形的，忘了不报错，只在并发上来以后表现成别的页面故障。

## Consequences

工厂必须由构造参数传进去，不能在 Service 内部 import 模块级的工厂对象，否则离线测试没有注入点、会真去连库。`last_active_at` 在每轮开始时写一次，此后由运行驱动者按固定节奏续期（见 [0037](0037-cross-process-run-coordination-in-database.md)），不由请求路由在流的 `finally` 里补写——那要么回到被否掉的方案，要么在客户端已断开时才执行。本列的语义因此是「最后活动时刻」，「最后一次提问时刻」只是它的一种来源。以后再加流式路由，同一条规则照用。
