# 个人偏好入库，localStorage 不再作为事实源

个人偏好此前只存在浏览器的 localStorage（`signaldesk.preferences.v1`），后端完全不知道它们。本决策
把它们迁进 PostgreSQL 的新表 `user_preferences`，并新增 `GET` / `PUT /auth/me/preferences` 两个接口
供账号读写自己的配置。表结构与接口清单见 [后端架构说明](../../backend/docs/architecture.md) 的
「数据库表」节。

具体形态：`user_preferences` 一行一个账号（`user_id` 既是主键也是账号标识），承载 `system_prompt`
（可空，`NULL` 表示用服务端默认）与两个检索数量参数 `document_limit` / `matches_per_document`。
接口取**当前登录账号**的配置，取值域由登录态决定、不由路径参数决定，因此路径里不带账号 id——从形态上
排除「改别人配置」的可能。（路径初稿写作 `/user/preferences`，实现时定为 `/auth/me/preferences`：
账号自助已有既定形态，`api/account.py` 的 router 是 `prefix="/me"`、挂在 `/auth` 下，新接口挂进同一个
router，自助类接口就只有一种形态。）提示词与会话快照的两层划分、以及请求体字段为什么删除，见
[ADR 0029](0029-session-scoped-system-prompt.md)。

**触发条件是「消费方从客户端转移到了服务端」，不是「表建好了以后可能有用」。** 当年
[ADR 0018](0018-settings-hub-with-local-preferences.md) 评估过「偏好存后端」并明确放弃，理由是那两个
偏好的消费方（每次请求）本来就由前端组装。这条理由对**提示词**不再成立：提示词要从「每轮请求参数」
改成「会话建立时定下来、会话内不可变」，服务端就必须有一个能读到的存放位置；值继续留在 localStorage
意味着后端仍要依赖前端每轮传对，而这次改动的目的恰恰是**不再信任每轮传来的值**。本决策不为将来可能
的配置项预留，只解决当前这一个已经发生的消费方转移——检索的两个数量参数本身没有发生这种转移，它们
一并迁入是为了让「配置只有一个事实源」。

## Considered Options

**继续用 localStorage，只把提示词复制一份到会话表。** 改动最小。但等于让「用户配置」有两个事实源：
设置页改的值在前端，会话建立时取的值在后端，两者靠前端每轮传参对齐——这正是本次要消灭的形态。

**key-value 窄表（`user_id` + `key` + `value`）。** 加配置项不用改 schema，听起来更灵活。放弃的理由是
它解决的问题并不存在：个人偏好的字段集合是**业务决策**的结果，加一个配置项本来就该走迁移；而
key-value 会把「这个账号有没有配过提示词」表达成「有没有那一行」这种隐式状态，在一行一账号的表里则是
显式的 `NULL`，同一账号的配置还会被拆成多行，读写都更绕。

**只迁提示词，检索参数留在 localStorage。** 最小改动，也符合「消费方决定存哪」的判据。最终全部迁入是
为了避免「一部分偏好跟账号走、一部分跟浏览器走」这种用户难以理解的分裂——用户不会记得「文档数这个
设置在另一台机器上不生效」。

**接口用部分更新（`PATCH`）而非整体覆盖（`PUT`）。** 设置页是「草稿 + 显式保存」的形态，提交的就是
完整一份，不存在只改一个字段的调用方；整体覆盖语义更简单，也不会出现「两个客户端各改一个字段、互相
覆盖」的合并问题。

## Consequences

**存储边界变化。** 偏好从「每浏览器一份」变成「每账号一份」：换浏览器、清站点数据不再丢配置，但**同一
账号在任何设备上看到的是同一套配置**，不再允许「这台机器用这套、那台用那套」。这是本决策要的效果，
代价是设置页与检索页各多一次读取（页面级缓存，刷新重读），且读取需要登录态。

**存量浏览器的偏好不迁移。** 用户在新表里是空行，需要重新配置一次。理由与「存量会话直接清空」一致：
项目仍在开发阶段，不为旧数据写一次性迁移代码。

**删账号清偏好接在业务层。** `user_preferences.user_id` 是逻辑外键：列、类型、索引在，库上没有
`FOREIGN KEY` 约束。删账号时由 `UserAdminService.delete_user` 在同一个事务里显式删掉偏好行，与它对
`agent_threads`、`access_tokens` 的处理放在一起——配置尤其不能指望运维命令兜底，会话有
`prune-orphan-threads`，配置没有对应的清理命令。详见
[ADR 0028](0028-drop-database-foreign-keys.md)。

**表设计为所有账号可用，接口按现有权限控制。** 决策当时 Agent 对话只对超级用户开放，但
`user_preferences` 不假设这一点——放开权限时不需要改表结构。**这一点已经发生**：Agent 对话已由
[ADR 0030](0030-agent-open-to-all-accounts.md) 放开给所有登录账号，表结构未因此改动，当初的判断成立。
