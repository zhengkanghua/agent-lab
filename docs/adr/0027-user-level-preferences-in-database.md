# 个人偏好入库，localStorage 不再作为事实源

个人偏好此前只存在浏览器的 localStorage，后端完全不知道它们。本决策把它们迁进 PostgreSQL 的 `user_preferences` 表（一行一个账号，承载系统提示词与两个检索数量参数），并新增读写接口；接口取当前登录账号的配置、路径里不带账号 id，从形态上排除「改别人配置」的可能。触发条件是「消费方从客户端转移到了服务端」，不是「表建好了以后可能有用」：此前评估过偏好存后端并明确放弃，理由是那两个偏好的消费方本来就由前端每次请求组装；这条理由对提示词不再成立——它要改成会话建立时定下来、会话内不可变（见 [0029](0029-session-scoped-system-prompt.md)），服务端就必须有一个能读到的存放位置，而值留在 localStorage 意味着后端仍要依赖前端每轮传对，那正是这次要消灭的形态。检索的两个数量参数没有发生这种转移，一并迁入是为了让配置只有一个事实源，用户不会记得「文档数这个设置在另一台机器上不生效」。

## Considered Options

**key-value 窄表（`user_id` + `key` + `value`）。** 加配置项不用改 schema，但它解决的问题不存在：偏好的字段集合是业务决策的结果，加一项本来就该走迁移；而且它把「这个账号有没有配过提示词」表达成「有没有那一行」这种隐式状态，一行一账号的表里则是显式的 `NULL`。

**接口用部分更新（`PATCH`）而非整体覆盖（`PUT`）。** 设置页是「草稿 + 显式保存」的形态，提交的就是完整一份，不存在只改一个字段的调用方；整体覆盖也不会出现两个客户端各改一个字段互相覆盖的合并问题。

## Consequences

偏好从「每浏览器一份」变成「每账号一份」，不再允许同一账号在不同设备用不同配置；存量浏览器里的偏好不迁移，用户重新配置一次。`user_preferences.user_id` 是逻辑外键，删账号时由业务层在同一事务里显式删掉偏好行（见 [0028](0028-drop-database-foreign-keys.md)），配置尤其不能指望运维命令兜底。
