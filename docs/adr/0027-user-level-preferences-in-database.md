# 个人偏好入库，localStorage 不再作为事实源

> **部分被取代（2026-09-17，见 [ADR 0028](0028-drop-database-foreign-keys.md)）。**
> 本文下方「决策」第 1 条（`user_preferences.user_id` 加 `ondelete="CASCADE"` 外键）与
> Consequences 里那段「那条『新表新列一律不加外键』的规范针对的是跨存储系统的关系……
> 因此用 `CASCADE` 保证账号删除时不留孤儿行」的论证**已经失效**。ADR 0028 把这条规范立成
> 「库表不建数据库级外键」并拆掉了存量 16 处约束；按新规范，`user_preferences` 与 `users`
> 同库同域**恰恰不该**加外键，删账号清偏好要接进 `UserAdminService.delete_user` 那条业务层
> 路径。**原文保留不改**，作为当时判断的记录；其余部分（表的数据形态、接口形态、两层提示词
> 的划分、存量不迁移）继续有效。

个人偏好此前只存在浏览器的 localStorage（`signaldesk.preferences.v1`），后端完全不知道它们。
本决策把它们迁进 PostgreSQL 的新表 `user_preferences`，并新增 `GET` / `PUT /user/preferences`
两个接口供账号读写自己的配置。本决策**部分取代** [ADR 0018](0018-settings-hub-with-local-preferences.md)：
那份文档中「偏好只持久化在本浏览器」这一条作废，其余部分继续有效。

## 为什么现在做

[ADR 0018](0018-settings-hub-with-local-preferences.md) 当年评估过「偏好存后端（账号级设置表）」并
明确放弃，理由原文是：

> 要新增后端能力域、迁移和接口，而这两个偏好的**消费方（每次请求）本来就由前端组装**；在接入第二
> 业务领域之前先不引入这张表。

这条理由对**提示词**不再成立。系统提示词要从「每轮请求参数」改成「会话建立时定下来、会话内不可变」，
这就要求服务端有一个能读到的存放位置。值继续留在 localStorage，意味着后端必须依赖前端每轮把值正确
传过来——而这次改动的目的恰恰是**不再信任每轮传来的值**。两者自相矛盾。

换句话说，**触发条件是「消费方从客户端转移到了服务端」，不是「表建好了以后可能有用」**。这一点
需要写清楚：本决策不为将来可能的配置项预留，只解决当前这一个已经发生的消费方转移。

检索的两个数量参数（`documentLimit` / `matchesPerDocument`）本身没有发生这种转移——它们的消费方
仍然是前端。它们一并迁入，是为了让「配置只有一个事实源」，而不是因为它们各自都需要服务端读取。

## 决策 (Decision)

1. **新建 `user_preferences` 表**，一行一个账号：`user_id` 主键、外键指向 `users.id` 且
   `ondelete="CASCADE"`；承载 `system_prompt`（可空，`NULL` 表示用服务端默认）与两个检索数量参数。
2. **三个偏好全部迁入**，localStorage 不再作为偏好的事实源。
3. **新增 `GET` / `PUT /user/preferences`**：读取与整体覆盖**当前登录账号**的配置。取值域由登录态
   决定，不由路径参数决定，因此路径里不带账号 id——从形态上排除「改别人配置」的可能。
4. **提示词与会话快照分成两层**：`user_preferences.system_prompt` 是账号的个人偏好（随时可改，
   影响以后新开的会话）；`agent_threads.system_prompt` 是会话级快照（建立时定下，会话内不变）。
5. **`AgentChatRequest.system_prompt` 字段删除**：值由服务端从配置表读取，不需要客户端每轮告诉它。
6. **数据形态是一列一字段，不是 key-value。** 个人偏好的字段集合由业务决定、对所有账号相同，
   新增配置项走迁移。key-value 会让「未配置」退化成「行不存在」这种隐式表达，并把行数按配置项数
   放大。
7. **更新 ADR 0018**：删除其中「偏好只持久化在本浏览器」的决策与对应后果，保留仍然有效的部分
   （设置中心 `/settings/:section?` 的形态、输入区只留状态入口、契约常量上收 api 层）。
8. **更新 ADR 0024**：`0024-global-business-configuration-and-admin-management.md` 里「也不据此
   迁移个人偏好到账号级存储」这半句随本决策失效；前半句「不把个人偏好混入全局字典」继续有效。

## Considered Options

**继续用 localStorage，只把提示词复制一份到会话表。** 改动最小，但等于让「用户配置」有两个事实源：
设置页改的值在前端，会话建立时取的值在后端，两者靠前端每轮传参对齐。这正是本次要消灭的形态。

**key-value 窄表（`user_id` + `key` + `value`）。** 加配置项不用改 schema，听起来更灵活。放弃的理由
是它解决的问题并不存在：个人偏好的字段集合是**业务决策**的结果，加一个配置项本来就该走迁移；
而 key-value 会让「这个账号有没有配过提示词」变成「有没有那一行」，把 `未配置` 表达成隐式状态，
在一行一账号的表里则是显式的 `NULL`。同一账号的配置还会被拆成多行，读取与写入都更绕。

**只迁提示词，检索参数留在 localStorage。** 这样最小，也符合「消费方决定存哪」的判据。最终选择
全部迁入，是为了避免「一部分偏好跟账号走、一部分跟浏览器走」这种用户难以理解的分裂——用户不会记得
「文档数这个设置在另一台机器上不生效」。

**接口用部分更新（`PATCH`）而非整体覆盖（`PUT`）。** 设置页是「草稿 + 显式保存」的形态，保存动作
提交的就是完整一份，不存在只改其中一个字段的调用方。整体覆盖语义更简单，也不会出现「两个客户端
各改一个字段、互相覆盖」的合并问题——那种场景在本项目不存在。

## Consequences

**存储边界变化。** 偏好从「每浏览器一份」变成「每账号一份」：换浏览器、清站点数据不再丢失配置，
但同时也意味着**同一账号在任何设备上看到的是同一套配置**，不再允许「这台机器用这套、那台用那套」。
这是本决策要的效果。

**登录从「可选」变成读配置的前提。** 偏好读取需要登录态；未登录场景（如果将来有）拿不到配置。
当前设置页与检索页都在登录后的范围内，本次不受影响。

**设置页多一次网络往返。** 进设置页要读一次配置，检索页也要读一次（页面级缓存，刷新重读）。这是
把配置搬离本地存储的固有代价，已接受。

**存量浏览器的偏好不迁移。** 用户在新表里是空行，需要重新配置一次。理由与「存量会话直接清空」一致：
项目仍在开发阶段，不为旧数据写一次性迁移代码。localStorage 里那份旧数据不再被读取。

**`user_preferences` 与 `users` 之间有外键，与 `agent_threads` 新列的处理不同。** 那条「新表新列
一律不加外键」的规范针对的是**跨存储系统的关系**（如 checkpointer 那四张 LangGraph 自管的表）；
本表与 `users` 同库同域，且配置没有对应的运维清理命令（会话有 `prune-orphan-threads`，配置没有），
因此用 `CASCADE` 保证账号删除时不留孤儿行。`access_tokens` 已是同样做法的先例。

**表设计为所有账号可用，接口按现有权限控制。** Agent 对话当时只对超级用户开放，但 `user_preferences`
不假设这一点——放开权限时不需要改表结构。**这一点已经发生**：Agent 对话已由
[ADR 0030](0030-agent-open-to-all-accounts.md) 放开给所有登录账号，`user_preferences` 的表结构
未因此改动，当初的判断成立。
