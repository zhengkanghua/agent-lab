# 第一版 Agent 只读

Agent 能调用的工具全部是只读的：不写 PostgreSQL 业务表、不写 Qdrant、不改 `processing_status`、不触发同步或索引。
`agent/tools/` 只允许包装已有的读取入口（`services/vector_search_service.py` 的检索方法、
`repositories/document_repository.py` 的读取方法）。要加写能力必须先废除或修订本 ADR。

这条边界不是「第一版先少做点」的排期，而是安全边界：模型的上下文里有 RSS 抓来的外部正文，那些文字是数据、
不是指令，但模型没有可靠机制区分两者。只读的情况下，最坏结果是回答错误；一旦有写工具，被正文里的注入
指令牵着走就会改坏库里的数据，而且改动会被后续检索读到，错误自我放大。

## Considered Options

**给 Agent 一个「重新索引这篇」的工具。** 用户读到过期正文时让模型顺手修，体验上顺。但触发索引会写
`documents.processing_status` 和 Qdrant，而决定要不要重索引需要的信息（`content_hash` 比对）前端已经有了
——见 [0002](0002-frontend-detects-stale-body-by-comparing-hashes.md)。用模型的判断替换一次确定的哈希比较，
是拿不确定换确定，方向反了。

**把写工具做出来但默认关掉，用配置开关控制。** 看着两全，实际上代码里那条写路径必须一直保持可工作，测试
也得覆盖它，等于成本照付、风险照担，只是把「有没有」变成「开没开」。真要写能力时再写，比留一条长期不走的
代码路径更便宜。

**允许写但加人工确认（`HumanInTheLoopMiddleware`）。** 每次写入弹给用户确认，风险确实降了。但当前只有超级
管理员一个用户，确认动作实际上是同一个人点「同意」，防不住注入——注入的目标本来就是让请求看起来合理。
需要写能力时应当先做权限分级和操作审计，那是另一个量级的工作，不适合塞进第一版。

## Consequences

「正文已过期」这类需要写入才能解决的问题，Agent 只能提示、不能修，用户仍要回检索页手工触发流水线。

`ToolErrorMiddleware` 的兜底文案可以放心复用检索链路的错误表（`VECTOR_SEARCH_ERROR_RULES`）：只读工具的失败
模式和检索接口完全同构，不需要为工具单独造一套。

放宽这条边界时要一起补的东西不止工具本身：权限分级、操作审计、以及对 RSS 正文的注入防护策略。任何一项缺失
就不该开写工具。
