# 工具输出整份交给模型，平台不再设长度上限

`search_documents` 与 `read_document` 交给模型的文本不再有任何长度上限：检索结果整份、文档正文整份。此前这里有一支按窗口比例算的上限（口径见下），这次整条撤销，理由是模型由用户按会话选、窗口跟着模型走（[0046](0046-model-catalog-and-user-model-choice.md)），就不该再拿一个固定上限去卡它，也不需要为省钱而截断。工具描述里那句「正文过长会明确截断」一并删掉——那是给模型看的契约，不再成立，留着就是一句假话。压缩口径（触发取窗口的 80%、保留最近 30%，见 [0045](0045-model-sees-whole-session-history.md)）没有跟着变，撤的只是工具输出上的那支上限。

**代价：单份工具输出没有程序上的上界。** 当「系统提示词 + 整份上下文记录 + 这次工具输出」超过当轮那个模型的窗口时，请求被上游拒绝，那一轮按失败收尾：错误按 `llm_request_rejected`（上游拒绝这一类，不可重试）交给订阅者，已经生成的部分留在会话里、那一轮标成未完成。**这不是工具错误**——模型收不到任何可纠正的说明，运行直接结束，重试也救不回来（同一条请求一样长）。压缩也救不了这一种：被顶出去的那份正落在保留的最近 30% 里，而摘要用的就是当轮同一个主模型（`runtime.py` 里没有另建客户端），所以一份正文自己就装不下时，摘要那一步同样会被拒。旧上限护住的正是这个场景，只是当时它要先被「一轮里多调几次工具」累起来才会发生，现在一份正文自己就能做到。

**谁会踩到、表现是什么。** 三件事同时发生才会：用户在会话里选了窗口小的模型、知识库里有单篇正文自己就超过那个窗口的文档、模型决定用 `read_document` 读全文。表现就是上面那种「那一轮没写完」。目录里的窗口今天填的是 1048576，约合百万汉字量级，也就是要一篇接近百万字的正文才撞得上（请求里还有系统提示词与已有上下文，实际撞线比这个数略低）；窗口是 `llm_models` 里的一条配置、随时可改，所以同一篇文档换一个更小的模型会被拒、换更大的就照常读完。

**平台刻意不在这里加拦截。** 要拦就得先有一个可信的窗口和一次可信的计数：目录里的窗口由管理员填、保存时不试调也不校验（[0046](0046-model-catalog-and-user-model-choice.md)），运行期的计数是近似值（[0045](0045-model-sees-whole-session-history.md) 已记）；而无论「量出来就拒绝」还是「量出来就截断」，都等于把这次撤掉的规则换个地方装回来。这条边界交给上游兜。

**存储量跟着上去。** 上限取消后一轮的工具正文等于整份正文，checkpoint 与 [0044](0044-session-history-in-own-table.md) 的会话历史表都按原样收下（checkpoint 里较旧的工具正文随后会被压缩清理掉，业务表的保留策略不跟它走）；0044 里那句「一轮的工具正文可以到 6KB」是旧上限下的估量，已在那里补了指引。检索那条从此只剩「最多 5 篇 × 每篇 2 段」这层间接约束，它本来也只有在某一段正文极长时才会大。

**界面文案对这条路径不对症。** `llm_request_rejected` 今天给用户的提示把原因归到「提问或自定义提示词」上、并建议换个说法再试，而这里换说法没有用——同一份正文照样超窗。本次不改这处文案，如实记下；要给这条路径一句真正可照做的话，是另一件独立的事。

## Considered Options

**保留按窗口比例的那支上限**（旧口径：窗口的 20%、封顶 20000 字符、保底 2000 字符，作用在**一次工具调用交给模型的文本总长**上，两个工具共用，超了截断并把截断说出来）。它当年的理由是「一轮之内不压缩」——1 − 压缩触发线 0.8 就是留给「本轮工具结果 + 回答」的余量，所以上限必须与窗口成比例，否则窗口小的模型一次读取就能把这一轮顶出窗口。否决的理由：它护住的那个风险本来就是已接受的边界（见上），而它换来的是替用户选的模型削减能力——窗口大也照同一个比例砍，等于花钱买了不用的窗口。

**把封顶调大或把比例调高。** 治标：调到哪儿都还是要挑一个数，挑完仍然在替用户的窗口做决定，而真正需要护住的量级只有百万字级的单篇文档。
