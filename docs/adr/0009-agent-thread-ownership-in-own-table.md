# Agent 会话的归属放自己的表

「某个会话属于谁」记在一张由 Alembic 管理的业务表 `agent_threads` 里，与 checkpointer 的四张表完全分开，归属判断只有 `AgentThreadService` 一处实现。在此之前 `thread_id` 是前端给什么就用什么，checkpointer 只按 id 取历史、不问是谁，靠「只有超级用户能用 Agent」兜着；一旦放宽权限，猜到或抄到一个 UUID 就能读别人的完整对话、接着别人的会话继续聊。

## Considered Options

**把归属写进 checkpointer 的 metadata。** 要读到它得先加载一个 checkpoint，「列出我的会话」变成把所有会话的历史读出来再过滤；更关键的是它把一个安全字段放进了第三方拥有的 schema，[0004](0004-checkpointer-tables-outside-alembic.md) 已决定不在那里放我们的知识。

**把账号编进 `thread_id`。** 靠解析字符串做鉴权：id 由前端传上来，伪造别人的前缀不需要任何成本，校验时也没有第二个信息源可比对。

**不做归属，继续靠超级用户权限挡着。** 把访问控制寄存在一个将来一定会变的权限设置上，而变更点（放宽权限）和事故点（跨账号读对话）离得很远，改的人不会想到这里。

## Consequences

删除会话要动两个存储、跨两个连接池不可能一个事务，顺序不能交换：先清 checkpointer 里的历史、后删归属记录，中途失败留下的是「历史没了、归属还在」，用户再点一次就干净；反过来会留下查不到也删不掉的历史。回滚这张表的迁移会让每个会话变成孤儿，重新 upgrade 也找不回归属。归属条件在真库上生效没有，编译出的 SQL 文本证明不了，所以除单测外另有一条默认跳过的真库集成测试。
