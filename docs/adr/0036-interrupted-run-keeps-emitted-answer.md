# 被中断的运行把已输出内容写进会话

一次运行被中断（用户停止、上游失败、超时）时，把服务端已经收到的模型输出补写进这个会话，下一次打开或回放时看到的就是「停在哪里、内容到哪里」，而不是一轮空提问。运行**正常跑完**时不补写——那条路径由 LangGraph 自己按节点写入，补写会造成重复。

触发条件是「运行本身被中断」，**不含「连接断开」**：断连不取消任何东西（见 [0035](0035-run-outlives-its-subscriber.md)），把它当触发条件会在运行还在跑时先落一条半截答案，等它正常跑完 LangGraph 再落一条，正好踩中上面那条重复。

这条决策来自一个实测出来的事实：checkpoint 的写入时机是**每个节点完整结束时**，不是每个 token。模型节点要等整个答案吐完才算结束，所以取消一个正在输出答案的节点，那一整格都不落库。用户在屏幕上看到的半截文字，断开那一刻只存在于浏览器内存和那条正在断的 HTTP 连接里，服务端拿不回来。而 `agent/streaming.py` 在流式过程中只累加用量数字（`_add_usage`），**不保留任何文本**——所以「已经在流式传输」不等于「已经在存储」，这两件事必须分开看。

已经落库的部分不需要补救，这也是实测结论：提问、每次模型要求调工具、每个工具结果各自在节点结束时独立落库，取消只影响「正在写的那一格」。所以补写的对象只有一样东西：模型已经吐出、但所在节点没跑完的那段文本。

## Considered Options

**不补写，那一轮只留提问和工具轨迹。** 实现最省，也是原本的范围划分。放弃它是因为它与用户看到的画面直接矛盾：字是一个一个出现在屏幕上的，关掉页面再回来全没了，这件事解释不通。而补写的成本实测下来只有三件事——服务端累积文本、收尾时写一次、带上正确的 `run_id`。

**整轮丢弃（连提问也不留）。** 把「用户按了停止」理解成「这一轮当作没发生」。否掉的原因是它惩罚了用户按停止这个动作本身：他往往是已经读到想要的部分才停的，把提问一起抹掉等于让他重新组织一次输入。

**把已输出内容做成流式写入（每个 token 或定期落库）。** 能让「进程崩了也不丢已输出部分」，但要为每个 token 付一次数据库写入，或引入一个节流写入通道。否掉的理由是收益边界很窄：它只覆盖「进程崩溃」这一种中断，而进程崩溃本来就会让那一轮的其他收尾一起失效。取消和失败这两条常见路径用收尾时写一次就够。

## Consequences

收尾写入最好不发生在取消传播的路径上。实测（`InMemorySaver`）确认 `aupdate_state` 在被取消的上下文里也能成功执行（包括连续被取消两次的情形），所以这条路可行；但停止做成**协作式**（运行单元自己发现停止标志、自己取消那次模型调用、然后正常收尾）能把这条风险基本消掉：写入时没有任何取消在传播，只需处理「写入可能失败」这一种普通情况。调用时显式给 `as_node`——省略时 LangGraph 会尝试从 `versions_seen` 推断，推断不出就抛 `InvalidUpdateError: Ambiguous update, specify as_node`（`langgraph/pregel/main.py:1934`），显式传参成本为零且去掉一条不确定路径。这条结论没有在 `AsyncPostgresSaver` 上验证过，真实数据库的异步写入与取消之间存在竞态窗口（只在进程被关闭这类无法收尾的情形下才需要面对），实现时要按「写入可能失败」处理，不能让收尾失败反过来中断清理。

补写的对象是**已吐出的文本里尚未落库的那一段**，不是整轮输出，**没有文本就不写**。前者是个容易做错的边界：一轮里模型节点会被调用多次（每次工具调用后都要再问一次），先完成的那些节点已经把文本落库了，而累积器里同样有它们。按整轮累积会把已落库的文本再写一遍，回放出的答案出现重复——实测：第一个节点先吐「我查一下。」再要求调工具，工具返回后第二个节点吐字时中断，已落库的 `我查一下。` 加整轮累积的 `我查一下。降息` 拼成 `我查一下。我查一下。降息`。实现上以「最近一次已落库的模型消息」为界，只累积它之后的部分。后者是为了不让「刚发出就被停止」的那一轮变成「有回答但内容为空」的怪状态。

补写的消息要带 `additional_kwargs["agent_run"]`，其 `run_id` 与这一轮提问携带的 `run_id` 相等，`completed` 取假。**这个字段只影响回放给出的状态，不影响文本是否显示**：`replay.py` 的 `answer` 是无条件拼接该轮全部模型消息的，与 `agent_run` 无关（实测：该字段为真、为假、或缺失，三种情况下 `answer` 都含那段文本）。所以「不写就看不到内容」不成立。

取假是为了与截断语义一致：状态是 `incomplete`，数据如实地说明这轮没写完；取真则一段被截断的半句话会被记为完整答案。**界面上不做任何截断提示**（前后端都不做结局标签），展示就是停在哪儿显示到哪儿；用户停止与上游报错也不区分——checkpoint 里区分不出来（见 [0035](0035-run-outlives-its-subscriber.md)），而这个区分当前没有产品价值。

服务端累积的是它**推出去**的文本，不是浏览器**实际收到**的文本，所以断网瞬间未能送达的字节也会被写进会话。这是刻意选的方向：多存一点内容，好过少存用户已经看见的部分。
