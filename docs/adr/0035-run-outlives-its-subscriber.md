# 一次运行不因订阅者离开而中止

Agent 一次运行的推进不再由 HTTP 响应体驱动。浏览器关掉页面或断网时，结束的只是「谁在看这次运行」这层关系，运行本身继续跑到 `done`，结果照常进 checkpointer，下次打开会话读到完整答案。**「停止」不是这一类**：它是对运行本身的动作，会把这次运行真的停下来，走那条跨进程的停止通道（见 [0037](0037-cross-process-run-coordination-in-database.md)）。在此之前的形态是反过来的：客户端 `fetch` 拉响应体，响应体拉 `stream_agent_events`，它再拉 `graph.astream`，没有人拉图就不前进；于是浏览器一断开，取消信号顺着这条链一路插进 LangGraph 的退出流程，那一轮停在半途、已吐出的文字不进历史。

这条决策的直接原因是「钱已经花了、结果却丢了」：模型那次调用是真实发生并计费的，而断开之后这一轮在 `checkpoint_writes` 里连一条 `__error__` 都没有，`aget_state` 拿到的是「有提问、没有任何模型消息」（实测见下）。用户看到的三件事——答案半途、那一轮未完成、`done` 的 `answer` 为空——是同一个原因的三个表现，不是三个 bug。

## Considered Options

**照现状，断开即取消。** 实现上最省。放弃它有两笔账：一是付过费的调用结果被丢弃，而用户重开页面时看到的是一段他自己也没要求中断的残缺答案；二是它把「关页面」和「用户要停止」当成同一件事（两者都只能靠断开连接来表达），而这两个意图恰好相反——一个是「我走了，但活要干完」，一个是「不要了」。把运行从连接上拆下来就是为了让这两件事各自可表达。

**只去掉取消，不加驱动者。** 这是最容易走错的一步，所以单独记下来：把取消信号从这条链上摘掉之后，图**不会**继续跑。没有人在 `__anext__`，`graph.astream` 就停在原地等一个永远不会再来的迭代调用，下一个 superstep 永不启动。实测能看到的假象是「节点还在跑完」——那只是断开前已经发出的那一次模型调用自己返回了，它之后的任何一步都不会发生。所以「断开不取消」是必要条件，不是解法。

**把运行搬进任务队列（Celery）。** 仓库已有那套设施，进程重启也不丢。否掉是因为代价与当前问题不成比例：要把图、模型客户端与 checkpointer 搬进 Worker 的装配，运行状态与事件流要跨进程传递，而主诉求（关页面后跑完、下次能读到）在同一进程内用一条后台任务就能满足。

## Consequences

必须有一个不依赖 HTTP 连接的东西把事件流抽干到 `done`；HTTP 响应退化成它的一个可选订阅者，没人订阅时它自己读完写库。

由此带来两条如实记录的边界，不是本决策能顺带解决的：运行所在的进程**被强杀**（崩溃、内存耗尽、超过停止宽限）时那一轮停在半途，因为没有任何东西替它续跑——**正常部署已经不属于这一类**：进程收到退出信号后把在途运行排空到 superstep 边界、记下「等接手」再退出，由别的进程接着跑完（见 [0040](0040-run-handover-on-deploy.md)）；生产 `WORKER_COUNT` 默认大于 1，同一会话的前后两次请求可能落在不同进程上，因此「在新连接上接着看旧运行的实时输出」不能在进程内存里实现。

LangGraph 侧没有「这次运行被取消」这类结局字段可查：`CheckpointMetadata` 只有 `source`（`input` / `loop` / `update` / `fork`）、`step` 等，没有结局；`__interrupt__` 是节点显式调用 `interrupt()` 的中断，与本项目无关；`__error__` 只在取消信号能贯穿到 Pregel 内部时才落库，而当前这条链的包装形状（`api/agent_chat.py` 的 `ensure_future` + `finally`）恰好让它落不了库。**判断「这一轮有没有跑完」要由我们自己记录**：实测（`InMemorySaver`）发现取消后残留的 `next` 取值随取消时机变化——打在模型节点上是 `("model",)`，打在工具执行期间是 `("tools",)`，而有的时机下图会自己把这一轮跑完、`next` 回到 `()`。仅凭 checkpoint 也无法区分「正在跑」「被取消」「进程崩了」。

不过**区分「用户停止」与「上游报错」不必做**，当前没有产品价值：两者都按截断语义展示（`completed` 取假），用户看到的是同一件事——这轮没写完。需要记录的只有「有没有在跑」与「有人要求停吗」，两者都在会话行上（见 [0037](0037-cross-process-run-coordination-in-database.md)）。

改动前 `api/agent_chat.py` 里那句「断开时 ASGI 服务器会 aclose 本生成器」的注释与实际不符（uvicorn 声明 ASGI `spec_version: 2.3`，低于 Starlette `responses.py` 里 `2.4` 的分水岭，因此走的是 task group + `cancel_scope.cancel()` 那条分支，生成器体内收到的是 `CancelledError` 而不是 `GeneratorExit`；Starlette 全目录没有一处 `aclose()`）。现象（控制流从 yield 直接跳出）是成立的，路径说错了；本次已按实测改正。留着这条是因为它解释了为什么收尾不能指望 `GeneratorExit`。
