# 定时任务与后台处理抽为公共组件，用 Celery Beat/Worker 加 Redis

把原先进程内的定时任务抽成项目内部公共组件，供知识库、Agent 及后续业务按同一契约接入；调度与执行
改用 Celery Beat/Worker，Redis 做消息代理，PostgreSQL 保存受理、执行与恢复依据。替代此前的
APScheduler 进程内调度与独立 scheduler 进程。

**为什么必须换掉进程内调度。** APScheduler 的执行状态只在进程内存里，服务重启就丢失已受理的执行。
本项目已经吃过一次同类教训：进程内互斥锁覆盖不了手动触发与不同进程，导致同一个业务写被并发执行。
要的是「受理先落库、进程怎么挂都不丢」，这就不是一个进程内调度器能提供的性质。

**为什么是 Redis。** 选它是因为 Celery 已经官方支持这套接入方式，运维成本可控。不同时引入 RabbitMQ
或 RocketMQ，也不保留 APScheduler 作为第二套调度来源；RocketMQ 被排除的理由是它与 Celery 缺少官方
现成接入，并非 Python 不能用它。

精确实现（各组件职责、调度细节、锁与领取条件、部署形态）见
[后端架构说明](../../backend/docs/architecture.md) 的「公共任务组件」节；跨模块时序见
[任务执行流程](../flows/scheduled-job-execution.md)；运维配置与验收命令见
[后端 README](../../backend/README.md)。本 ADR 只记决策与理由。

## Considered Options

**保留 APScheduler 作为另一套调度来源。** 部署面小、不需要 Redis。否掉的理由见上：它的执行状态活在
进程内存里，重启即丢，而「持久受理」正是这次要买的东西。

**启用 Celery result backend 保存执行结果。** 更省事，Celery 自带。否掉是因为 PostgreSQL 已经覆盖
查询、结果与恢复，再存一份就出现两个事实源，且两者会在故障时给出不一致的答案。

**引入通用批次进度系统。** 清理与解析这类长任务看起来需要一个统一的进度模型。否掉是因为业务已有
自己的持久待办与完成标记，再建一套就得在两边同步状态，而复用它们足以支撑现有三种任务。

**新增独立的人工恢复页面。** 「待核实」看起来需要一个专门的处置入口。否掉是因为日常的「立即执行／
重试」加任务详情里的异常说明已经覆盖了已确认的操作，异常核实复用现有维护入口即可。

**把长 `ETA/countdown` 任务直接交给 Redis，靠 Celery 的 `autoretry` 计数。** 自建逻辑更少。否掉有
两条：长延迟任务常驻 Redis 会占住内存；Celery 的计数与实际业务状态可能脱节。重试次数与下次尝试时间
记在 PostgreSQL、由 Beat 到期投递，才能让「重试额度」和「业务当前状态」对齐。

## Consequences

**不承诺「恰好一次」。** PostgreSQL 与 Qdrant、原件存储之间没有共同事务，所以保证的是持久受理、可补投
和受控领取，远端操作仍可能重复。跨存储部分成功的正确性依靠业务自身的重复执行安全与结果核验，不是靠
调度组件的投递语义。

**无法证明旧写入已停止时，会阻塞后续写操作。** 这是老板明确接受的数据安全取舍：宁可让同步与索引等待，
也不用心跳过期来自动解锁——那会在远端写入其实还没结束时放进第二个写者。代价是清理慢会连带阻塞同步和
索引。

**升级涉及新增持久化状态，新旧写入口不得无保护混跑。** 迁移期间必须停用旧的 APScheduler 与常驻
消费者，否则两套执行入口会同时处理同一批业务。
