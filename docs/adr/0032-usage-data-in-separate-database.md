# 用量数据存放在独立的 llmops 数据库

用量记录从第一天起就放在独立的 PostgreSQL 数据库 `llmops` 里，不与业务表同库。将来把用量统计抽成独立 LLMOps 服务时，整库可以直接 dump 迁移，业务表一行都不用碰；抽取之后它也能只被授权这一个库，业务数据对它完全不可见。

## Considered Options

**与业务表同库同 schema。** 最省事，但迁移时要写导出脚本、还要安排双写窗口，正是要避开的场景。

**同库、独立 schema。** 也能整块 dump，且跨 schema 还能 JOIN。被否不是因为做不到，而是独立 LLMOps 是明确的目标形态：同库不同 schema 只是逻辑分离，抽取时仍要跟业务库共命运，且无法只授权一个库。

## Consequences

PostgreSQL 跨库不能 JOIN。用量记录只存账号 UUID，后台要显示邮箱时由应用层两次查询拼装，或将来引入 postgres_fdw（本项目当前零 FDW 使用）。

删账号时用量记录**不跟着删**，理由见 `CONTEXT.md` 的「用量记录」词条；代价是记录可能指向已不存在的账号，展示时要处理这种情况。

新增第二个库意味着第二个连接串、第二个 Engine 及其生命周期，以及部署时在同一实例里 `CREATE DATABASE llmops`。**这个 Engine 只由 API 进程持有**：Agent 对话只在 API 进程跑，Worker 与 CLI 都不调生成式模型，所以没有「Worker fork 后重建」与「CLI 释放」这两回事（原先这里写着三处都要各自释放，与实现和 `docs/specs` 都不符，是把「两个进程也读同一份 `.env`」误当成了「两个进程也持有这个 Engine」）。

跟着这个边界的一条当前事实：**Worker 侧不记账**。用量采集器只在 API 进程装配，所以将来若有定时任务开始调生成式模型，那条链路上的调用不会被记录（不是记成 0，是根本没有采集器），也不会报错。真要那么用，得同时把采集器接到 Worker 的装配里去。
