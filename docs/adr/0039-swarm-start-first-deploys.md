# 后端部署改用 Swarm 服务，先起后停

后端的部署方式从「停掉旧容器、跑迁移、再起新容器」改成「把 API、Beat、Worker 做成 Swarm 服务、用先起后停（start-first）更新」：迁移与起容器都在旧版本还在服务的时候完成，旧容器只在新任务启动判定成功之后才被停掉，它手上还有在途运行就先排空到可交接的边界、交给新版本接着跑完（上限 120 秒，见 [0040](0040-run-handover-on-deploy.md)）。收益是部署期间**新请求不中断**，以及 `docker service update --rollback` 能秒级切回上一版镜像。**「就绪之后才切流量」这个说法并不成立**（Swarm 的入口不等健康检查通过就把新任务加进转发集合），而**「正在跑的回答不被打断」也不是本决策的功劳**——那条由 0040 的排空续跑解决。

代价是换掉编排形态，四件要一起接受：1Panel 不再管这三个服务（官方对 Swarm 的态度是「中短期内不会支持」，并推荐用应用商店里的 Portainer 管理，所以 Portainer 只看与应急、写入者始终是 CI）；入口端口从「只绑本机」变成「全网卡监听」（Swarm 的路由网格不支持只绑回环，这是官方记录的已知行为），安全边界因此从端口绑定换成**云安全组/VCN 安全列表（只放 80、443、SSH）**——它在网络边缘拦，Docker 的 NAT/FORWARD 绕不过；编排的网络也从「加入面板那张共享 bridge」换成「自持一张 swarm 作用域的 overlay，本项目的叫 `agent-lab-net`」（栈挂不上 local scope 网络，这是 Docker 的硬限制，报错直说 scope 不对），而需要跨过去的容器内依赖只有 Redis，把它接上这张网一次即可（**人工一次，不由部署流程代劳**——部署流程不去动面板管的共享容器）——旧口径「本项目不创建 Redis、专用网络或数据卷」因此改口为「不创建 Redis 与数据卷，创建并自持一张本项目的 overlay」，服务之间的可见范围同时从「面板上所有应用共用一张网」收窄成「三个服务与 Redis」。

新版本能不能接班由一个**只读的就绪端点**判定，不复用现有的 `/health`：`/health` 刻意只回答「进程活着、数据库能连」，代码里写明它不做就绪语义、理由是不让健康检查本身成为故障来源——那条理由继续成立，所以新增而不是改造它。就绪判据在业务库探活之外**加上 checkpointer 连接池**：它是独立连接池，业务库探活探不到，「进程起来了但 Agent 用不了」的新版本必须在**旧任务被停掉之前**被判出来——就绪判定能拦住的是「要不要停旧任务」这一步，拦不住「新任务已经被分到一部分流量」（那由压小启动窗口负责）。上游大模型**不纳入**判据：上游抖动是外部故障，把它变成部署门禁只会让别人的故障挡住自己的发布。

## Considered Options

**Kamal（自带代理的部署工具）。** 同样能做到零停机与秒级回滚，配置进仓库、命令直白，而且它的入口是普通容器、端口绑定比 Swarm 更可控。否掉是因为它多一个常驻代理进程、要和已有的 OpenResty 协调端口，而 Swarm 的切换逻辑由 Docker 自己承担，我们一行都不用写。

**自己写一个 edge nginx。** 最可控（配置进仓库、可随时演练），但「改生产流量方向」这一步要由我们的部署脚本执行，写错的失败模式是整站不可用。

**k8s 或云厂商的蓝绿/灰度。** 能力最全（控制台、审计、自动摘除不健康实例、跨机高可用），但代价是引入一整套集群或一个云产品；而且云厂商的负载均衡只替掉「指针」这一环——两份后端、排空策略、迁移兼容一件都不少，那些才是无法外包的部分。

**只缩短窗口、不做双活**（把停止宽限调小、迁移前置）。改动极小，但它降不到零：剩下的那几十秒（迁移 + 起容器 + 就绪检查）正是本决策要消掉的那一段，用户在新请求上依旧会看到报错。

**不做，只把停机窗口记成取舍。** 在「唯一的用户就是部署者本人」的现状下这条站得住。否掉的理由是现在还在开发阶段、改造那一次停机的代价为零，而改造一旦完成就永久生效，还顺带把今天完全没有的「秒级回滚」补上。

## Consequences

**首次改造要停一次机，也只有那一次。** 普通容器占着宿主机端口，Swarm 要发布同一个端口，先停后起躲不掉；所以趁没有用户时做。改前的编排与旧容器留着，出问题按手册退回 compose，并且这条逃生路径**必须真跑一次**——没演练过的回退等于没有。

**「版本回滚」要真的能用，需要三件配套。** 一是**不再自动清理上一版镜像**：部署脚本最后那句 `docker image prune -f` 会在新镜像顶掉 `backend-latest` 之后把旧镜像当无名镜像删掉，而回滚要回到的那一版必须在本地；改为只删 7 天前的无名镜像，既保住上一版、又不让磁盘无限涨。二是**删列、改列名、改语义、拆约束的迁移拆两次发布**（先发「代码不再用它」、下一次发布再删）：`--rollback` 的前提是旧代码能跑在当前结构上，做过破坏性迁移之后这条退路就不存在，只能按部署手册那条「恢复备份」处理。三是**图状态结构没变**——与接手（见 [0040](0040-run-handover-on-deploy.md)）同一条前提：旧代码接不了新形状的 checkpoint。这条纪律与用不用 Swarm 无关，但 Swarm 把「秒级回滚」变成一个真实承诺，所以必须一起守；也因此本次只把它记成规则，不上机械门禁。

**三个进程的更新顺序是声明出来的，不是默认值。** API 用「先起后停 + 就绪检查 + 排空」，排空上限 120 秒、停止宽限 180 秒（见 [0040](0040-run-handover-on-deploy.md)），这就是本决策本身。Beat 必须「先停后起」：它只在到点时往队列投任务，「先起后停」会让两个 Beat 短暂同时活着，同一个周期任务可能被投两次；它没有手上活要收尾，停止宽限 30 秒就是。Worker 用「先起后停」，差别只是「先停后起」期间有一段没人领任务的消费空窗；**正在跑的文档批次在两种顺序下都会被允许跑完**——Celery 收到终止信号是温和退出，先把手上的任务做完，上限是 Worker 容器自己的停止宽限（保持不变：360 秒），超过才留下需要人工确认的「待核实」。三个服务的停止宽限因此在编排文件里分别声明，不共用一个数。

**排空的上限不再由「一次运行能跑多久」推算。** 把 `agent/limits.py` 的常量按最坏情况乘起来（模型调用 8 次 × 每次最多 3 次尝试 × 单次 60 秒超时，加工具调用 12 次 × 每次最多 3 次尝试 × 每次 30 秒超时），一次运行可以拖到小时级——这正是 0040 否掉「在旧进程里等它跑完」的理由，也是「不能按运行时长设上限」的论证。API 的排空上限改由 0040 定：等一个 superstep、上限 120 秒，所以停止宽限取 180 秒（外面还套着 uvicorn 自己的关停超时）。Worker 的停止宽限保持 360 秒，理由是让手上的文档批次做完。

**「先起后停」本身不等于零停机。** Swarm 的入口会把流量发给健康检查还在启动中的任务（社区实测的直接现象），而应用是先装配完才开始接请求，所以新任务一旦进了转发目标，落到它身上的新请求就会在容器里排队等启动完成——表现为这几秒内一部分请求变慢。因此零停机的实际条件是**把「被加入转发目标」到「真能服务」之间的窗口压到最小**：**把「能服务」与「已就绪」分开**——启动路径上那些不属于能服务前提的对外调用（今天最重的一项是启动时对上游模型服务的一次自检，超时 5 秒）从生命周期的等待段里拿出来、改在后台跑，它们的结论由就绪端点表达。**不要再串行等待它们**：并发只能把窗口从「相加」变成「取最慢」，上游卡住时仍是 5 秒，验收会因此不通过。（这带来一处对外表现变化：配置写错不再让对话接口返 503，而是提问后收到 `llm_model_not_found` 事件；用户文案不变。）验收也按此取值：**只看请求有没有失败会漏掉「都慢几秒」这种形态，所以要看失败与延迟二维。** 因此本决策里「零停机」的口径是**「用户感知不到」（成功率 100% + 延迟不出现数量级劣化），不是数学上的零**；要数学上的零只有自己拿指针（自建代理）一条路，而那取决于开工前那条实验量出的是「失败」还是「变慢」。

**「坏版本不接班」的判据落在「旧任务不被停」上，不是「流量没分过去」。** 这两件事由不同机制管：**流量什么时候开始分给新任务**由入口决定，它不等就绪；**旧任务什么时候被停**由更新器按任务是否启动成功判定，失败即回滚管的是「容器退出」，判不出「起来了但不健康」。而本系统里「服务检索但 Agent 不可用」是刻意允许的（装配失败不致命），所以它必须被就绪端点如实报成未就绪，否则一个聊天用不了的版本会替掉好的版本。**这一条必须实测**（验收里分开测「启动期失败」与「起来了但不健康」两种）：若实测发现旧任务会在新任务不健康时被停，那就超出接受范围，要改用「自己拿指针」那条路。

**入口端口从此绑在全网卡上。** 安全边界从「绑 127.0.0.1」换成**云安全组/VCN 安全列表只放 80、443、SSH**（与 `0001-swarm-start-first-deploys.md` 的实现决策同一件事）：它在网络边缘拦，Docker 的 NAT/FORWARD 规则绕不过它；如果靠的是宿主 iptables/ufw，就会被 Docker 绕过，那种情形下必须改用 DOCKER-USER 链规则。验收必须从**真正的外网侧**测一次（同一个 VPC 内的另一台机器不算），并在服务器上看 `ss -tlnp` 确认绑定是全`0.0.0.0`。

**已知边界，不在本次范围。** 前端静态文件仍是「一次 rsync 覆盖、旧构建的哈希分片立刻被删」，停留在旧页面的用户点懒加载路由会 404；它与 API 的切换是两件独立的事，本次不做，记在这里以免被当成已经解决。前端的两版本共存要另开一次决定（保留上一版产物，或两份目录加软链切换）。

**另一条已知边界：一个容器里两个 API 进程时，就绪探针的回答是抽样。** 探针每次是一条新连接，内核在两个进程之间分派，所以它只代表被问到的那个进程；两个进程里坏掉一个时，容器仍可能报就绪。这是「一个容器两个进程」今天就有的事实，不由本次改造引入，也不影响本决策成立（新版本整体起不来时，哪个进程都会让探针失败）；要让它变确定就得改成「一个容器一个进程、要并发就多开副本」，那件事留到有用户之后再评估。
