# 超管身份在建号时决定，之后不可变更

取消「降权」这个动作：超级用户身份只在建号时决定，之后既不能把超管改成普通账号，也不能把普通账号提升为超管。要收走某人的管理权，只有注销那个账号一条路。理由是不必把这套权限做成可以反复改的中间状态——本项目是内部平台，管理权只有「建号时给」与「注销时收」两个时点，而一旦可改，就要长期维护「不能降掉最后一个活跃超管」那套算术。

## Considered Options

**保留降权，继续用「不能降最后一个活跃超管」保护它。** 这是改动前的做法，也是多数后台系统的默认形态。放弃它不是做不到，而是这套权限在本项目里没必要变成可反复调整的对象：多一个可改的维度就多一条并发保护、多一条错误分支和一组用例，而它换来的能力（把某个人从管理员调回普通账号）可以由「注销再建号」覆盖。

**只禁「自己降自己」，对别人仍允许。** 会让规则分裂成两套（对自己的行一套、对别人的行一套），而前端本来就已经有一套「管理员把自己降级后重新取会话、跳转」的处理逻辑；规则越分越细，正是「不需要搞那么复杂」要避免的方向。

## Consequences

改状态接口只剩「停用/启用」一个动作，不再接受超管标记；建号接口仍可指定超管身份，那是唯一的授予口子。

「不能降最后一个活跃超管」那条保护随之作废（降权不存在了），但「**不能停用或注销**最后一个活跃超管」必须保留——停用和注销都会让一个人退出活跃超管，锁死入口的风险不变。

前端列表里那个「超级用户」开关要删掉，配套的「停用/降级自己之后重新取会话、跳转」那套处理也要删（它服务的两个动作一个被禁、一个已取消）。

一个实际代价：**要把一个已有账号提升为超管，只能注销它再新建**，而新账号是另一个身份——它名下的会话归属与个人偏好不会跟着过来（注销保留数据，但保留的是旧身份的数据）。当前量级下这不构成问题，需要提升权限的场合本来也发生在建号时。

这条决定与 [ADR 0034](0034-account-deletion-is-soft-delete.md) 叠加之后，收走管理权的手段只有注销，而注销在第一版是不可恢复的——所以「误把超管注销掉」在当前形态下没有回头路，只能靠注销前的确认文案兜。
