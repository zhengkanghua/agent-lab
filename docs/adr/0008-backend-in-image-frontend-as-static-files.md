# 后端进镜像，前端只当静态文件

后端打成 Docker 镜像推 ACR，服务器拉下来跑；前端不进容器，CI 把构建产物直接 rsync 到站点目录，由宿主机 OpenResty 发文件，反代、TLS 和限流全在 OpenResty，仓库不产出任何 nginx 配置。「前后端分离」是代码组织方式，不是部署方式：后端是要跑起来的进程，有卡死的 Python 版本和几十个依赖，那台机器上还跑着别的服务，值得用镜像隔开；前端产物是一堆静态文件，不运行、没依赖，没有任何东西需要被隔离，套容器只是多一层壳，而且壳里必须再塞一个 web server。流程与踩过的坑见 [容器部署文档](../container_deployment.md)。

## Considered Options

**前后端各一个容器，前端容器里放 nginx。** 最常见的写法，但机器上就多了一个 nginx 进程和一份配置；部署者同时是唯一维护者、已在用 OpenResty 管其他服务，多一个 web server 的认知成本高于收益。

**后端容器顺便用 FastAPI 的 `StaticFiles` 发前端。** 前后端发版从此绑死，也和「两个运行时各管各的依赖和构建」相冲。

**后端也不用容器，CI 直接 rsync 代码，服务器上 systemd 跑。** 这条路是正当的，被否只因为版本隔离在这台混跑多服务的机器上更值钱；以后觉得 ACR 那一环太重，切回这套的成本不高。

## Consequences

只推 `backend-latest` 一个 tag，回滚要把旧 commit 重新推一次或手动触发工作流，这是单人项目明确接受的取舍。History 模式的 `try_files` 回落只存在于 OpenResty 里，仓库中没有任何东西能保证它被配上、也没有测试能守住，只能靠部署文档写明。迁移由部署脚本显式执行而不写成 compose 服务，迁移失败时中止在后端那一步、前端仍是旧版本。
