# 跨进程的运行协调直接落数据库

「这个会话有没有在跑的运行」和「有人要求停它吗」这两件事，记在业务库 `agent_threads` 的两个新列上（在途运行的 id、停止请求时刻），**没有第二个状态副本**。每个进程起一个小协程每秒做一次批量查询，把自己手上在跑的运行读出来写进内存标志，运行单元每轮只看那个内存标志。**不引入发布订阅，也不加缓存层。**

不引入发布订阅，是因为换来的延迟差别几乎不可感知：轮询最坏一秒，发布订阅几十毫秒，而这是「用户按下停止按钮」这个动作。用一个能静默失效的机制去换感知不到的差别不划算——订阅会独占一条 Redis 连接、断线重连期间的消息丢失且不报错，正是最难查的那类故障。这也与业界成熟做法一致：LibreChat 与 Vercel AI SDK 都是「在消息上记取消意图、流式循环轮询」。

不加缓存层，是因为它省下的负载按现状可以忽略：每个 API 进程每秒一次按主键的批量查询，加每次提交时一次主键查询。而它的代价是一整套只为自己存在的机制——进程级客户端生命周期、过期时间、回填续期、双向写序的不变量、以及一条「缓存不可用」的降级分支。按仓库工程取舍第一条，新增机制要能指出对应的需求或具体故障风险，这里指不出。**将来数据库确实出现压力时再加**，那时它会有可测量的理由；现在加只是把不确定留给以后。

## Considered Options

**Redis 发布订阅停止信号。** 延迟最低，但订阅连接的生命周期要自己管，重连期间消息静默丢失；Redis 不可用时连降级的余地都没有（订阅不上就是收不到）。否掉之后连带的收益是：这条链路上不再有「缓存故障」这个需要长期维护的正确性承诺。

**现在就用 Redis 给这两列做缓存。** 见上：省下的是每秒一次主键查询，换来的是上面那一串机制和三条为此而生的用户故事。

**把在途状态只放进程内存。** 生产 `WORKER_COUNT` 默认大于 1，停止请求落到的进程可能不是跑着这次运行的那个，内存态在跨进程场景下等于没有；同会话串行的校验也会有一半概率失效。

**为运行协调单独建一张 `agent_runs` 表。** 概念上更干净，但会话与在途运行是一对一（同一个会话同时最多一次运行），挂在使用它的那张表上就够；单独建表还会绕开现有的清理路径——删会话本来就会删 `agent_threads` 的行，新列跟着走，不必新增任何连带删除代码（见 ADR 0028 对连带删除的要求）。

## Consequences

「停止请求的时刻」是**会话级**标记、不指向某一次运行，所以它需要两道守：写入端只在「在途运行的 id 与请求里的运行 id 相等」时才写，挡住迟到的停止；读取端靠「下一次占位时一并清掉」保证新运行不会继承上一次的停止请求。只在运行收尾时清是不够的——进程可能在清之前就被杀掉，留下一个陈旧的停止标记，于是刚起步的下一次运行一开场就被它停掉，而这恰好是写入端用运行 id 比对想防的那件事，只是从写端挪到了读端。

僵尸判定复用 `agent_threads.last_active_at`（运行过程中顺手更新它），不新增活动时间戳：两者语义与写入时机几乎重合。代价是这段运行期间的会话不会被「旧会话清理」挑中——一个正在被使用的会话本来也不该被清掉。**这扩大了该列的语义**（它原本只记「最后一次提问时刻」），列注释要跟着改，[0010](0010-sse-routes-use-short-lived-db-sessions.md) 的后果一节已在本轮访谈中同步更新（不再是「流结束后不再写」）。本表没有 `updated_at`（刻意不继承 `TimestampMixin`），不存在误用它的风险。

进程崩溃时没有任何清理动作会执行，所以「标记永久有效」本身就是要防的故障。**僵尸阈值不由操作超时决定，而由「多久往库里更新一次活动时间」决定**：更新是驱动者自己的循环在做，不受「一次模型调用跑了多久」影响，所以阈值只需高于更新间隔一个安全倍数即可。把阈值挂在「模型超时 + Tool 超时 + 各自重试」的下界上反而会算错——`ModelFallbackMiddleware` 会把主备两次重试串起来，那个下界少算一半，会把活着的运行判成僵尸、放第二次运行进来写同一会话。具体秒数在 `agent/limits.py`（该模块就是本项目放有界执行参数的地方）。

注销账号是**软删除**：归属行保留（见 [0034](0034-account-deletion-is-soft-delete.md)），所以上面挂着的那两列也原样留着，不需要任何清理代码；一个在强杀时留下的在途标记同样没人会去清，但那个会话谁也读不到、删不到，不为它写清理逻辑。
