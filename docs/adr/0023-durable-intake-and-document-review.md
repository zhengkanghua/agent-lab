# 原始资料持久接收与文档解析审核分开

2026-09-08，老板确认文件与 FreshRSS 统一接入 Docling、正常结果自动索引、异常结果等待人工处理，且成功结果也允许主动复核。原有解析失败发生在 Document 保存之前，缺少可复核和重试的持久记录；因此接收原始资料与是否采用解析结果需要分开。2026-09-11，接收、审核、采用隔离与删除规则已落入前后端代码；实际存储验收与环境切换仍需独立完成。

## 已确认的决策

- 保存原始资料与对应的持久处理信息，解析失败时保留失败记录，支持后续重试和人工处理。FreshRSS 保留实际接收并选作正文的原始 HTML，以便重新解析。
- FreshRSS 的原始正文和对应记录可靠保存后，解析失败项可以留待人工处理，正常资料继续同步。接收位置的推进以资料已持久保存为前提，存储失败不能当作可跳过的解析异常。
- 原始资料或最新编辑草稿及对应处理待办保存成功后立即返回处理状态，后台完成解析、预览与索引，页面展示进度和结果。待办必须持久保存，后端进程重启不能使已受理资料失去后续处理依据。
- 按可检测的异常拦截：解析报错、没有有效正文或 Chunk、检测到正文或标题因超限被丢弃等结果等待人工处理；其余结果自动进入后续索引流程。多级标题、标题跳级和表格本身不构成异常；这些检查不保证发现全部语义缺失，已成功处理的结果仍提供主动复核入口。
- 人工处理可对照原始资料检查解析正文、标题层级和 Chunk 预览；MD 和 FreshRSS 解析正文采用 Markdown 编辑，TXT 保持纯文本编辑。修改后可重新生成正文、标题目录和 Chunk 预览，并确认采用或拒绝；不新增类似 Word 的可视化编辑器。解析失败时允许重试或由人工提供修正正文，原始资料本身保持不变。
- 人工修改先作为待确认结果，确认采用后才参与正式正文与索引更新；查看和编辑预览本身不代表已采用。
- 新候选解析失败、等待审核或尚未完成采用时，旧已采用版本继续可用。确认采用后先在后台准备新版本索引，成功后才切换正式正文和索引；失败时保留旧版本，页面展示采用进度或失败状态。没有旧已采用版本的资料在索引准备成功并完成采用前不对普通读取和检索开放。
- 正式检索、Agent 取用和普通全文读取以当前可用的已采用版本为准；索引准备中的候选不能提前被取用，版本切换不能把一篇 Document 的不同版本混成一组检索结果。
- 人工修正过的 FreshRSS 资料收到来源新内容时，产生待复核候选，人工版本保留到新候选被采用；重复收到相同原始资料不能覆盖人工正文。
- 尚未采用的人工草稿存在时，来源更新保留该草稿，另存最新来源内容并提示更新；人工决定继续采用当前草稿，或放弃草稿并基于最新来源重新生成预览。“草稿只保留最新”指最新一次人工编辑，不允许来源同步覆盖它。
- 人工明确拒绝已经可用的资料后，该资料停止被后续检索、Agent 取用和普通全文读取；管理记录仍保留，供后续修正。仅打开复核或编辑草稿不会撤下旧已采用版本。
- 保留各个已采用版本、其对应原始资料和审核结论；未采用的编辑草稿只保留最新内容。更新草稿不覆盖已有的采用记录与审核结论。
- 明确删除或符合条件的定时清理应清除该资料的原件、草稿、已采用历史、审核记录及向量索引；人工拒绝只停止使用，不执行上述删除。
- 待审核、失败和拒绝记录不按保留期自动清理，保留供人工处理或明确删除。定时清理继续只选择已采用且完成索引的资料；存在尚待处理的候选时，不因旧已采用版本到期而连同候选自动删除。当前保留期仍按发布日期起算，没有发布日期时使用创建时间，范围仍由任务指定的 KnowledgeBase 决定。

## 取舍与已有契约

原始资料留存让解析失败也能被定位、重试和审核，并避免单篇坏资料长期阻塞同一 Source 的后续内容；代价是需要持久表达接收、解析和审核过程，协调原件存储与数据库记录。后台受理成功只表示资料和待办已保存，不表示解析、采用或索引成功；失败阶段与后续处理需要在管理界面可见。正常资料仍可自动处理，人工审核不成为全部资料的必经步骤。

已采用版本与候选结果分开，使人工编辑和来源更新不会提前影响正在使用的正文；保留已采用历史便于核对当时使用的资料，但需要协调历史正文、原件和删除操作的生命周期。只保留最新编辑草稿，避免把每次修改都扩展成一份完整文档历史。

保留期不替人工做审核决定，代价是待审核、失败和拒绝记录会持续占用存储，需要人工处理或明确删除。定时清理一旦选中资料，则清理其完整文档历史，不承诺清理后还能回看已采用版本。

这调整了现有来源导入中“全部解析通过后保存 Document 并推进 checkpoint”的顺序。Source 与 KnowledgeBase 的准入规则继续沿用 [ADR 0020](0020-knowledge-base-management-slice.md)。写资源协调继续沿用 [ADR 0019](0019-scheduled-execution-and-write-coordination.md)：后台待办持久化不等于允许自动抢占旧写入；进程中断或远端写入结果不确定时，仍遵守原有的人工恢复边界。游标前进表示此前资料已可靠接收，不表示其解析结果已采用或索引完成。清理扩展到原件和文档历史，同时保留 ADR 0019 的删除待办与条件复核原则。

本决策扩展了 [ADR 0021](0021-agent-run-evidence-and-replay.md) 中未建立完整文档历史的范围。历史留存用于管理核对；现有“打开引用读取 PostgreSQL 当前全文并对照当时片段”的契约继续有效，未新增从 Agent 引用打开历史全文的能力。

这调整了 [ADR 0002](0002-frontend-detects-stale-body-by-comparing-hashes.md) 中后端不核验文档版本可用性、允许旧索引直接返回的边界：后端必须隔离未采用候选与已停止使用的资料，不能仅靠前端 hash 提示。用户打开先前检索结果时仍需比对正文 hash，因为检索结束后可能发生正式版本切换。[ADR 0001](0001-backend-owns-result-uniqueness-and-order.md) 中结果唯一性与顺序由后端保证的责任保持有效，具体搜索步骤需要适配版本隔离。

候选、已采用版本和审核结论分别持久保存，独立索引实例避免新结果覆盖旧 Point。兼容重建复用已采用版本的冻结清单，改变 Chunk 规则必须重新预览和采用；跨存储恢复保留原件与索引实例依据。精确表结构、状态与错误契约以 schema、代码和测试为准，跨模块时序见 [文档生命周期](../flows/file-document-lifecycle.md)。
