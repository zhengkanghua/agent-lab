# 库表不建数据库级外键，引用完整性由业务层维护

2026-09-17，老板确认把「库表不建数据库级外键」立成明确规范：**库表可以有外键「字段」，但不建外键
「约束」，也不靠数据库做级联。** 用一条总迁移把存量 16 处约束全部拆掉，连带语义搬到业务代码里。
本决策取代 [ADR 0027](0027-user-level-preferences-in-database.md) 中「同库同域应当加外键」那段论证。

规范本身写在根 [`AGENTS.md`](../../AGENTS.md) 的「业务与数据约束」（每次动库表都要守的常驻规则），
「删父表必须连带子表」这条义务写在 [`backend/AGENTS.md`](../../backend/AGENTS.md)。16 处约束的清单见
迁移 `alembic/versions/d4b7c1e93a58_拆掉数据库外键约束_drop_database_foreign_keys.py`，各连带语义的
业务层等价物见 `DocumentRetentionRepository.finish()`、`UserAdminService.delete_user()`、
`ScheduledJobRepository.delete_job()` 的 docstring。

**它原本只活在别人的引用里。** 项目里早就有「新表新列一律不加外键、关系在业务层维护」的说法，但审查
时发现它只出现在两份已交付的施工规格与 `docs/adr/0027` 三处，**全是转述**——不在 `AGENTS.md`、不在
`CONTEXT.md`、不在任何 ADR 正文里。一条规则没有出处却已被引用三次，后来的人只能靠转述拼凑它的含义。
**更要紧的是它被解释窄了，而且正好用反。** ADR 0027 当时把它读成「只针对跨存储系统的关系」，于是
得出「同库同域的表反而应该加外键」的结论，并据此批准给 `user_preferences.user_id` 加 `CASCADE`。
老板的原话里没有「跨存储」这个限定，那是后来加上去的。所以本次做的是把这条规则立成明确的一条、
扩大它、并用一次迁移把存量对齐——是「两条规则合并成一条」，不是新增限制。

## Considered Options

**保留数据库外键，只把「新表不加」当作风格约定。** 改动为零，数据库继续兜底。否掉是因为存量那 16 处
约束的连带语义**互相矛盾**：同一个 `document_id`，有的表是 `CASCADE`、有的是 `RESTRICT`、有的
`SET NULL`，读代码的人无法从列定义看出「删这篇文档会发生什么」；而这些语义本来就必须由业务逻辑决定
（比如换版决策记录要保留、操作者置空）。让数据库和业务代码各决定一半，是漂移的源头。

**只拆 `CASCADE`，保留 `RESTRICT` 作为最后一道防线。** 看起来更安全——数据库至少能拦住误删。否掉是
因为 `RESTRICT` 拦住的场景里有两处（`knowledge_bases`、`sources`）**根本没有物理删除路径**，等于在
为不可达的场景留一段没人能验证的代码；而真正的删除保护必须知道业务规则（哪些子表该删、哪些该置空），
数据库没有这个信息。

**把四张 checkpointer 表也纳入 Alembic 管理，统一处理。** 否掉见 [ADR 0004](0004-checkpointer-tables-outside-alembic.md)：
那四张表的结构定义权在 `langgraph-checkpoint-postgres` 手里，我们不持有。

**把删账号的清理挂到 fastapi-users 的删除钩子上。** 比自己写一条路径省事。否掉的理由是**把业务逻辑
寄存在别人拥有的钩子里**，与既有决策拒绝「把安全字段放进第三方 schema」是同一类错误：钩子的调用时机、
是否被绕过、升级后是否还在，都由上游决定，而我们要守的是「删账号不留孤儿」这条业务义务。义务放在
自己的 Service 里，改代码的人搜得到。

## Consequences

**数据库不再有任何兜底，这是本次最主要的代价。** 今天写错删除顺序，数据库会直接报错拦住；以后会静默
留下孤儿数据。风险有两层：写错删除顺序会静默产生孤儿，缓解手段是连带逻辑集中在各聚合自己的
Repository/Service 里、路径唯一可测；改错模型会把 `ForeignKey` 从模型里去掉，顺带打断 `relationship`
的 join 推断（`NoForeignKeysError`，应用第一次 ORM 映射就起不来，而且报错会出现在看似无关的测试里），
所以模型层修复必须与迁移同一次做完。

**「库上无外键约束」不固化成长期回归断言。** 它是一次性迁移的验收条件，用 `pg_constraint` 在迁移测试里
查一次即可；固化成长期断言等于把实现细节变成需要永久维护的测试。

**删账号入口是随后单独确认新增的。** 拆外键本身只需要补一条**业务层**删账号路径，所以第一轮只加了
`UserAdminService.delete_user`，没有动接口和页面——开一个删账号的 HTTP 路由是**新增用户可见能力**，
不该顺手夹带在拆外键里。老板随后确认要这个入口，于是补上了 `DELETE /admin/users/{user_id}` 与管理页的
「删除账号」键。记在这里是为了让后来的人知道：这条路由不是因为拆外键而必然存在的。
