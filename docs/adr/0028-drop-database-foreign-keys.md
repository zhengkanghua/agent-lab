# 库表不建数据库级外键，引用完整性由业务层维护

老板确认把「库表不建数据库级外键」立成明确规范：库表可以有外键「字段」，但不建外键「约束」，也不靠数据库做级联；用一条总迁移把存量 16 处约束全部拆掉，连带语义搬到业务代码里。常驻规则写在根 `AGENTS.md` 的「业务与数据约束」，「删父表必须连带子表」写在 `backend/AGENTS.md`。这条规则原本只活在别人的引用里：项目里早有「新表新列一律不加外键」的说法，但它只出现在几份施工规格与 [0027](0027-user-level-preferences-in-database.md) 的转述里，没有出处；0027 还把它读成「只针对跨存储系统的关系」，据此批准给 `user_preferences.user_id` 加 `CASCADE`，而老板的原话里没有「跨存储」这个限定。本文取代那段论证，是把两条规则合并成一条，不是新增限制。

## Considered Options

**保留数据库外键，只把「新表不加」当作风格约定。** 存量 16 处约束的连带语义互相矛盾：同一个 `document_id`，有的表 `CASCADE`、有的 `RESTRICT`、有的 `SET NULL`，读代码的人无法从列定义看出删这篇文档会发生什么；这些语义本来就必须由业务逻辑决定，让数据库和业务代码各决定一半是漂移的源头。

**只拆 `CASCADE`，保留 `RESTRICT` 作为最后一道防线。** `RESTRICT` 拦住的场景里有两处根本没有物理删除路径，等于为不可达的场景留一段没人能验证的代码；真正的删除保护必须知道业务规则，数据库没有这个信息。

**把删账号的清理挂到 fastapi-users 的删除钩子上。** 把业务逻辑寄存在别人拥有的钩子里，与拒绝「把安全字段放进第三方 schema」是同一类错误：钩子的调用时机、是否被绕过、升级后是否还在，都由上游决定。

## Consequences

数据库不再有任何兜底：今天写错删除顺序数据库会报错拦住，以后会静默留下孤儿数据，缓解手段是连带逻辑集中在各聚合自己的 Repository/Service 里、路径唯一可测。模型里去掉 `ForeignKey` 会顺带打断 `relationship` 的 join 推断，报错出现在看似无关的测试里，所以模型层修复必须与迁移同一次做完。「库上无外键约束」只在迁移测试里查一次，不固化成长期回归断言。删账号的 HTTP 入口是随后单独确认新增的能力，不是拆外键的必然产物。
