# 读路径自己核对 Alias 指向集合的索引规格

`current` Alias 的名字里不带 schema 版本，同一个名字在 schema 升级后会指向另一版集合；写侧每次落盘都校验集合规格，读侧却从来不核。于是「进程配置的 schema 版本与索引不是一个版本」表现为每个 Point 都被逐点契约拒掉，而**结果为空时不经过那个检查**——2026-09-27 起线上看到的是「模型查不到资料」、日志里同一句 `qdrant_response_invalid`，直到 10-01 才被查出来。现在读组件在第一次检索前用写侧同一份 `VectorIndexSpec.validate_collection_info` 核对一次 Alias 指向的集合，不一致就抛 `QdrantSearchIndexSpecMismatchError`（沿用既有 `qdrant_configuration_invalid`），消息写明是哪个字段、期望什么、实际什么。

## Considered Options

**放进就绪检查，让 Swarm 的就绪门禁自动回滚漂移的部署。** 能更早挡住，而且门禁已经存在。否掉是因为它把 Qdrant 的可用性绑进 API 的健康：上游抖一下，`/ready` 就会让 Swarm 把容器判成不健康并重启，而这类抖动今天只影响「这次搜索返回什么错」。放大一次上游抖动的代价大于提前几分钟发现配置错的收益。

**把 schema 版本做进 Alias 名字（`..._v3_current`）。** 结构上就不可能读到错版本的索引，比事后校验更彻底。它动的是数据布局（新建 Alias、可能的迁移、运维命令重写），而这次的根因是「读侧配置与索引不一致」，用同一份规格判定就能覆盖；先做小的，这条留作将来的备选。

## Consequences

**一进程只核一次，缓存不随 Alias 切换失效。** 换指向只发生在写侧的重建发布上，而目标集合那时已经过同规格校验；真有跨规格的写者，逐点的 spec 检查仍然是兜底（只是错误码退回宽泛的 `qdrant_response_invalid`）。这是刻意留下的降级：读侧自证是诊断手段，不是唯一防线。

**读侧用的是写侧那份完整规格，不是「读得到就够了」的子集。** 于是 chunk 参数、tokenizer 版本这类常量改动也会让读侧拒掉旧集合，直到按规矩递增 schema 版本并重建。这是有意的：同一个 Alias 下「配置和索引必须是一套」这个判断，读写两侧给同一个答案，比读侧自己再养一份更窄的判据不容易漂移。代价是这类改动会同时停掉检索与写入，报错会指出具体字段。

**探针失败不改变行为。** Qdrant 不可达、集合不存在、鉴权失败时按「没核过」处理（不缓存），把结论交回原查询自己的错误分类。这条边界是为了让这次新增的校验永远不引入新的失败形态——它只把一个已经存在的失败说得更清楚。
