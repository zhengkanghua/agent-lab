# 检索只留文档级契约，后端不再保留 Chunk 级接口

本决策取代 [0013](0013-search-page-multi-round-record-stream.md)，但只撤销它的一部分：检索页的形态不变——多次检索在同一条向下累积的检索流里、最新一条贴着底部输入坞展开、旧记录折叠成标题行可回看，前端也仍然只走按文档分组的检索。撤销的是 0013 末尾那句「后端 `/vector-search` 的 Chunk 级契约与单测保留」：这条按片段的旧接口一并删掉，连同它的请求与响应模型、服务层方法、端口与适配器上的同名方法、只服务它的两个数量常量、以及点名它的单测与文档。Chunk 级的命中载荷和它的映射逻辑保留，分组链路仍在用。

**当初的判据与它错在哪**：0013 写下那句时并没有为「保留」给理由，它是那轮重构的**范围声明**——本轮题目是检索页的形态，后端接口动不动不在题目里，于是默认「留着是零成本」。这条默认判断是错的。`/vector-search` 从落地起就没有任何生产调用方：前端检索页走按文档分组的 `POST /document-search`，Agent 的检索工具走同一条分组链路，全仓库唯一调用它的是它自己的单测。零调用方不等于零成本，代价是两条检索契约并行演化——schema、服务层、端口与适配器、单测、OpenAPI 生成物和若干份文档都要跟着这一条没人用的路径维护。错的性质是把「没有调用方」读成了「留着无害」。

## Consequences

这是一次不可逆的对外契约变更。仓库内已经没有调用方，但仓库外的脚本不受本仓库约束，删掉就是 404；恢复的成本等于重写一条路由加它的 schema、端口与适配器，不是翻一个开关。

**撤销本身该被推翻的条件**：出现一个真实在用的 Chunk 级调用方，判据是「已经有人在生产里传 query」——检索页要做片段级的展示或筛选、评测集要按 Chunk 取命中、外部脚本要按片段取数都算。届时应按当时的需求重写接口，不要从旧契约里捞一份回来：捞回来的那条是按旧调用方的形状写的，带着四维过滤这种从没有入口的参数，会立刻变成第二次「留着无害」。设想中的「以后可能有人要」不算判据，0013 那次正是被这条设想拖住，留下两份契约并行演化了一轮。
