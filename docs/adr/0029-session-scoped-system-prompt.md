# 会话级系统提示词在建立时固定

系统提示词此前是「每轮请求的参数」：前端每轮把值发上来，后端直接装进本次运行的上下文，既不落库
也不读会话。本决策把它改成**会话级设定**——建会话时从账号的个人偏好读一次，写进 `agent_threads`
的 `system_prompt` 列，此后这个会话的每一轮都用这份值，中途不可改；账号在设置页改了提示词，只影响
**新开的会话**。请求体里的 `system_prompt` 字段随之删除。

## 为什么要固定

**回放看不出当时用了什么设定。** 提示词不进 checkpointer 的消息历史（`agent/replay.py` 的模块
说明写明：它由 `resolve_system_prompt` 每次动态注入模型请求），所以回头看一条历史回答时，无法
知道它是在默认提示词下产生的还是在某份自定义提示词下产生的。落进会话表之后，回放按 `thread_id`
查一次就能回答。

**去掉一个由客户端引入的前缀不稳定来源。** 上游中转站普遍对前缀稳定的请求做缓存计费，而每轮由
浏览器重送提示词，只要前端存储或请求组装有任何变化，前缀就变了。**这条收益有明确上限**：提示词
末尾的日期段由 `append_current_date` 无条件追加，拼的是 UTC 当天日期，跨过零点前缀必然变化。因此
本决策只承诺「去掉客户端引入的不稳定来源」，不承诺缓存持续命中。日期机制不动。

## Considered Options

**继续每轮由请求体传，只把值复制一份到会话表。** 改动最小，但等于让提示词有两个事实源：设置页
改的值在前端，会话建立时取的值在后端，两者靠前端每轮传参对齐——而那正是本决策要消灭的形态。

**提示词写进用户消息的 `additional_kwargs`，供回放读取。** 放弃。那是运行级元数据的口袋
（`run_id`、`scope` 都在里面，每轮都可能不同），而提示词是会话级属性，整个会话恒定不变，两个层级
不该共用同一个口袋。而且它会让系统提示词进入 checkpointer 的消息历史，推翻 `replay.py` 记录的
既有设计。

**会话已开始后在设置页把编辑器置灰。** 放弃。设置页的编辑框是全局的、管的是后续新会话，把它灰掉
会让用户没法为下一个会话准备提示词，是功能损坏。「当前会话已锁定」对用户也不是一个需要应对的状态。

## Consequences

**`agent_threads` 的 `system_prompt` 列与 `scope` 列的写入语义相反，这是有意的。** `scope` 续聊时
请求带了就覆盖，另有 `PATCH /agent/threads/{thread_id}/scope`；`system_prompt` 建立后不变，续聊
不重读偏好。同一个 `ensure_thread` 里并排放着两种相反的语义，实现时必须在它的 docstring 里写清，
否则后来的人会以为其中一处写漏了、顺手「修」成一致的——那会分别破坏 `scope` 的改选能力或提示词的
恒定性。

**存量会话直接清空，不写兼容分支。** 项目仍在开发阶段，没有真实用户在用。清理顺序固定为「先清
checkpointer 的历史，再删 `agent_threads` 的归属记录」，理由与既有删除路径一致（见 ADR 0009 与
`api/agent_threads.py` 的 docstring）。按这个顺序清理不会产生孤儿会话，不需要跑
`prune-orphan-threads`。
