# 部署的「形状」只有一个写入者：CI 写形状、服务器的 `.env` 写值、图形界面只读

栈编排 `backend/docker-stack.yml` 由 CI 在部署时上传并执行 `docker stack deploy`，服务器 `<DEPLOY_DIR>/.env` 只提供值（密钥、地址、规模），1Panel 与 Portainer 只用于查看和应急。写入者超过一个时，「谁最后写谁生效」，回滚回到的可能是某次手工改动留下的形态，而不是任何一版代码。

具体分工是三句话。**CI 管形状**：服务、副本数、更新顺序（先起后停）、停止宽限、健康检查都来自 git 里那份 `backend/docker-stack.yml`，改形状要改文件、走一次部署。**`<DEPLOY_DIR>/.env` 管值**：密钥、地址、规模等键由服务定义里的 `env_file` 注入容器，CI 只读不写；改值不需要动 git，但要按部署手册「手工跑一遍同一套流程」重新部署一次才生效（`docker stack deploy` 会把新值写进服务定义并滚动更新）。**图形界面只读**：1Panel 与 Portainer 用来看服务状态与容器日志，栈显示「在 Portainer 外部创建、控制权受限」是预期的。

例外只有一条：**应急时人工 CLI 是允许的写入者**（`docker service update --rollback` 回上一版、切指定镜像、`--force` 重启）。它改的是当前服务定义的状态，不改变「形状的真源在 git」——所以手工做过之后要回到 CI 部署，让服务定义重新由文件决定。

## Considered Options

- **在面板里改环境变量或重新部署**：改动不持久，下次 CI 部署按 git 与 `.env` 覆盖回去。症状是「我明明在面板上改了，过两天又变回去了」。
- **在面板里新建第二个栈**：会出现第二份服务定义，症状是「改了没生效」；更糟的是回滚目标被污染——`--rollback` 回到的是那个栈的最后一次更新。
- **把形状整体交给面板管**：面板的编排形态与栈文件不是同一套（见 [0039](0039-swarm-start-first-deploys.md)），而且 1Panel 对 Swarm 的态度是中长期不专门支持。

## Consequences

部署与回滚的目标因此总是可预测的：一个栈、一个形状来源、一个值来源。代价是想改形状必须走一次部署，哪怕只是加一个健康检查；面板上那些「编辑」入口也不能当部署用。
