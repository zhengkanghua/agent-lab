# 用量统计模块与项目领域解耦

用量统计放在一个独立子包里，只吃一个纯数据结构——UUID、数字和字符串枚举，不导入 `agent/`、`knowledge/` 或任何 ORM 模型，也不把 LangSmith 之类的第三方可观测平台当数据源。这样它能在不改业务代码的前提下整块搬走，把写入入口从函数调用换成 HTTP 上报就能接到外部 LLMOps。

## Considered Options

**复用已有的任务受理机制来持久化。** 那套为「受理一条都不能丢」设计，每次模型调用都要落库、投递、等 Worker 领取，对一条纯追加的事实记录太慢太重，且写入要等 Worker 才完成。

**把 LangSmith 当用量数据源。** 它是可选开关、可以被关掉、可能采样，schema 由外部控制；而用量必须能脱离它重算和展示。它继续只当调试视图。

## Consequences

写入契约不传 `UserRecord` 这类 ORM 对象——传了就搬不走，契约里只有标识符和数字。采集失败不得影响对话：记录入口 fire-and-forget，写库失败只记自己的日志，不向调用方抛异常。

用量先进进程内队列、批量写库，所以查询结果有约一秒的延迟。队列有界，容量按「数据库挂多久不丢
数据」定而不是按突发倍数定：它只是内存兜底，不是限流，正常与异常情况下都基本不可达。进程退出前
必须把队列排空：没有退出排空的异步写入会在快速重启时丢掉最后几条，且不报错——这正是本项目
参考的开源网关踩过的坑。

`CONTEXT.md` 因此不收录「LLMOps」一词：它是这个模块将来独立部署后的平台形态，也是数据的下一个归属地，不是本项目当前的概念。
