# 破坏性迁移等旧容器退出之后才执行

数据库迁移分成两段执行，边界由迁移文件里的一个标记决定：加列、加表、加索引这类**向后兼容**的变更不带标记，照旧在 `docker stack deploy` 之前跑完；删列、改列名、改语义、拆约束这类**破坏性**变更在迁移文件里写 `POST_DEPLOY = True`，由部署脚本推迟到新容器就绪、旧任务**全部退出**之后才执行。判断边界的脚本是 `agent_lab.scripts.alembic_pre_head`，它从 head 往回走、跳过所有带标记的迁移、停在第一个不带标记的 revision；迁移链有多个 head 时它直接失败，不猜一个值出来。

这样安排买到的是**部署失败时的退路**。在这之前，迁移一律先跑，于是「新容器起不来」这件事的后果被放大成整站不可用：列已经删了，旧任务还在排空（停止宽限 180 秒，见 [0039](0039-swarm-start-first-deploys.md)、[0051](0051-drain-without-handover.md)），它读到不存在的列就崩；更新器按 `failure_action: rollback` 退回旧容器，退回去的旧容器照样读那些列、照样崩。分两段之后，破坏性变更执行之前库一个字没改，旧容器完好，`--rollback` 或重新部署旧版本都安全。

**它不解决另一半问题，这一点必须说清。** 发布成功、破坏性变更也执行完之后，旧代码就跑不了当前结构了，那时候 `--rollback` 会成功、服务是坏的。要保住「发布之后还能退回上一版」，仍然得把这类迁移拆两次发布（先发「代码不再用它」、下一次发布再删）。两阶段执行让「部署失败」这一半有了机械保证，「发布成功之后」那一半还是发布纪律，两件事不能混。

**判据不能数容器个数。** 等待旧任务退出时，第一版判据是「`docker ps` 里 Up 的容器数回落到副本数」，它是错的：滚动更新按 `parallelism: 1` 逐个替换，中途会出现「一个旧容器已经退出、另一个还在排空」而 Up 个数刚好等于副本数的瞬间，那时放行就会删掉另一个旧容器正在读的列。正确判据是数「已经被要求停、但 `CurrentState` 仍是 Running」的任务（`docker service ps --filter desired-state=shutdown`），三个服务都归零才算退干净。就绪判定也看不出这件事：排空中的旧任务 `desired-state` 早已不是 `running`，它在「运行中任务数不少于副本数」那条检查里是隐形的。

## Considered Options

**让数据库也能自动降级（版本化回滚）。** 部署时记录每次发布对应的 alembic revision，回滚时先 `alembic downgrade <上一个 revision>` 再切镜像。技术上可行，我们那三条删列迁移的 `downgrade` 都是干净的「加回一个可空列」。否掉有两个理由：一是降级路径平时没人跑、紧急时刻才第一次跑，出错的概率比不回滚还高，这也是业界对关系库的一致口径——推荐往前修或让变更向后兼容，而不是回滚结构；二是它要求每次部署记一份「版本—镜像」对应关系，为一个紧急时刻才用的路径养一套平时没人验证的机制。真需要「发布后还能退」时，拆两次发布更简单，代价只是多一次发布。

**拆两次发布（原来 0039 写的那条）。** 这是绕开而不是解决：它靠流程约束让「需要回滚库」这件事不发生，人一旦漏了就没有任何东西兜底；而且它把一次改动拖成两次发布。两阶段执行把「部署失败」这一半从纪律变成脚本行为，纪律只留在「发布成功之后」那一半。

**把迁移全部挪到换容器之后。** 对这批删列迁移成立，因为新代码本来就不读那些列。但对加列类不成立：新代码要用新列，容器在缺列时起不来，更新器回滚，于是迁移没跑、部署永远上不去，是个死锁。所以必须按迁移的性质分两类，不能一刀切。

**不真删列，留成僵尸列。** 让旧代码永远能跑，退路永远在。否掉是因为它把「没有读者的一列」永久留在库里，这类残留正是本次清理要消掉的东西，用它换退路等于把问题换了个形态。

## Consequences

**漏写标记不会有任何报错。** 加了 `drop_column` 却忘了写 `POST_DEPLOY`，那条迁移就按老办法在第一阶段执行，把还在排空的旧容器打死，而这个错误只在部署那一瞬间才可能暴露。这是整套机制唯一靠人的地方，写进了容器部署文档的约束第 8 条。想让它机械可查，需要在部署侧或一条静态检查里枚举「这条迁移里有 `drop_column`、改名、改语义、拆约束就必须带标记」，本次没做。

**等待超时按「部署失败但服务正常」处理。** 240 秒内等不到旧任务全退，脚本报失败并跳过第二阶段迁移；此时新容器已经在服务、库没被改，下次部署重试这一步即可。这条路径的代价是一次红色部署，而不是一次故障。

**用量库那条链没有标记，行为不变。** `llmops` 有自己的迁移链（见 [0032](0032-usage-data-in-separate-database.md)），它的迁移都是加表加列、向后兼容，所以全部在第一阶段跑。将来那条链若出现破坏性迁移，同样要加标记，脚本按 `ALEMBIC_CONFIG` 区分算的是哪条链。

**撤销这件事的条件**是先有「发布成功后也要秒级退回」的真实需求，而那时更该做的是拆两次发布，不是给这套机制加降级能力。这套东西的位置很清楚：它只保证部署失败时旧容器能顶住，不做数据库回滚。
