# 部署时只排空，由旧进程自己收尾

本决策取代 [0040](0040-run-handover-on-deploy.md)，保留排空、删除接手。进程收到退出信号后仍把在途运行**排空**——停在当前 superstep 做完、状态落盘的那一刻——但不再在会话行上记「被排空、等接手」，也不再有任何进程去扫那个标记、重建运行上下文续跑。停在边界的这次运行由旧进程**自己**收成未完成：补写已推出但未落库的文字、写进会话历史、释放会话位、发一个终态事件，然后退出。用户看到的是「未完成」的现有内容，会话立刻能接新提问。

排空本身一行没删：`RunControl` / `GraphDrained` / `request_drain` 都是 LangGraph 上游的能力，我们写的只是接线。三个预算数也不动——停止宽限 180 秒、排空上限 120 秒、uvicorn 关停超时 30 秒——只是排空成功之后那条路从「写一个标记」变成「跑完整个收尾」，余量从「可能用上」变成「必然要用上」。

**当初的判据，以及它错在哪**：0040 给接手的判据是「用户在界面上不感知，随后拿到完整答案」——正在回答的那一轮不该让用户重发。它失效的性质是收益与成本同时被估错。收益侧，「不感知」本来就打了折：连接会断一次，界面会短暂显示「正在生成」，真正换来的只是那一轮不用重发；而重发这条路是现成的（刷新后看到未完成，点重试或直接追问）。成本侧，排空是上游的轮子，接手那半全是自研：跨进程认领、重建运行上下文、从冻结元数据读回范围、认领之后失败的放弃路径、带标记的会话不能被新提问顶掉，外加为了接手才持有的进程级图与追踪配置。一整套机制只换「部署时那一次不用重发」，不划算。

顺带纠正一处写错的论证：排空成功那一支原先写着「补写会把已经落盘的内容写成重复的一截」，这条理由不成立——`GraphDrained` 抛出时，尚未落库的那部分文字必然是空串（收到落盘确认就清空），补写是空操作。原先拒绝补写的另一半理由「释放会话位会让接手找不到它」随接手一起消失。所以把排空并进统一收尾不是推翻一个有意行为，是纠正一处论证。

## Consequences

用户可感的后果要如实记：部署或重启时正在回答的那一次，会停在边界、标成未完成，刷新后看到的是已经输出的部分、不会自己长完；会话不锁死，可以立刻追问。界面上不新增任何文案或标注。强杀、内存耗尽、断电不受影响，表现与改动前完全相同——那一类从来没有人替它收尾。

跨进程停止机制一行不少：生产是 2 个副本 + 先起后停，停止请求仍可能由另一个进程写下（见 [0037](0037-cross-process-run-coordination-in-database.md)），取消接手不减少它一行。「放弃」这条收尾路径也仍然必须存在，只是触发点从两个收成一个：排空等待超时。

排空之后留下的半途 checkpoint 会与同一会话的下一次提问耦合：会话已经解锁，而旧的待跑节点还在那份状态里，新运行可能把它一起带出来。这是取消接手带来的新常规状态，不是已知缺陷，落地时要实测确认表现。也因此「两次部署之间图状态结构不变」这条发布纪律不能删——它的理由不再是有进程要接着跑完，而是排空留下的半途状态会被新代码读到。

**撤销本身该被推翻的条件**：那一轮的损失变成真实成本时——一次运行到分钟级以上、部署频繁、外部用户规模上来，重发本身以及「半途状态被下一次提问读到」的代价开始真金白银地付。判据是重发成本大于接手成本，不是「部署更顺一点」。届时应先看上游或平台是否已经把接手做成现成能力（LangSmith Deployment 的 resumable streaming 已经把运行所有权、排空、断线续上一起管了），再决定是自己写那半套还是换形态；直接翻回 0040 不是选项。
