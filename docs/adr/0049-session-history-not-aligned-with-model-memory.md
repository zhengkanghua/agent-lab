# 会话历史仍落业务表，界面不再对齐模型记忆

本决策取代 [0044](0044-session-history-in-own-table.md)，并保留它的主体：用户回看的会话历史落我们自己的业务表，每轮结束写进去、界面读它；LangGraph 的 checkpointer 退回原本的角色，只存上下文记录，压缩策略怎么改都与用户看到的东西无关。撤销的是 0044「代价」段那句自我约束——「两份数据不一致时，界面必须说清哪一份是模型的记忆」——以及 Consequences 里那条「摘要那条分界痕迹要一并转存过来，否则界面上画不出那条分界线」。落实下来是整条分界线消失：库里那一列、压缩发生时在摘要行上记下它的转存、读出、对外字段、前端那条线与它那句长文案，摘要行本身也停写。

**当初的判据，以及它错在哪**：0044 只留下这条结论、没有写推导，访谈时已无法复原当时的思考，能读到的判据就是它自己给的那句——那是仓库里第一次为同一段对话保留两份数据，而 `replay.py` 的模块说明曾以「副本注定和真实上下文分叉」拒绝过这种做法，这条自我约束是给那个担忧上的保险：既然分叉了，就在界面上标出哪一份是模型的记忆。错在把「两份数据不同」当成了「必须向用户解释这个不同」。界面展示读的是业务表，模型上下文是 checkpointer 的事，两个用途本来就不同——用户要完整历史，模型要控上下文预算，没有谁需要向谁对齐。业界三家（ChatGPT、Claude、Gemini 的 Web 端）也都把上下文压缩边界留在内部，没有一家把它画进对话流。

残留价值只有一条：连续问很多轮之后，用户问「你刚才说的那个数字是多少」，模型可能答不出来。这一条靠行为解决就够——它会自己说资料不足，不需要一条常驻分界线替它解释上下文预算。代价是「模型只保留了摘要」这件事从此不可追溯：分界标记只能在压缩发生的那一刻记下、事后推不出来，摘要行也停写，所以已压缩过的会话里不再有任何可回查的痕迹。这个代价是有意接受的。

## Consequences

两份数据仍然存在，也不会合并：业务表是用户看到的档案，checkpoint 是模型的上下文。本决策改变的是「不需要在界面上表达这个差异」，不是「差异不存在」——下一次有人想在界面上画出模型记忆，先读这一段。

会话历史的写入点仍在运行收尾路径上，而那条路径有多个入口（用户停止、排空、上游失败或超时），同一次运行的收尾仍可能被执行不止一次，所以这张表必须**按运行去重**，否则一次收尾会写成两轮。这个要求的理由不再是「另一个进程会接手」——接手那条路径已取消（[0040](0040-run-handover-on-deploy.md) 已被取代），去重留下是因为收尾本身可能被重复执行。

**撤销本身该被推翻的条件**：界面要展示的对象与业务表里的记录不再是同一个东西，也就是「模型记得什么」本身成为用户能看、能动的东西——查看或清空模型记忆、选择只看最近若干轮、长会话里按记忆边界回滚。判据是「用户会因为不知道模型记得什么而做出错误决定」，不是「两份数据不同」。真要恢复，得在压缩发生的那一刻重新落一条事实，事后推不出来，成本远不止一条文案。
