## 二、当前能力（一句话版）

Agent 问答：`/agent` 入口，`POST /agent/chat` 走 SSE，六种事件（`run_started` / `token` / `tool_call` / `tool_result` / `done` / `error`）。模型只有两个只读工具（检索文档、读取全文），运行范围按会话冻结在开始运行之前，工具内不能扩大。证据以 `[[E...]]` 标识随工具结果下发，收尾核验成 `citations` 与 `invalid_citations`，前端渲染成可点的小丸，点开进阅读器看当前原文。会话侧栏按今天／昨天／本周／更早分组、分页、可删不可改名。历史与记忆叠了三层机制：整份历史送模型、旧引用标识在发送副本上剥掉、超阈值时先清理旧工具正文再压成中文摘要。运行脱离 HTTP 连接，停止走独立接口（`run_id` 比对，最多 1 秒生效），进程收尾时排空并在部署后由新进程接手。上限全部写在 `agent/limits.py` 且不进 `.env`。用量由包装 chat model 采集，落独立 `llmops` 库。

向量库查询：`/search` 走 `POST /document-search`，按 Document 分组，`document_limit` 1..100（默认 10）、`matches_per_document` 1..20（默认 3）。后端还支持 `score_threshold` 与整组 `filters`（来源、提供方、文档类型、标签 OR、发布时间区间），**前端没有暴露这两项**。页内支持多轮累积（检索流）。数量参数不在这页，在设置中心的「检索偏好」。按片段的 `/vector-search` 后端保留、前端已不用。

完整导航见 `docs/FEATURE_MAP.md`，本文不复述。

## 三、与业界对比的结论

三家（ChatGPT、Claude、Gemini 的 Web 端）是通用助手，本项目是只读的知识库研究助手。拿通用助手的功能全集当尺子会得出一张很长的「缺」清单，而其中大部分与本项目定位无关。按这个前提，结论是：

真正该补的缺口只有三个——**重新生成**（老板已定暂不做）、**跨会话记忆**（老板已定暂不做）、**跑完通知**（既然运行已经脱离连接，通知是这条链路的自然收尾，目前未决）。

三处我们比三家更细：工具轨迹透明度（按工具名合并计数、失败落定时不收起）、模型失效态不静默回落、用量明细到模型维度。

一处明显的产品定位错位：**把裸 system prompt 当作面向终端用户的设置项**。三家都不让用户编辑完整提示词，给的是包装过的风格指令（Custom instructions / Project instructions / Customize），且不会让用户指令与应用安全规则在同一个提示词里竞争。我们这里是用户写 4000 字，中间件再硬追加三段高优先级规则。

一处只有我们有的 UI：**记忆分界线**。查到的三家官方文档与第三方梳理里，没有任何一家把上下文压缩边界画进对话流。

## 四、已经定下的事

### 4.1 工程文案按三类改造

现状是把内部机制写进用户可见文案，个别句子还描述了用户根本看不到的现象。分类与处置：

第一类，状态信息，保留原样：「执行中」「未成功」「N 项未成功」（`AgentToolTraceList.vue:45`、`:124`）。这些是用户当下真需要知道的，措辞也是人话。

第二类，机制解释，改成「用户能做什么」：记忆分界线那句长文案（`AgentTranscript.vue:33`）、`本轮对话中断，这次工具调用的结果未送达。`（`useChatStream.ts:36`）、`这次工具调用没有结果记录，当时的对话中断了。`（`useThreadHistory.ts:39`）、`会话记忆连接中断`（`model/agent-error.ts:78`）。改法示例：「这次检索没拿到结果，可以重试」比描述中断机制有用。

其中记忆分界线那句还有个独立问题：后半句「较早的工具原文可能已被清理成占位文字」描述的是**模型那一侧**的状态。`AgentTranscript.vue` 自己的注释就写着回看读的是业务表、用户看到的原文始终完整，所以这半句在界面上根本对应不到任何可见现象。它是否整条保留见第五节。

第三类，只该出现在模型上下文里的，要核实到不了用户眼前：`[出处已失效]`（`evidence.py` 的 `STALE_CITATION_NOTICE`）与 `[... tool result middle pruned ...]`（`limits.py` 的 `PRUNED_TOOL_RESULT_PLACEHOLDER`）。按 ADR 0044 的设计，回看读的业务表在运行收尾时写入、此后永不清理，被清理的是 checkpoint 里的历史轮消息，那些轮次早已写进业务表，所以这两个占位符正常情况下不进用户视野。**这一条是按 ADR 描述推的，没有逐行核实 `project_run_messages` 的投影时机**，实施前要实跑一次确认。

结构性建议：现在这套文案的问题不是多，是用内部视角写。同一句话内部用户读起来是「系统很诚实」，外部用户读起来是「这个产品不太稳」。改造时把它们集中到一处按「用户能做什么」重写，而不是散在各组件里各自解释机制。

### 4.2 「重新生成」不做，现有「重试」够

现状的准确描述是「重发」而不是「重新生成」：`useChatStream.ts:286` 的 `retry()` 把最后一轮的 `question` 塞回草稿框再调一次 `send()`，开的是一次全新运行，重新检索、重新调模型，失败轮保留在历史里便于对照。因为整份历史送模型，第二次回答能看到第一次写了什么。

业界的 regenerate 是同一份上下文重新采样，通常替换原回答或形成分叉。两者不是一回事。老板定：重试够用，不做 regenerate。

### 4.3 删除自定义系统提示词功能，只用内置提示词

老板已定：完全删除自定义系统提示词，直接用我们写好的系统提示词。

连带删除：账号偏好里的 `system_prompt` 字段与会话行上的快照字段（ADR 0029 的落地）、`GET /agent/default-prompt` 接口、设置页那一项、Agent 页上「本轮用了自定义提示词」的徽章、`middleware.py` 里 `select_system_prompt` 的「用户写的 / 内置默认」分支（简化成固定提示词 + 三段追加）、`limits.py:72` 的 `MAX_SYSTEM_PROMPT_CHARS`，以及对应测试。

连带要处理的决策记录：**ADR 0029（会话级系统提示词）失效**，需要 supersede。按仓库约定 ADR 只在 `domain-modeling` 访谈里写，本文不下手；与 5.2 改 ADR 0044 是同一趟可以一起做的事。

代价要记住：用户从此无法调整回答风格。三段追加（日期、「历史不是本次证据」、「资料边界」）保留，理由见 6.3。6.3 里那三个动作因此作废，只保留「三段追加不砍」这部分事实。

### 4.4 跨会话记忆暂不做

低成本的一致性修补：新会话空态现在只写「Agent 在选定的知识库中检索文档、读取全文，并根据查到的资料作答」，没有一句告诉用户它不记得上次问过什么。既然决定不做，就在这里用一句轻文字说清边界。

### 4.5 两套流式处理合并

`useChatStream` 与检索页的 `useSearchStream` 目前刻意不共用，注释里写明了理由。老板定：合并，两套容易分叉。

核实代码后发现这句「两套流式实现」说得不准：`useSearchStream` 里没有 SSE，它是一次性 `await searchDocuments(...)`，拿到整份 JSON 就结束；SSE 帧解析本来就只有一份，在 `api/agent-chat.ts` 里。所以真正有两份、会随改动分叉的不是流式管道，而是**陈旧响应守卫**——两处各写了一遍同样的序号比对，连理由注释都各写一份。

合并的边界因此收窄成：把那个守卫抽成一份纯逻辑，`useChatStream` 与 `useSearchStream` 各自调用。两者真正不同的「运行是一等公民」还是「请求是一次性」仍然留在各自的生命周期里。`useChatStream` 里那个 `runSequence` + 本轮 `runId` 的双守卫（理由：AbortController 拦不住「事件已拿到、await 未恢复」那个窗口）就是这份实现的内容。另外三处同类拷贝（会话历史、文档审核、cron 预览）刻意保留不动：它们各自的路径与理由不同，合并它们属于另一个需求。

### 4.6 `UnknownToolGuardMiddleware` 去掉

它的存在理由写在注释里：`LLM_MODEL` 曾被配成中转站的 `auto` 路由，模型发出过 `Bash(...)` 调用。现在模型来自目录、由自己配的渠道提供（ADR 0046），触发条件已消失。

去掉后的后果要记住：LangGraph 会自己回一条 `status="error"` 的 `ToolMessage` 让模型纠正，而这个类自己的注释写明了模型通常纠正不了，用户看到的是「查了资料但不回答」。万一再出现模型乱发工具名，排查会从「第一条日志指向工具名」退回到「从前端和流式管道查起」。这个代价已被接受。

### 4.7 用量采集的架构保持不变（审查结论修正）

上一轮审查把「用量采集的完整度」列为过度设计，这个判断是错的，已收回。

独立迁移环境不是顺手加的，是 ADR 0032 的直接后果：用量数据放在独立的 `llmops` 库，理由是将来抽成独立 LLMOps 服务时整库可以直接 dump、业务表一行不用碰、抽取之后只被授权这一个库。ADR 0033 再把模块本身解耦（只吃 UUID、数字、字符串枚举，不导入 `agent/`、`knowledge/` 或任何 ORM 模型）。第二套 alembic（`backend/alembic_usage.ini` + `backend/usage_migrations/`）是「第二个库」的必然产物。

判断错在方法上：当时只看到 `FEATURE_MAP.md` 里「有自己的迁移环境」几个字，没读这两条 ADR 就下了结论。

留一个真实的张力供老板判断，不是建议改动：ADR 0032 的立项理由是「将来抽出独立 LLMOps 服务」，而那个目标形态今天并不存在。按 `AGENTS.md` 工程取舍第 1 条（仅有「以后可能需要」的设想不足以引入约束），这条决策站在那条规则的边缘。它值不值，取决于「抽出 LLMOps」有多确定。

## 五、还需要拍板的事

### 5.1 「原文对照」（引用与证据层）要不要保留

这是这轮最需要判断的一条。先把机制用大白话说清。

每份工具结果发下去的时候，系统会为它盖一个流水号（`E` 加 12 位十六进制，形如 `[[E1a2b3c4d5e6]]`），并在提示词里要求模型「引用时把这个号原样抄上」。号只能由系统发，模型编不出来——这正是它比「让模型自己写文档标题」可靠的地方。

麻烦出在第二轮。整份历史都送进模型，上一轮回答里那句「……`[[E1a2b3c4d5e6]]`」就摆在它眼前。模型看到自己上次这么写过，下一轮很容易顺手照抄同一个号。可这次真正发下去的号是新的，上一轮那个号不在这次的账上，核验时就变成一条点不开的引用，前端会显示成「有引用解析不出来」。

所以系统在把历史递过去之前，先用橡皮把旧号擦掉、改成 `[出处已失效]`。它不是在宣告「这个出处过期了」，是在把可抄的字从纸上抹掉，逼模型只能引用这次真正发下去的号。

为什么不靠提示词叮嘱「别抄上次的」？因为模型不是靠记住规则来避开的，它靠的是「眼前有什么就照着什么写」。叮嘱不管用，擦掉才管用。

顺带回答老板提的思路：「想清空记忆就开新会话」不解决这个——擦的是**同一个会话里**上一轮留下的号，跨会话本来就没有上一轮的号可擦。

下面是与上面同一件事的技术描述，供实施时对照。先澄清一个误解，它影响判断：`[出处已失效]` 那层处理**与原文改动无关**。引用核验（`evidence.py` 的 `resolve_citations`）只按 `citation_id` 关联，`DocumentEvidence.content_hash` 记录取证时的正文版本，从不参与「与当前正文是否一致」的核验。原文被替换后，旧轮次的引用照样点得开，指向当时读到的那一版。

它要处理的是另一件事：**模型会照抄**。`api/agent_chat.py` 把整份历史送进上下文（ADR 0045 撤掉了历史裁剪），历史回答里带着上一轮的 `[[E1a2b3c4d5e6]]`，模型看到自己上次这么写过，下一轮大概率照样写。而新一次运行只承认本次工具结果分配的标识，抄来的全部落进 `invalid_citations`。`strip_stale_citations` 就是在发送副本上把它换掉，断掉照抄的通路；只改副本是因为 `request.messages` 与 graph state 是同一批对象，就地改会把剥离后的文本写进 checkpoint。

老板提出的思路是「一个会话一个问题的时代才需要它，现在记忆保留、用户想丢弃记忆就开新会话」。这条路不成立：照抄问题恰恰出现在**同一个会话的第二轮**，与记忆该不该留无关；只要历史里有旧标识、而模型又被要求写引用，它就会抄。

另一种思路是「把号整个删掉，问题不就没了」。这条路不通，因为号就是引用的身份证：前端点开一条引用时要凭它找回「哪篇文档的哪一版」（`citation_id` → `document_id` + `content_hash`）。号没了，引用就无法定位，用户点不开任何东西。

能不能改成让模型输出文档标题、前端按标题匹配？不可靠：标题会重复，模型会改写或编造标题，而编造一个标题比编造 12 位十六进制容易得多，那层防伪造就没了。改成「本次回答内的序号」也不行：序号只在一次回答内成立，历史回看时旧回答里的 `[1]` 已经没有对应的列表可查。

所以现状已经同时满足了两头：**模型看到的是擦过的历史，用户看到的是完整的存档**。擦只发生在「送给模型的那一份副本」上，checkpoint 与业务表都不动，回看时引用照常点开。也就是说「历史里有旧号会被模型抄」这个问题今天就已解决，不需要再改。

要砍就整条砍，不能只砍 strip 那 20 行——只砍它会让模型更容易写出解析不出来的标识，前端出现一堆原始 `[[Exxx]]` 文字。整条砍的范围：

- 提示词里的引用要求（`DEFAULT_SYSTEM_PROMPT` 的「关键结论附引用」、中间件硬追加的「原样引用本次 Tool 给出的 `[[E...]]`」）
- 工具里的 `citation_id` 前缀与 `ToolEvidence`
- `artifact` 及 `validate_tool_evidence` 这套双路径共用校验
- 业务表的 `evidence` 列
- 回放里的引用核验
- 前端引用小丸、`open-evidence` 这条链、`invalid_citations` 提示

**不在此列**：`DocumentReader` / `useDocumentReader` 是 `DocumentReader` 复用的，`/admin/files`、`/admin/documents` 也在用，砍引用不影响它。

我的判断：不砍。它是这个产品唯一区别于「通用 chatbot 接私库」的东西，而且是防幻觉的硬护栏而不是装饰——`citation_id` 由应用生成、模型只能照抄不能自己编，这一点比让模型输出文档标题或 UUID 可靠得多。

但讨论中老板把问题推到了更实质的一层：点开引用能看到什么。核实后发现那里确实有偏差，而且比「留不留引用」重要得多，见 5.4。结论是引用保留，但点击后的展示要从「直接打开当前全文」改成「先看见当初那段」，而这是纯前端改动。

### 5.2 记忆分界线删不删

先说清它的由来，这是老板没听明白的那部分。

它不是为了用户需求而加的，是 ADR 0044 自己写的一条自我约束。那条 ADR 把用户回看的会话历史从 checkpoint 搬到业务表之后，「界面显示的完整对话」与「模型手里的那份上下文」第一次成了两份数据，它的 Consequences 里写着：「剩下要守的是：两份数据不一致时，界面必须说清哪一份是模型的记忆。」记忆分界线就是这句话的实现，数据来源是压缩时记在摘要消息上的 `memory_boundary_run_id`（`middleware.py` 的 `_build_new_messages`），事后推不出来，所以只能用一条线表达。

老板的反问是对的：模型记忆是 checkpoint，压缩后是什么样就是什么样；用户看的是业务表，目的是看到完整历史。这两个用途本来就不同，不需要对齐。所以那句话的理由不成立——用户不需要知道模型的上下文预算是怎么花的。

真实的残留价值只有一个：连续问了很多轮之后，用户问「你刚才说的那个数字是多少」，模型可能答不出来。但这件事可以通过行为解决（它自己会说资料不足），不需要一条常驻分界线。

所以我的建议是删。老板已批准可以动。删除时**这等于撤销 ADR 0044 里那句自我约束**，要改 ADR；按仓库约定 ADR 只在 `domain-modeling` 访谈里写，本文只记结论。同时要一并删的还有：`AgentTranscript.vue:32` 的文案与 `:72` 的渲染、`conversation.ts:63` 与 `:187` 的字段与赋值，以及后端 `replay.py` 把分界标记从 checkpoint 摘要消息转存到业务表的那段逻辑（既然不再画线，就不必再转存）。

### 5.3 部署排空与接手选哪一档

先纠正一个事实，它影响结论：前端**没有轮询重发机制**。`useThreadHistory.ts` 里那组常量是 `RUN_WATCH_INTERVAL_MS = 3000`（刷新后每 3 秒问一次「这轮还在跑吗」）与 `RUN_RECOVER_ATTEMPTS = 5` × `RUN_RECOVER_INTERVAL_MS = 6000`（约 30 秒，刻意覆盖「先停后起」的部署窗口）。它等的是同一个在途运行，等不到就回退成「中断」，由用户自己决定要不要重发。

而且 ADR 0040 有一条连带事实：**容器停止宽限期从 600 秒降到 180 秒，正是排空换来的**。取消排空，这个 600 秒要还回去；ADR 0040 自己的估算是「按有界执行常量的最坏组合，一次运行能拖到小时级」，所以完全取消意味着一次部署可能要等接近一次运行的时长。

三档的实际形状：

| | 保留（现状） | 完全取消 | 只排空、不接手 |
|---|---|---|---|
| 旧进程退出前 | 等当前 superstep 落盘，记「等接手」，退出 | 不动作，靠宽限期等连接和任务结束 | 等当前 superstep 落盘，记「未完成」收尾，退出 |
| 新进程 | 每 30 秒扫描、认领、重建上下文续跑 | 无 | 无 |
| 用户看到 | 连接断一次，短暂「正在生成」，随后拿到完整答案 | 那一轮被截断，看到半截内容，会话解锁，可重发 | 那一轮标成未完成，可重发 |
| 部署等待 | 一个 superstep 级 | 一次运行的时长（最坏小时级） | 一个 superstep 级 |
| 要删的代码 | 无 | 排空与接手全套 | 只删接手那半边 |
| 额外风险 | 图状态结构改动后的接手正确性只能靠发布纪律 | 没有 | 没有 |

老板已定**第三档：只排空、不接手**。这档也是我的推荐。成本大头不在排空，在接手：接手要跨进程认领、重建运行上下文、从冻结元数据读回范围、处理「认领之后失败」的放弃路径、保证「带等接手标记的会话不能被新提问顶掉」（ADR 0040 那条条件写入的失活分支）。这一整套换来的收益只是「部署时正在回答的那一轮不用重发」。

**排空那半边其实已经是上游的轮子。** `runs.py:28`、`:30` 分别从 `langgraph.errors` 和 `langgraph.runtime` 导入 `GraphDrained` 与 `RunControl`，这是 LangGraph 上游（PR #7274「allow graph to graceful shutdown/drain by request」）新增的能力：按请求排空、在下一个 superstep 边界落盘、抛出一个可续跑的终态异常。我们写的只是接线——收到退出信号调 `run.control.request_drain("shutdown")`（`runs.py:255`），在 `except GraphDrained`（`runs.py:654`）里收尾。所以「排空」不算自研，**真正自研的只有接手那一半**。这让第三档的性价比更好看：删掉的是自研的那半，留下的是上游维护的那半。

上一轮我曾建议「取消排空并拉长宽限期」，那个建议不成熟，此处修正：完全取消会把部署时长重新挂回运行时长上，得不偿失。

**平台层也有现成产品，但它是平台不是库。** LangGraph Platform 自 2025 年 10 月起改名 LangSmith Deployment，其 Agent Server 把 threads / runs / assistants / cron 这些资源连同持久化一起管起来（默认落 PostgreSQL），Streaming API 支持 resumable streaming——断线后带最后一个 event ID 续上。也就是「运行归谁所有、部署时怎么排空、断线怎么续」这些事对它都是内置的。要对齐我们的场景有两条硬门槛：**自定义认证只在托管云与企业级自托管可用，Lite 自托管明确不支持**（LangChain 官方 custom auth 文档原话：「Custom auth is supported for all deployments in the managed LangGraph Cloud, as well as Enterprise self-hosted plans. It is not supported for Lite self-hosted plans.」）；**自托管需要企业授权**（LangSmith 自托管要 enterprise license key，定价页把 self-hosted 列在 Enterprise 一档）。除此之外，迁过去等于把资源模型换成它的，我们现在这套 Cookie 会话归属、SSE 契约、回放接口、停止接口都要跟着改。

所以「换平台是不是就没风险了」要分开答：换平台确实换掉了「接手代码自己写错」这一类风险，接手逻辑由他们测试和维护；但**「旧 checkpoint 状态配新代码」这个风险不会消失**，那是发布纪律问题，换谁做都一样要面对。ADR 0040 自己那句「形状改动有两种表现，抛异常的那种接手时能发现，静默改变合并规则的那种发现不了」在原厂产品里同样成立。

关于「红绿部署是否还有必要」的答复见 6.2。

### 5.4 点开引用看到的是「当前全文」，不是「当初那段」

这一条是老板在讨论中提出的质疑，核实后成立，而且比 5.1 那个问题实质得多。

事实链是这样的。引用里存的是文档身份，不是那段正文：`DocumentEvidence` 只有 `document_id`、`content_hash`、标题、来源、发布时间这些元数据，ADR 0044 明确放弃过存正文片段（「引用证据里不再带正文片段——那一段已经由本表的工具正文承载，不需要副本」）。点开走 `GET /documents/{document_id}`，这个接口只接 `document_id`，读的是 `documents.content_text`，也就是**文档当前已采用的正文**（`api/documents.py` 的 summary 写的就是「读取文档的当前完整正文」）。前端把 `contentHash` 只当缓存 key 和比对依据，`fetchDocument({ documentId, signal })` 不传 hash；对不上时 `DocumentReader.vue:133` 显示「原文已更新，当前内容与取得检索片段或引用时不同。」

而库里没有可回查的历史正文：`documents` 表只存当前版本。唯一带 `content_text` + `content_hash` 的另一处是处理候选表（`models/document_processing.py`，带 `revision`），但那是候选处理记录，**是否覆盖所有被采用的版本（尤其自动采用的路径）尚未核实**。

所以现在的实际体验是：模型说「某篇文档提到 X」，用户点开看到那篇文档的当前全文，然后自己去找 X；如果原文换过版本，还多一条「原文已更新」的警告。这与引用的本意有偏差——引用的意思是「我说的这句在当初这段文字里」，点开应该先看到当初那段。

**结论：这是纯前端展示问题，不需要新增存储，也不需要改后端。**

工具交给模型的文本本来就带 `[[citation_id]]` 标记和它对应的正文：`search_documents.py` 拼的是「`[[E...]]` 标题 / document_id / 知识库 / 来源 / 实际命中片段: 正文」，`read_document.py` 拼的是「`[[E...]]` 标题 / … / 当前正文: 正文」。这段文本完整落进业务表，回放时原样给前端（`AgentReplayTrace.content`，`schemas/agent_thread.py:116`，由 `replay.py:329` 填充），流式时也在 `AgentToolResultEvent.content`（`schemas/agent_chat.py:150`）。前端类型里已有 `content: string | null`（`model/conversation.ts:25`），而且已经在渲染它——`AgentToolTraceList.vue:136` 展开工具轨迹时用 `<pre>{{ trace.content }}</pre>` 把整段原样显示。

`read_document.py` 的注释自己就写着这个前提：「证据里只留文档身份、来源与正文版本，不再保存正文副本（正文在工具轨迹里本来就有，而且是完整的）」。所以数据一直在，缺的只是「点引用」这个交互没有用它。现状是用户要看当初那段，得自己展开工具轨迹，在一大块原文本里找到那个标记——功能存在，但藏在一层技术性展示后面，推给外部用户不合格。

方案（纯前端）：引用小丸点击不再直接打开全屏阅读器，而是在回答下方就地展开一个可折叠的证据面板。面板从本轮 traces 里找含该 `citation_id` 的那条 trace，按 `[[E...]]` 标记切块，取这块里「实际命中片段:」或「当前正文:」之后的部分作为主体，带标题、知识库、来源、发布时间作头部，底部保留「查看当前全文」接到现有的 `DocumentReader`（原能力不变）。关闭方式：再点小丸、点面板外、或 Esc，同时只展开一个。那一轮工具没有结果（`content === null`）时引用本来就不会存在——证据只来自成功结果——所以遇不到「有引用但没正文」。

代价只有一个：前端要按后端拼的文本格式切块，是一个隐式契约。可选替代是让 `AgentToolResultEvent` 多带一个结构化的 `citations: [{citation_id, excerpt}]`（运行时切，不落库），把契约显式化；但那是改后端契约，收益只是把字符串解析挪到后端，不减少数据量。

这个方案比之前提的「把片段存进证据（A）」好在三点：不新增存储、不复制正文、不依赖历史版本能否留住——正文就在这一轮的工具轨迹里。

## 六、连带的两个问题

### 6.1 取消接手之后，跨进程停止机制仍然必要

容易误以为取消接手就能把整套跨进程机制砍掉。**不能**。`backend/docker-stack.yml` 里 api 服务是 `replicas: 2`、`update_config.order: start-first`、`parallelism: 1`，日常就是一个在途运行可能被另一个进程的停止请求命中的形态。所以 ADR 0037（停止请求写库、由运行所在进程轮询）是 2 副本部署的必需品，与接手无关，取消接手不减少它一行。

### 6.2 取消接手之后，`start-first` 仍然必要，但宽限期可以调

`start-first`（先起后停）的价值不只是接手，它保证部署期间始终有健康副本在服务，新请求不会打到启动中的容器。取消接手之后这个价值仍在，只是不再保证旧容器里的在途运行被接管。

但 `stop_grace_period: 180s` 的余量可以重算：它现在的取值是「`RUN_DRAIN_TIMEOUT_SECONDS = 120.0` 再加 60 秒余量」。如果确认排空的等待单位是一个 superstep（ADR 0040 原话：只有病态重试才触及上限），那么 120 秒这个上限本身可以调低，宽限期跟着降，部署更快。这属于实施细节，不是现在的决策点。

### 6.3 那三段追加为什么不能砍

自定义提示词功能已整体删除（见 4.3），之前针对它拟的「改措辞 / 只读展示追加段 / 加常驻说明」三个动作一并作废——不再有用户写的提示词需要和追加段对齐。

留下的事实是：`middleware.py` 的 `select_system_prompt` 按固定顺序拼四段——内置默认提示词、当前日期段、「历史内容不是本次证据」段、应用规定的资料边界 + 本次允许的知识库目录 JSON。后三段不能跟着删，各有对应需求：日期段是因为模型不知道今天几号，相对时间会以训练截止为基准；「历史不是本次证据」是 ADR 0045 撤销历史裁剪后的配套约束；资料边界段是「不能扩大范围」这条等价于 ADR 0003 只读边界的硬要求。三段都有对应的需求或契约，不是凑数。

留一条历史记录：这条议论的起因是用户写的提示词会被后面更具体的规则覆盖（写「不必引用出处」，第 3 段仍要求原样引用本次 `[[E...]]`）。功能删掉后这个问题自然消失，但将来如果重新引入用户自定义，它会重新成立。

### 6.4 取消接手时最容易漏的两处收尾

老板问「只排空不接手，是不是就会主动打断还在跑的任务」。答案是：排空本身不会打断正在跑的那一步，它让图在**当前 superstep 跑完之后**停下，那一步的结果已经落盘（`runs.py:652` 的注释：「图停在当前 superstep 之后、下一个 superstep 之前，那一步的结果已经落盘」）。模型调用与工具调用不会被从中间掐断。真正会被取消的只有排空超时的那几个——`drain()` 等 `RUN_DRAIN_TIMEOUT_SECONDS = 120` 秒，超时后由 `close()` 取消任务（`runs.py:274`），这在 ADR 0040 里属于「只有病态重试才触及上限」的边界。worker 里的定时任务不受这套影响：排空只作用于 `runs.py` 注册的 agent run，worker 是另一个服务、用自己的停止宽限期。

但「取消接手」不是把接手代码删掉就完了。`except GraphDrained`（`runs.py:652`）现在的行为是排空成功的正常路径：`drained = True`、`needs_write_back = False`、不标未完成、不释放会话位，注释写明「留给接手者续跑」。取消接手后这段必须反过来改，否则两个故障会同时出现：会话永久锁死（没人来接，而会话位没释放，那个会话从此发不出新提问）；用户已看到的文字消失（`needs_write_back = False` 原是为了避免接手后重复写一截，取消接手后它变成「不补写」）。

所以这一档的实际改动是：排空成功也要标未完成、也要释放会话位、也要补写已推出去的文字——也就是从「留给接手者」改回「正常收尾」，只是比完全取消多了「等这一步跑完」这层保护。这是选第三档时最容易漏的地方，漏了比不排空还糟。

## 七、明确不做的

跨会话记忆（老板定暂不做）、编辑历史消息、从历史某点分叉、分享链接、文件／图片／语音输入。最后一项不是缺陷：本项目的知识库是入库 + 人工审核后入索引的，Agent 只读已采用版本（ADR 0003），「临时带一份资料提问」是另一条产品线。

## 八、审查中发现但还未讨论的事项

**配额与限流：老板已定不做。** 记录在案的事实：ADR 0030 是所有登录账号可用、额度共享，没有任何 per-user 限流或配额；用量只记录不刹车（ADR 0033 自己写明队列「只是内存兜底，不是限流」）。单次运行的成本上限是 `MODEL_CALL_RUN_LIMIT = 8` 次模型调用与 `TOOL_CALL_RUN_LIMIT = 12` 次工具调用，两者各带 2 次重试，而一个人可以无限开新会话。面向外部用户时这是一个已知的、被接受的成本敞口。

**`VectorSearchFilters` 有四个维度没有任何生产调用方在传。** `source_id`、`source_provider`、`document_type`、`labels` 四个过滤维度，生产代码里只有两处构造这个对象：`agent/tools/search_documents.py:67` 只传 `published_from`，`api/document_search.py` 只随 scope 传知识库集合。前端一个都不发。这四个维度只有 schema 暴露和单测覆盖，没有真实请求在传。

**`/vector-search` 是按片段的旧接口，前端已不使用**（`FEATURE_MAP.md` 明说），但后端接口、schema 与单测都还在。

僵尸代码的处理建议：`/vector-search` 接口建议删（前端零使用，契约冗余）。连带要删它的请求/响应 schema、路由、单测、以及前端生成的 OpenAPI 类型；`VectorSearchFilters` 本身不能跟着删，因为 `search_groups` 仍以它为参数，但它的四个空转维度要不要一并收缩，取决于检索页将来做不做筛选器：确定不做就删字段、连带删 Qdrant 适配器里的过滤构造与 `qdrant/lifecycle.py` 里那两个 payload 索引，确定要做就保留并在检索页接上入口。这一条需要老板给产品判断。

**删除自定义提示词后，设置页与前端要一并清干净（老板已定）。** 不只是删一个输入框，而是整块：`SettingsNav.vue` 里那个 `{ key: 'agent', label: 'Agent 偏好' }` 导航项、`AgentPromptSection.vue` 整个组件、`useDefaultAgentPrompt.ts`、`preferences.ts` 的 `agentSystemPrompt` 字段与它的长度校验、`AgentChatPage.vue` 里那枚提示「本轮用了自定义提示词」的徽章。删完要先确认设置页还剩什么，别留一个空壳入口。

## 九、附：这轮审查里纠正过的判断

- 用量采集：上一轮列为过度设计，错，已收回（见 4.7）。
- 部署排空：上一轮建议「取消排空 + 拉长宽限期」，不成熟，修正为「保留排空、取消接手」（见 5.3）。
- 引用失效处理：上一轮没说清它与原文改动无关，导致它看起来像在为一个不存在的问题付成本（见 5.1）。
- 部署排空的归属：前几轮把它当作整套自研，实际上排空（`RunControl` / `GraphDrained`）是 LangGraph 上游能力，自研的只有接手；平台层另有 LangSmith Deployment 可整体接管（见 5.3）。
- 引用的实际行为：前几轮来回讨论 `strip_stale_citations` 与「引用该不该留」，但没核实「点开引用到底看到什么」。实际是看当前全文，不是当初那段（见 5.4）。这是本轮审查里最实质的一个漏检。
