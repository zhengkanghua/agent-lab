# LLM 调用用量记录

## 问题陈述

Agent 对话是全项目唯一真正烧钱的链路，但今天它的消耗**一行都没有入库**。一次运行结束时，token 合计
只写进一行日志，除此之外没有任何记录，也没有任何接口能把这份数据读出来。想问「这个月花了多少」
「哪个模型花得多」，只能去翻容器日志。

这份日志本身还不完整。它只从模型的流式增量里累加，而那个累加只认模型节点自己的产出，于是**历史摘要
压缩的调用一次都进不了合计**——长会话里最烧钱的那部分正好落在盲区。

老板给的边界很清楚：**这个需求只做「把每一次模型调用记下来」，并让本人能查自己的用量。** 金额、
额度、图表、后台超管视角、今日/本周卡片都不在本期范围内。「这个月花了多少」由一个接受时间范围的
汇总接口回答，界面自己算比例。

另一条明确约束：这块数据将来可能抽出去做独立的 LLMOps 平台，所以从第一天起就要能整块搬走，模块
本身不能和业务领域缠在一起。

## 解决方案

新增一个用量记录模块，只做一件事：把「一次模型调用消耗了多少 token」如实记下来，并让本人能查到。
它记录，不拦截——不设额度、不做限制、不算金额。

采集点放在模型客户端外面包一层，由 Agent 的运行时装配负责包住主模型与备用模型。**记账的判据只有
一个：这次调用有没有进到包装层**——也就是「把请求交给模型客户端」这个动作有没有发生。进来了就记
一条，它成功、失败、超时、还是被取消，都只是这条记录的字段不同；包装层没被碰到（模型客户端没构造
起来）就不记，那种情况没有过这次调用。

这条判据刻意不写成「上游有没有真的收到字节」：那在包装层判不出来，DNS 失败、连接被拒和「发出去
之后超时」在包装层是同一形状的异常。判据落在「这次调用进入了我们的记账点」上，这是包装层唯一能
确知、也唯一需要知道的事。

**只有这一个判据，没有例外。** 一次运行里可以有多次调用（每次工具调用之后都要再问一次模型），
重试的每次尝试也各算一次——它们各自都是独立的一次调用。这次调用被取消时（显式停止、上游失败、
进程关停，以及今天把运行挂在浏览器连接上时客户端断流也会触发取消），记账不能只写在正常返回之后：
它要落在「无论这次调用怎么结束都会经过」的位置，被取消的那次同样补一条——状态失败、token 为 0、
用量来源标为缺失、耗时算到取消那一刻。

数据落在**独立的 PostgreSQL 数据库**，与业务表不同库。将来抽成独立服务时整库直接 dump 迁移，业务表
一行都不用碰；抽取之后它也能只被授权这一个库。

模块只吃一个纯数据结构——UUID、数字和字符串枚举，不导入业务领域代码，也不用任何业务 ORM 模型。

写入先进进程内队列、批量落库；采集失败绝不影响对话，采集入口不抛异常、不阻塞调用方。

查询只有面向**当前账号**的只读接口：用量明细（分页）、用量汇总、模型名列表（给筛选栏取值）。明细
与汇总接受同一组可选筛选：时间范围、模型。

## 实现决策

**模块。** 新增一个独立的用量子包，内含契约、采集器、仓储、用量表模型与装配五个部分；**不导入**
Agent、知识库或任何业务 ORM 模型。包一层模型的包装类放在 Agent 侧（它依赖 LangChain），它只负责
构造契约并交给采集器，不碰数据库。

**采集点与装配。** 采集点在 Agent 运行时装配处，不在模型构造入口内部：注入假模型的路径也必须被
包住，否则端到端测试一条记录也不会有。**采集器通过一个可选的注入参数进入运行时装配，缺省是空实现
（什么都不记）**；生产由 API 进程的 lifespan 注入真实采集器，并负责它那个 Engine 的创建与释放，
读接口从同一处拿 session。这样现有的离线测试不传就是空实现，既不会因为缺配置而失败，也不会去连库，
而包装本身在两种情况下都发生。

**摘要压缩不需要额外装配。** 运行时把主模型实例同时交给摘要压缩用，它已经是包装实例，所以摘要调用
照样经过采集。**本期不区分调用来源**（不记录主模型／备用模型／摘要压缩这类标签），装配保持现状。

**包装类必须满足的行为。** 包装的存在只应当带来「多一条记录」，不应当改变任何其它可观察行为。

- **包在模型的公开调用方法外面，不重写内部的生成钩子。** 改写流式钩子会直接改掉行为：框架判断
  「这次要不要走流式」先看子类有没有覆写它们，不覆写就直接判定为不支持流式；而生产里真正让底层流式
  的是挂上去的流式回调处理器。包在公开方法外层就一个钩子都不碰，流式与否完全由底层模型自己决定。
  调用配置与其余参数要原样下传，但**不要自己改动它们**：往里塞一份空的 callbacks，或者传
  `stream=False`，都会真的把流式关掉。反过来，「漏传配置就不流式」这个说法在本仓库不成立——回调
  是框架放在运行上下文里交给底层的，模型节点调用模型时也不显式传 config，所以流式还在不在，不能靠
  断言「config 被转发过」来保证，要按下面「生产路径必须单独测」那条盯请求本身。
- **工具绑定必须真的到达底层模型，且绑定之后调用仍然经过包装。** 这两条同时成立，意味着不能简单地
  在绑定方法里返回自身（那会丢掉工具，模型不再调用检索工具，不报错），也不能返回底层的绑定结果
  （那会丢掉记账）。做法是拿底层产出的绑定重新挂到包装实例上，并容得下底层不接受绑定（测试假模型
  直接返回自己）的情形，那种情况下退回「不绑工具、仍由包装记账」。
- **显式逐项委托模型的可观测属性**：模型名、默认请求头、超时、温度、重试次数、能力画像、LangSmith
  参数，以及 provider 特有的构造参数。不使用兜底转发，漏一项要能被测试发现。
- **取消必须原样再抛**：记账在 `except BaseException` 里完成（取消抛的是 `CancelledError`，
  它是 `BaseException` 不是 `Exception`），记完无条件重新抛出；吞掉它会把「已停止」变成「继续跑」。

**记账点与取数。** 图里的模型节点是同步调用模型的公开方法，包装层拿到的是一条聚合好的消息，直接读
它的用量即可——没有「多份结果求和」这回事。包装还要覆盖模型的流式入口，否则外部调 `stream`／
`astream` 会撞上未实现的生成钩子；那一条不在本期的取数路径上，也不进验收。取运行身份（当前运行的
上下文）**可能失败**：这一步失败只把账号／会话／运行记成缺失，**不能**把这次调用判成失败；只有拿不到
用量才是「用量缺失」。**归属缺失必须留一条日志**：三个查询接口都按账号过滤，账号为空的记录谁都查
不到，不记就没有人知道账本正在少算。采集入口是同步、立即返回、不抛异常的，所以在取消路径上调用它
是安全的。

**运行身份传递。** 请求级上下文增加账号标识与会话标识两个字段（都有默认值，默认空表示归属未知），
由 Agent 对话入口构造时填当前账号与会话 id；运行标识沿用已有的运行 id。采集器在模型调用那一刻从
当前运行的上下文读这三个值；摘要压缩发生在中间件内部、不在模型节点，这条路同样拿得到。

**写入契约。** 契约是一个不可变数据结构，字段为：调用标识、账号标识、会话标识、运行标识、模型名、
输入／输出／缓存／合计 token、耗时毫秒、状态、用量来源、发生时刻。账号、会话与运行都以 UUID 形式
传入，**不传 ORM 对象**；标识符字段不用项目领域词汇，模块不知道「会话」「运行」是什么，只知道这是
几个不透明引用。

**调用标识。** 由采集器在受理每一条记录时生成一个 UUID，表上带唯一约束。它必须跨进程唯一：生产是
多个 API 进程，每个进程各有自己的队列，用序号或「每次构造算一次」都会撞唯一约束，而按写入失败的
处置方式是丢弃，结果是账本静默少数。它挡住的是「同一条记录被重复写入」（批量提交失败后的重试），
**不挡「同一次调用被重新受理」**——重放会拿到新 UUID、账本多一行，本期没有去重机制，也不承诺这一条。

**用量来源取值**：上游自报、缺失。判定就是「拿到没拿到用量对象」——拿到就是自报（哪怕报回来的总量
都是 0），没拿到就是缺失。**状态取值**：完成、失败；失败包含上游报错、超时、被取消。

**发生时刻与耗时。** 发生时刻取调用进入包装层的 UTC 时刻；耗时取进入包装层到结束之间的单调时钟
差值，中途被取消时算到取消那一刻。

**token 口径。** 输入、输出、合计三个数原样记录上游报的值，合计以上游报的合计为准、上游没报时用
输入加输出补齐。输入 token **已经包含**缓存命中的部分，所以三者不能相加当成消耗。缓存数在用量对象
的输入明细里，键名以 `cache_read` 结尾（不同服务档位会带前缀），取值要按后缀匹配、不能写死；上游
没报缓存时这一列**记缺失，不记 0**——否则「没报缓存」与「报了 0 缓存」会混在一起，正好是这份 spec
要区分的那件事。

**写入。** 采集入口立即返回、从不向调用方抛异常。内部是进程内队列加批量落库：后台按刷写间隔把队列
里最多一批记录写出去，队列为空时直接返回、不做任何数据库访问。队列有界，满了丢弃新记录并记一条
日志；写入持续失败也记一条日志。**不做累计计数与账目守恒**——本期只要求
「不把故障传回对话」和「丢了能在日志里看见」。进程关停时尽力把队列刷完，刷不掉的部分记一条日志，
不阻塞关停超过一次刷写间隔；进程被强杀或机器掉电时队列整体消失，这是有界队列方案的已知代价。
写入失败不重新入队：卡死时重新入队会让内存持续增长，把「数据库慢」放大成「进程 OOM」。

默认参数（住在代码常量里、可调）：队列容量 10000 条；批量上限 100 条；刷写间隔 1 秒；提交失败后
重试 1 次，仍失败则丢弃该批。

**独立 Session。** 采集器自己持有绑定用量库的 session 工厂，每次刷写开一个短 session、写完提交、
立即关闭。不复用业务库的请求级依赖：它绑的是业务库；长连接的流式请求生命周期很长，会占着连接；
而且请求结束时那个 session 已经关闭，刷写时拿不到。连接串用异步驱动，刷写不做阻塞调用。

**用量库 Engine 的两个使用者。** 写入的消费者任务（每次刷写借一个连接、毫秒级归还）和读用量的
HTTP 接口（每个并发请求借一个）；连接池大小按并发查询数定。这个 Engine 只由 API 进程持有：Agent
对话只在 API 进程跑，Worker 与 CLI 不调用生成式模型。跟着这条边界的一个当前事实：**Worker 侧不
记账**，将来若有定时任务开始调生成式模型，那条链路上的调用不会被记录。

**表结构。** 只追加，不修改、不删除；自增主键 + 写入契约里的全部字段。时刻列带时区，写入的就是
UTC 瞬时，用量库的会话时区也钉成 UTC——不这样做的话，写入与查询两边在代码里看起来都用了 UTC，
筛「某一天」的结果会整体偏几小时。索引两条：`(账号标识, 发生时刻)` 覆盖不带模型筛选的明细与汇总；
`(账号标识, 模型名, 发生时刻)` 覆盖带模型筛选的明细／汇总，也覆盖模型名列表要的「本账号下有哪些
模型」。运行标识不建索引：本期没有按它筛选的接口，建了就是白付写入代价；列仍然保留，因为「这条账
属于哪次提问」是记账时天然就有的事实，事后补不回来。

**迁移独立。** 用量库单独一套迁移环境（独立的 ini、env 与版本目录），与业务库各自独立的迁移链；
用量表的 ORM 模型挂在自己的元数据上，**不能**被业务侧的迁移环境看到，否则自动比对会在业务库里建
这张表或把它当成多余表删掉。不使用 Alembic 官方的多库模板：它的分派依赖模板生成的函数签名，而现有
全部历史迁移的签名是普通 `upgrade()`，运行时会直接报错，不是静默跳过。

**配置。** 新增用量库的连接配置，沿用仓库里「每个外部依赖一个配置类」的写法。两条处置的边界要
划清：**配置缺失或不合法 → 启动失败**（这种错改了配置就能好，静默降级只会让「用量统计悄悄没在工作」
难以发现）；**配置没问题但运行期连不上库（或表还没建）→ 降级为空实现 + 记日志**（这正是「一个次要
库的故障不升级成主要功能不可用」）。这个配置只在 API 进程装配采集器时读取：Worker 与 CLI 不走这条
路径，也不会因为共用同一份环境文件而被要求这个连接串。**校验必须落在「失败会让进程起不来」的那
一层**：`main.py` 的 lifespan 里搜索与任务运行时在外层 try、Agent 装配在内层且异常被兜住（只让
`/agent/*` 返 503），把读取点放进内层就会得到与第一条相反的静默降级。

**HTTP 接口。** 三个面向当前账号的只读接口：用量明细（分页）、用量汇总、模型名列表（给筛选取值，
不做其他聚合）。明细与汇总接受同一组可选筛选：时间范围（UTC 起止时刻，闭开区间）、模型。**凡是
列表支持的筛选维度，汇总接口必须一并接受**，不允许出现「列表认这个参数、汇总悄悄忽略」的缝隙。
用量库不可用时的处置与写入侧相反：**这三个接口返回稳定的 503，不返回空列表、不返回零汇总**——把
「查不到」渲染成 0，正是 token 口径那一节反复拒绝的事（迁移没跑、库被摘掉都会变成「这个月没花钱」）；
写法与 `api/agent_threads.py` 对数据库故障的处置一致。

汇总返回固定形状的聚合：输入、输出、缓存、合计四个 token 各自的总和，加上调用次数（就是明细的
行数）。验收口径是「四个字段逐列相加等于同一筛选条件下列表里全部记录的对应列之和」；缓存那列只
累加有值的行，缺失不是 0，两者不混。

明细返回 `{items, has_more}`（与仓库现有列表接口一致，用 limit+1 探测），**不带 total**：账本表
持续增长，精确 COUNT 是白付的代价，而用户不需要精确总数；需要计数时放在汇总接口里。分页单位是
一条调用记录，排序为发生时刻倒序、主键倒序——同一账号的多个会话并发写入时会落在同一毫秒（一次
运行内的多次调用是串行的，不会），只按时刻排序会让同一行在两页里重复、另一行被跳过。分页方式就是
偏移量分页（跟仓库现有列表一致），它的已知取舍是翻页期间新写入的记录会把整页往后顶，可能让某一条
在两页里重复、另一条被跳过——**这条漂移本期不处理，验收时不当作缺陷**。

时间范围以 UTC 时刻传入，时区换算只发生在前端展示层。本期不做「今日」「本周」这类预置口径。

**前端。** 设置中心新增一个分区：汇总数字 + 明细列表 + 时间范围与模型筛选。第一版不做图表，不做
后台页面。后端契约新增后要按仓库既有命令重新生成前端类型（那是生成物，不手改）。

**删账号不删用量。** 删账号的 Service 不改动用量库。用量记录是不可变事实账本，不是账号的附属数据；
无论账号是硬删还是按账号注销那份 spec 改成软删除，结论都一样——本期不做后台页面、不显示邮箱，
所以也不依赖账号行是否还在。

**部署与文档交付。** 服务器侧要多一步创建用量库、并跑它那套迁移，落点写进部署手册与部署工作流的
迁移步骤；环境变量模板要补上用量库各项（本地那份环境文件不能当模板）；镜像构建必须把新的迁移
环境一并打进去，否则部署时要么找不到文件、要么空跑导致用量表根本没建；能力地图加一行用量查询；
后端 README 补配置项与命令。

## 测试决策

好测试只验证可观察行为，不锁实现细节。测试接缝按「从高到低」排，**每层证明什么必须说清**。

**内存 SQLite 层（每次回归都跑）。** 采集器与包装类、查询接口都在这一层，用假仓储、假模型或内存库，
不连真 PostgreSQL；装配先例是仓库里任务系统那套用内存 SQLite 复制表的辅助模块。这一层证明的是
**记账逻辑与失败处理**：入队、批量落库、写入失败不向调用方抛异常、库不可用时降级、工具绑定仍然
到达底层模型（含假模型不接受绑定的情形）、取运行身份失败时归入「归属未知」并留下日志，而不把成功
调用记成失败、三种结束方式各留记录（正常、抛异常、取消）、取消时包装仍然抛出而不吞掉、上游报了 0
与上游什么都没报可区分、缓存缺失不被记成 0、接口的分页与筛选、权限（只能查到自己的记录）、空列表是
正常响应、用量库故障时查询接口返回 503 而不是空结果、同一筛选下汇总四列与次数等于列表相加。包装的
可观测属性单独一条：把真实客户端包起来，逐项断言属性与未包装时一致——**注意不能指望现有的构造测试**，
它只调模型构造入口，根本不经过包装，而漏委托带默认值的属性不会报错，只会静默给出空值。

**端到端接缝（集成，最关键）。** 在真实 LangGraph 图里跑够轮次逼出摘要压缩，验证摘要调用也被记录、
主调用也被记录、所有记录带同一个运行标识。这是唯一能证明「摘要压缩调用真的被记账」的测试，而那正是
本次要修的核心缺口。它用内存 SQLite 上的真实用量表与真实采集器，走完真实的入队→落库→查询链路；
落点是内存 SQLite，因此它证明的是记账逻辑，不是真库行为。这条测试离线可跑，不需要登记集成测试
开关——那份白名单是给真 PostgreSQL/Qdrant 的用例用的。

**生产路径必须单独测。** 上面那条端到端测试历史上的盲区是：它用图的同步调用跑，而生产用的是流式
调用入口。两者的差别不在模型节点的调用方式（那条永远是同步调用公开方法），而在有没有挂上消息模式的
回调处理器：挂了，底层模型就走流式 HTTP，请求里才会带请求用量的开关；不挂就是非流式。于是「用量
恒为 0」的缺陷在测试全绿的情况下存在过。所以另有一条**走生产入口**的用例盯着请求里是否带那个开关。
它的接缝要说清：**不能靠注入假模型**——那会直接替掉模型构造入口、被测的那行开关根本没跑到，用例
会绿得毫无意义；正确做法是在 HTTP 传输层造假上游，让真实客户端被构造出来并发出请求，再断言请求体。
这条断言只对 OpenAI 兼容分支成立：Ollama 分支没有这个参数，它的用量来自响应里的提示与生成计数。

**真 PostgreSQL 层（需显式授权，默认跳过）。** 守的是内存库证明不了的那些：记录真的落进独立库、
索引齐全、唯一约束成立、时刻列带时区且按 UTC 解释、业务库的迁移链不会碰用量表。这个新测试要
登记进仓库的集成测试开关表，并用一个独立的连接串变量指向用量测试库——复用业务库那个变量是不行的，
用量在另一个库。**运行规矩**：
首次交付前跑一次；之后改动碰到用量库相关的东西（表结构与迁移、采集器的落库路径）时重跑；其它需求
的回归不必跑——与仓库「已经通过的检查不重复执行」一致。这条规矩要写进交付说明的检查项，否则
「默认跳过 + CI 不跑测试」等于这些声明永远没人验。

**不改动的测试。** 现有结束日志里 token 合计的严格相等断言保持原样——运行时的日志合计与数据库记录
职责不同，前者保持现状只报三项。

## 超出范围

- **金额与成本核算、额度限制与预警。** 只记 token 数，不算钱、不拦截。
- **后台超管视角。** 不做「全部账号」页面、不按账号筛选、不显示邮箱，因此也不做跨库邮箱拼装。
- **按运行筛选与按运行分组的视图。** 运行标识只记进账本，不提供按它查询的入口。
- **今日／本周卡片与预置时间口径。** 时间范围由调用方传入。
- **图表与趋势分析。**
- **队列溢出与写入失败的精确计数、账目守恒等式、关停排空的分档参数。**
- **Embedding 用量的统计。** 检索与索引链路不调生成式模型，本期不纳入，也不改动 Embedding 提供方
  的响应解析。
- **用量的自动清理与归档、运行级汇总表与物化视图、独立的分页总数。**
- **本地 tokenizer 估算、按月分区、多供应商适配层。**
- **抽取独立 LLMOps 服务本身。** 本期只保证数据与模块可搬走，不真的搬。

## 补充说明

**一个已探明的框架行为要记住。** OpenAI 兼容客户端在自建 `base_url`（本项目的中转站就是）下不会
自动请求用量，于是流式请求里不带「回传用量」的开关；而 Agent 的生产入口本来就是流式调用，按官方
契约上游此时不会回用量、用量会静默记成 0。本项目的中转站实测宽容（流式也回用量），所以当时恰好有
数——但那是上游行为，不是保证。因此构造客户端时对 OpenAI 兼容分支显式打开这个开关，把「请求用量」
变成本项目的主动契约；Ollama 分支不设这个参数（它没有这个概念，用量来自响应里的计数）。

**摘要调用为什么漏，成因要说准。** 它不是因为框架把中间件内部的调用从流里删掉——实测：在真实
摘要中间件加 checkpointer 的图上，摘要的增量确实出现在消息流里，节点名就是那个中间件。真正把它挡在
合计之外的是本项目那段只认模型节点的累加判断。这个区别不是措辞问题：照前者排查会去找框架的流转换器，
而问题在自己那行过滤里。相关的 ADR 目前写的是前者，需要按这条复核；而它关于「采集点必须在包装层」
的结论本期仍然成立——那是唯一能覆盖中间件内部调用的位置。

**一条依赖。** 取消从哪来由另一份 spec 决定（Agent 运行脱离浏览器连接）。它落地后，客户端断开只
减少订阅者、不再取消运行，于是「被取消的调用」只剩显式停止、上游失败与进程关停；在此之前，断流
仍会在取消路径上留下一条。两种世界下采集器的行为不变（同一条取消分支），变的只是那条记录的来源
频率——所以本 spec 不必等它，但施工到那块时要知道它。顺序是：本 spec → Agent 运行脱离浏览器连接。

**文档待办（受仓库门禁约束，不在本 spec 的交付范围内）。** 采集点那条 ADR（0031）里关于摘要漏记
的成因与「来源标签」的结论都要按本期复核（来源标签本期不记）；模块解耦那条 ADR（0033）里关于
队列容量定标的说法要跟着本期的「不做精确计数与守恒」一起复核。术语表新增或复核三个词条：模型调用、
用量、用量记录；「LLMOps」不收录——它是这个模块将来独立部署后的平台形态，不是本项目当前的概念。
这几处只能在专门的访谈流程里改。

（本 spec 只写已经定稿的决策，不随施工进度改动）。交付时随本 spec 一并删除。
