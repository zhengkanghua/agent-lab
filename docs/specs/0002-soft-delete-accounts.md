# 账号注销：硬删除改为软删除

## 问题陈述

超级用户在后台删除一个账号时，`users` 表里那一行会真的消失。这件事本身没错，但它的连带后果没人
算过账：账号一没，邮箱就查不到了，而用量统计那边的记录还留着——那些记录的账号标识从此指向一个
不存在的账号，页面上只能显示「账号已删除」。更要紧的是，Agent 会话归属、个人偏好这些跟着账号走
的东西会**一起**被清掉，而它们不是「账号的一部分」，是这个人在系统里留下的记录。

老板的判断是：用户体系的依赖太多，账号不该硬删除。生产上的通行做法也是保留。删除对使用者来说
就是「注销」——这个账号我不再用了，但它做过的事不该跟着消失。

这里还有一个必须先说清的现实：`is_active` 这个字段是 fastapi-users 框架自带的，框架在登录与认证
两处直接读它。所以它不能删、不能改名。它能表达的就是「这个账号能不能用」——也就是「停用」。
都靠它。

## 解决方案

给账号加一个**独立的注销时间字段**，删除动作从「删掉那一行」改成「给它盖上注销时间」。账号行、
会话归属、个人偏好全部保留；只把登录 Token 删掉，让注销的人立刻进不来。

注销与「能不能用」是两件独立的事，所以用两个字段分开表达：`is_active`（框架原有，管能不能用）
和 `deleted_at`（新增，管这个人还在不在）。三个状态由这两个字段组合出来：活跃 = `is_active=true`；
停用 = `is_active=false`；注销 = `deleted_at` 有值（此时 `is_active` 也是 false，否则登录门挡不住）。

`is_active` 保持它原来的样子——真列、布尔、框架读得到、代码可以赋值。这样不动框架要求的东西，
也不用删掉约束里对 `is_active` 的引用（那是被否掉的方案才需要的动作）；本次要动的是**给它所在的
环境托管那条约束补一个条件**，并**新增一条配对约束**，见「实现决策」。

## 用户故事

1. 作为超级用户，我想要注销一个账号时它不再从数据库里消失，以便它留下过的记录还有主可查。
2. 作为超级用户，我想要注销的账号仍然能被查到是谁（邮箱还在），以便用量统计里那些记录能显示
   具体的人而不是一句「账号已删除」。
3. 作为超级用户，我想要注销一个账号后他立刻登录不进来，以便注销不是只改了个显示。
4. 作为超级用户，我想要在账号列表里默认看不到已注销的账号，另有一个开关才显示出来，
   以便日常管理不被这些行干扰。
5. 作为超级用户，我想要已注销的账号显示成「已注销」并带上注销时间，以便和正常账号一眼区分。
6. 作为超级用户，我想要已注销的账号不能再被停用或改密码，以便不会对着一个已经注销的账号做
   无效操作。
7. 作为超级用户，我想要确认注销后这个人的密码也不能再用了，以便离职的人不会因为密码没改而回来。
8. 作为超级用户，我想要注销时保留这个人的会话归属与个人偏好，以便「他做过什么」这些记录还在。
9. 作为超级用户，我想要注销后决策记录里的操作者标识仍在，以便这段事实不被改写（查询入口见
   「超出范围」）。
10. 作为超级用户，我想要停用和注销是两件事，以便停用的人可以被重新启用、注销的人不能。
11. 作为超级用户，我想要不能停用或注销最后一个活跃超管，以便不会把管理入口锁死。
12. 作为超级用户，我想要不能停用或注销环境托管账号，以便部署配置里的那个恢复通道始终有效。
13. 作为超级用户，我想要不能停用或注销自己，以便不会在操作中途失去权限（**后端规则**，不靠
    前端按钮拦）。
14. 作为运维者，我想要环境托管账号被注销时服务启动直接失败并说明原因，以便不会静默把它复活
    成一个能登录的超管。
15. 作为运维者，我想要数据库层也拦得住「环境托管账号处于注销状态」这种数据，以便业务代码漏写
    时不会留下一个坏掉的数据。
16. 作为运维者，我想要数据库层也拦得住「已注销却还能登录」这种数据，以便不会出现一个看起来
    注销了、实际还能进来的账号。
17. 作为运维者，我想要迁移只改结构、不删数据，以便一次部署推送不会清掉别人环境里的账号。
18. 作为开发者，我想要注销是幂等的，以便重复注销同一个账号不会报错也不会改坏数据。
19. 作为开发者，我想要账号是否可用只有一个判据，以便不会出现「登录放行了、别的入口拦着」这种
    两处结论不一致。
20. 作为开发者，我想要给已注销账号改密码这类请求返回明确的领域错误，以便调用方分得清
    「账号不存在」和「账号已注销」。
21. 作为开发者，我想要邮箱唯一性保持不变，以便已注销账号的邮箱不会被别人占用后造成历史记录混淆。
22. 作为开发者，我想要「已注销账号上哪些动作允许、哪些拒绝」一次写清，以便实现与测试不会
    各挑一边、两条验收用例正面冲突。
23. 作为超级用户，我想要一个账号的超管身份在建号时就定下来、之后不能改，以便管理权只有「建号
    时给」与「注销时收」两个口子，不会出现「悄悄降权」这种中间状态。

## 实现决策

**两个字段，各管一件事。** `is_active`（Boolean，框架原有、保留原状）管「这个账号能不能用」；
`deleted_at`（带时区的时刻，可空，新增）管「这个人还在不在」。这条取舍的来龙去脉见 ADR 0034。
一个账号在任一时刻处于三种情形之一：

| 情形 | `is_active` | `deleted_at` | 能否登录 | 可逆 |
| --- | --- | --- | --- | --- |
| 活跃 | true | null | 能 | — |
| 停用 | false | null | 不能 | 可重新启用 |
| 注销 | false | 有值 | 不能 | 第一版不可恢复 |

**列的类型按仓库惯例是带时区的时刻。** 别写成不带时区的日期时间——本仓库所有时刻列都带时区、
连接会话固定为 UTC，而一条不带时区的列不会被任何测试抓到，却会让注销时间在展示与比较上与全库
其余时刻列不一致。

**为什么用时间戳而不是布尔。** `deleted_at` 记下注销发生的时刻，前台能显示注销时间，将来若做
保留期清理也有起点。布尔 `is_deleted` 拿不到这些。

**注销时两个字段一起写。** 只写 `deleted_at` 而不置 `is_active=false` 是不行的：登录与认证两条路
都只看 `is_active`，那样注销等于没做。注销的具体动作是：`is_active` 置 false、`deleted_at` 置当前
时刻、`is_superuser` **保留**（不改角色，将来若做恢复，恢复出来权限是对的）。

**注销的连带处理变了。** 现在是硬删除，同一事务里做四件事；改成注销后：

| 表 | 原来 | 现在 |
| --- | --- | --- |
| `agent_threads`（会话归属） | 删掉 | **保留** |
| `user_preferences`（个人偏好） | 删掉 | **保留** |
| `access_tokens`（登录 Token） | 删掉 | **删掉**（注销的人不该再有活着的会话） |
| `document_review_records.actor_id`（换版决策留痕） | 置空 | **保留**，但这只是不改写事实，**不是提供查询入口** |

保留最后一项的理由要写清，它很容易被误读：项目里**没有任何接口或界面把 `actor_id` 变回一个人**
（审阅决策的对外契约只暴露这个标识本身，前端审阅功能完全不引用它）。所以保留它并不会让「是谁拍
的板」变得可查，它的价值是**不把已发生的事实改写成另一个样子**——置空会让一条人工决策看起来像
自动决策（那一列的注释就是「人工拍板的操作者；自动决策为空」）。要不要做查询入口见「超出范围」。

**注销的唯一路径。** 账号管理 Service 的删除方法是唯一入口，只是行为从「删行」变成「盖时间戳 +
删 Token」。方法名与接口路径都不改（前端点「删除账号」看到的仍是删除，只是语义与文案改成注销）。
它不再删会话归属与偏好，因此**那个只为「删账号时清偏好」而写的方法、以及它那条单元测试，要一并
删掉**——它的文档注释逐字写着「供删账号时在同一事务里调用」，留着就是假话，而它已经没有别的生产
调用者。

**已注销账号上的动作分两类，这是一条不变量：注销本身幂等成功，其余写动作一律拒绝。**

- **幂等成功**：对已注销账号再调一次注销——返回成功，不改已有 `deleted_at`，不重复处理；
  撤销会话仍可执行（它删 Token 是实际动作，第二次删 0 行，所以幂等，但**不是「无副作用」**）。
- **一律拒绝**：停用/启用、重置密码——返回领域错误，**不是**「账号不存在」。

两类各自的理由不同：注销是同一个目标状态，重复到达它是成功；而停用/改密对一个已经注销的账号
没有意义——它不能再登录了，改它的密码改的是什么？返回错误比静默成功更诚实。

新增两个领域错误码 `account_already_deleted`（对已注销账号做写动作）与 `account_self_protected`
（停用或注销自己），都映射成 409，与现有那两个保护类错误码同一形状。

**超级用户身份只在建号时决定，之后不能改。** 这是本次明确的行为调整：**取消「降权」这个动作**。
要收走某人的管理权，只有注销那个账号一条路：不能把超管改成普通账号，也不能把普通账号提升为
超管。理由与取舍见 ADR 0038——管理权只有「建号时给」与「注销时收」两个口子，谁有权限就只由
建号记录决定。

连带三件事：

- 改状态接口**只剩「停用/启用」一个动作**，不再接受超管标记；建号接口仍可指定超管身份，那是唯一
  的授予口子。
- **「不能降最后一个活跃超管」那条保护作废**，因为降权这个动作不存在了；但「**不能停用或注销**
  最后一个活跃超管」仍要保留——停用与注销都会让一个人退出活跃超管。
- 前端列表里那个「超级用户」开关删掉；建号表单里那个勾选保留。

**「不能停用或注销自己」是后端规则。** 客户端不可信，前端那句「是自己就返回」只是体验，不是边界。
所以停用与注销这两个动作都要知道**调用者是谁**，而现在的写接口只把目标账号传进来、没有把调用者
传进来（路由上的超级用户依赖只做鉴权，不把身份交给处理函数）。

因此这两个接口要新增一个调用者身份依赖（复用现有的超级用户依赖），把当前账号 id 传进 Service；
Service 在写之前先比：**目标就是调用者本人、且这次动作是停用或注销**，就抛 `account_self_protected`，
映射 409。**不靠前端拦**——直接打接口也必须被拒。（「降权自己」不在这个规则里——降权这个动作
本身已经取消，见上。）

注意这一条**改变了现有行为**：现在「停用自己」是被有意允许的，前端还专门实现了「把自己停用或
降级之后重新取会话、跳转」那一套处理。新规则把停用自己拒掉、而降权整个取消，所以**那套处理逻辑
与它配套的用例要一并删掉**；同时自己那一行的停用/启用与注销在界面上也不提供。这条要写出来，
否则后人会以为漏改了。

**账号是否可用只有一个判据。** 所有「能不能用」的判断都走 `is_active`（框架也是这么读的），
不新增第二个判据。所有「还在不在」的判断走 `deleted_at`。两条判据不混用。

**活跃超管的判据。** 保护规则里「活跃超管」的含义是「`is_active` 且 `is_superuser` 且未注销」。
停用与注销两条路径都要数这个，抽成账号管理 Service 的一个私有方法共用，避免将来改判据漏掉一处。
**不新建抽象模块**——连带清理与保护逻辑留在各聚合自己的 Service 里。

**邮箱唯一性不变。** 邮箱上的唯一索引一个字不改：已注销账号的行还在、邮箱仍占着索引，所以同一个
邮箱不能建第二个账号。这是老板明确的选择（先这样）。**代价要落在文案上**：超管会遇到「列表里查
不到这个人、建号却说过邮箱被占用」的情况。

文案不需要知道占用者是不是已注销——**建号判重靠唯一索引抛出的完整性冲突，异常里没有这个信息**，
而那段代码注释明确写了「不先查询再插入」（并发下那种查法必然漏）。所以文案写成一个不需要额外
查询的事实陈述：**「该邮箱已被使用（可能是已注销的账号），不能重复建号。」**不在冲突之后补只读
查询、也不改判重方式。

**数据层也拦一道（两条约束）。** 一是**环境托管那条约束**加上「未注销」条件，变成「环境托管账号
必须是活跃、未注销、超管、已确认」；二是**新增一条配对约束**，禁止「已注销却仍可登录」这**唯一
一种**字段组合：

```sql
CHECK (NOT (deleted_at IS NOT NULL AND is_active))
```

第二条的值在于它不拦任何正常写入——实测（同一批 CHECK 共存）五个正常写入点全部通过：启动同步
建号、CLI/接口建号、停用、停用后又改回活跃、注销；只有「把已注销账号的 `is_active` 改回 true」
会被拒。而它防的正是那条**静默的越权登录**：`is_active` 有多个写者（启动同步的建号与拉回活跃、
两类建号、改状态），任何一个漏掉配对，表现都是「列表显示已注销、这个人照常登录」而没有任何报错。

数据库这两条只做兜底，业务层的检查仍要保留——先给出清楚的原因，而不是一个数据库错误。

**启动同步遇到已注销的环境托管账号时报错拒绝启动。** 启动时会把配置里那个邮箱对应的账号强制拉回
「活跃的超管」，这是恢复通道的本意（超管全被锁在门外时改配置重启就能拿回入口）。但如果库里那个
账号已经被注销，这个动作就是**把一个已注销的人复活**。所以同步时先检查 `deleted_at`：有值就抛错、
拒绝启动，并说明「配置里的邮箱对应一个已注销账号，需要人工处理」。不静默复活，也不静默跳过——
两者都会让人在不知情的情况下失去（或拿回）管理入口。

**迁移只改结构。** 一次迁移做四件事：加 `deleted_at` 列（可空，带时区）、改写环境托管那条 CHECK、
新增配对那条 CHECK、把存量账号按现在的 `is_active` 原样保留（`deleted_at` 全为 null——现在库里
没有「已注销」的账号，因为以前注销就是真删）。**不删任何数据、不删任何列。** 部署流程会自动执行
迁移升级，所以迁移里不能有清数据的动作。

迁移要有 `downgrade()`（本仓库每个迁移都有）：删列、还原环境托管那条 CHECK 的旧文本、删掉配对
那条 CHECK、**不动数据**。结构回滚不替业务决定数据去留。

**模型侧有两处必须跟着改，否则会静止漂移：**

- **新列要带中文注释**——有一条离线用例断言账号表每一列都有注释，不加直接红。
- **模型里那条约束的文本要改成与迁移同一句**（两条约束都是）。它是**独立的一份**，而全仓库没有
  任何测试比对模型元数据与库上的约束；不同步的话，凡是用模型元数据直接建库的真库用例得到的都是
  「不拦已注销环境托管账号、也不拦配对违例」的库，与「数据层也拦一道」的目标不一致且不会有人
  发现。

**不新增真删账号的命令。** 开发环境要清空账号时，走两条现成的路：逐个走业务注销（软删除），或者
直接重建数据库（drop 后重新迁移、启动同步会重建环境托管超管）。后者是运维动作，不是本 spec 的
代码。

理由：新增一条能真删账号行的命令，会在库里造出**第二条硬删除路径**，而根仓库常驻指令的业务与
数据约束与 ADR 0028 都把「删账号路径唯一可测」写成了约定；而且它必然撞上 `actor_id` 那个两难
——注销之所以保留它是「账号行还在」，真删之后保留就造出孤儿标识，置空又把人工决策伪装成自动
决策。为了一个开发便利引入这个两难不值得；真删的需求由重建库满足。

**HTTP 契约。** 删除接口的路径与 204 状态码不变，只改语义、接口描述与前端文案（从「删除」改为
「注销」）。改状态接口**只剩「停用/启用」一个动作**（不再接受超管标记）；建号接口仍可指定超管
身份，那是唯一的授予口子。见「超级用户身份只在建号时决定」。

账号列表接口新增一个查询参数表达「带上已注销的」（默认关，与服务层的同名参数对应）——**不把参数
写进契约，前端那个开关就没有可调的东西**。列表响应项新增 `deleted_at`（可空），`is_active` 保持
原样。两处响应模型里 `is_active` 的语义描述一起收窄为「是否可用」，与 `deleted_at` 一起读才能判出
三种情形。

删除与改状态两个接口都要新增调用者身份（见「不能停用或注销自己是后端规则」一节）。前端提交的
**静态客户端是从后端契约生成的产物，改了后端接口描述就要重新生成并提交**——仓库里没有任何检查
比对这两份，不重新生成就会一直留着旧文案（现在里面那句仍是「置空换版决策留痕的操作者」）。

**列表与查询口径。** 账号列表默认只返回未注销账号，另加一个参数才带上已注销的。所有写操作的
第一步那个「取出并锁定目标账号」的方法**不过滤**，它必须能查到已注销账号，才能对「给已注销账号
改密码」返回正确的领域错误而不是「账号不存在」。

**登录失败文案不变。** 停用与注销都返回同一句通用错误（上游的「凭据不正确」），不区分原因——
区分会让攻击者拿「这个邮箱存在但被停用了」这种信息。

**前端。** 后台账号列表加「显示已注销」开关（默认关）。已注销的行显示「已注销」标记与注销时间，
且不提供停用/启用、注销、重置密码按钮。自己那一行同样不提供停用/启用与注销。列表里那个
「超级用户」开关**整个删掉**（授予只在建号时做）。删除确认弹窗的文案从「该账号的会话与登录状态
会一并清除，且无法恢复」改为说明注销的含义（数据保留、不能登录）。**同时删掉为「停用/降级自己」
写的那套后续处理**（重新取会话、跳转）——它服务的两个动作一个已被禁、一个已取消。

这一节有三件容易被当成「只是界面」而漏掉的事：

- **新错误码要进前端那张「错误码 → 文案」表**（那张表自己的注释就写着「新增码时两边一起改，
  漏了这边只会退到兜底文案」）。不落表的话，超管对已注销账号点停用/改密、或者碰到自己那行，
  看到的会是「请稍后重试」——对一个永远不会成功、且原因很明确的动作给出「稍后重试」的指引。
  **那张表里现有一条「不能停用、降级或删除最后一个启用的超级用户」的文案也要去掉「降级」**。
- **查询键要带上那个开关，注销成功后不能把行从缓存里摘掉。** 现在列表的查询键不带参数、缓存有
  十秒新鲜期，而创建/更新/删除三处都直接改同一个键。开关若照直加而不改键，点一下不会发请求
  （数据还新鲜），表现是「开关像坏了、列表没变」；而删除成功后那段「把这一行从列表里滤掉」的
  逻辑会把行移除，开关开着时「行还在、只是已注销」就不成立。那三处缓存写入也要跟着多键一起改。
- **概况条的数字口径要说清。** 现在「超级用户」是按 `is_superuser` 数，而注销后 `is_superuser`
  **保留**（见上），所以开关打开时会把一个登不进来的账号计进超管数，三个数字口径不自洽。
  口径定为：**「超级用户」只数未注销的**（与「启用」一致）；「全部账号」是否含已注销的随开关走。

**不改动的地方（重要）。** `is_active` 这个名字在别处也有，但清单比直觉短，实测结果是：

| 位置 | 字段 | 与本次有关吗 |
| --- | --- | --- |
| 知识库 | `is_active` | **同名不同义**，本次不动 |
| 定时任务 | `enabled`（不叫 `is_active`） | 无关 |
| 来源 | 没有启停字段 | 无关 |
| 登录者自述与后台账号响应 | `is_active` | **本次要改的**，但语义要写清（见上） |

本次只碰账号表与账号相关代码。**尤其不要把知识库的 `is_active` 一起改**（前端知识库目录、知识库
组合式函数、文件资料列表里那些都是知识库的）。另外那两处响应模型里的 `is_active` 是**两套语义
描述**，本次要一起收窄成同一说法。

## 测试决策

好测试只验证可观察行为，不锁实现细节。**每层证明什么必须说清**，下面几条尤其不能混。

**本次的验收核心没有离线落点，必须在真 PostgreSQL 上跑。** 注销要验证的是「账号那一行还在、
`deleted_at` 有值、`is_active` 为 false、登录 Token 清空、会话归属与个人偏好仍在、决策记录的
`actor_id` 未变」——这六项里有四项要查四张不同的表。而现在唯一观测得到这些表的用例**默认跳过**；
能离线跑的那个带假会话的账号管理用例只有四个方法，连一张表也查不到。所以验收核心写在那两份
真库用例里，**本次交付前必须跑一次**（与用量 spec 同一条规矩）。

**两份真库用例的断言要整段重写，** 因为它们现在写的就是旧语义：把「账号行没了 / 会话归属清空 /
`actor_id` 置空 / 偏好行没了」改成「账号行还在且 `deleted_at` 有值 / 会话归属仍在 / `actor_id`
未变 / 偏好行仍在」。**但这不等于只改这几类断言**——其中那份迁移用例里有一个必改项：**它把迁移
目标钉成了一个硬编码的版本号常量**。新迁移一加进来，那个常量就变成「旧版本」：库里没有
`deleted_at` 列，而模型有，于是那个文件用模型插种子数据、再走删除路径时会直接因「列不存在」崩掉
——**不是断言失败，是目标为「验收核心」的用例自己坏了**。所以要把该常量更新为新迁移的版本号。

**不能停用或注销自己（后端规则）。** 这条要分两层验，缺一层就拦不住：

- **Service 层**：对新加的那个调用者参数传自己，返回 409 `account_self_protected`。
- **接口层**：断言假 Service 收到的是「目标账号 + 当前登录账号」两个参数——**这是钉住「路由真的
  把调用者传下去了」最便宜的一条断言**。现在那个假账号 Service 的删除方法是单参数的，而且整个
  Service 依赖被替换掉，所以「路由有没有注入调用者」根本不在观测范围内；把路由改回不传，整套
  离线测试照样全绿。

因此 spec 要求：**新加的调用者参数必填、无默认值**。若写成可选参数，任何漏传的调用方都会静默绕过
这条规则。另外要注意一个陷阱：**现在直接打 Service 的那几条用例（改状态与注销各两条）的目标账号
都是调用者自己**——给它们补调用者参数时必须换成一个**不同的**账号 id，否则新规则会先命中，断言
就从原来的保护码变成 `account_self_protected`，那它们就不再验原来那件事了。

**降权取消后，两条现有用例要改而不是删：** 一条原本验「不能降级最后一个活跃超管」——那条保护
已作废，这条用例应该改成验「**不能停用**最后一个活跃超管」（它守的需求还在，只是触发动作变了）；
另一条原本用「取消超管」验「环境托管账号不可动」，同样要改成用「停用」验（这个保护与降权无关，
不能因为动作没了就把用例删掉）。**判定标准：用例守的那条需求如果还在，就换一个仍能触发它的动作；
需求本身消失了（不能降最后一个活跃超管），才删。**

**已注销账号上的动作分类。** 注销本身幂等成功（第二次仍返回成功、`deleted_at` 不变）；停用/启用、
重置密码各返回 409 `account_already_deleted`；撤销会话仍可执行且返回 0。

**两条配对不变量。** 注销后读回那一行：`deleted_at` 非空时 `is_active` 必须为 false；且「环境托管
且已注销」这种行在数据库层写不进去。前者与「注销核心行为」同一条用例里断言（它是同一件事的另一
面）；后者直接写库尝试，必须被约束拒绝。

**登录被挡住，分两层。** 用已注销账号的邮箱与正确密码登录必须失败，且错误文案与「密码错误」
**完全相同**（对应「登录失败文案不变」那一节）。两层各自证明什么：

- **离线层能验一半**：认证的离线用例把用户管理器换成了替身，但**换掉的只是管理器**——登录路由里
  那道 `is_active` 门照旧执行。所以把预置用户设成不可用，就能离线断言「不可用账号登不进来、且文案
  与密码错误相同」。这一半不需要真库。
- **真库层补另一半**：离线层验不到「注销真的把 `is_active` 置成了 false」。拿一个真账号走完注销、
  再拿它的邮箱与密码登录，这一半只有真库能串起来。所以真库那份认证用例要新增这一条。

**启动同步。** 构造「配置里的邮箱对应一个已注销账号」，启动同步必须抛错而不是把它复活。这条要打
在真正的启动同步入口上（那份真库认证用例已经在直接调它），不是打在内部的某个辅助函数上。

**注销后的可见性。** 账号列表接口默认不含已注销账号；带上那个新参数时含，且响应里 `deleted_at`
有值、`is_active` 为 false。这条要把查询参数一起验——只验 Service 参数会让「接口上没暴露」这种
漏失从缝里滑过去。

**迁移。** 存量账号迁移后按原 `is_active` 分别是活跃/停用，`deleted_at` 均为 null；迁移不动任何
行数。先例是既有的迁移测试。

**`is_active` 不被误伤。** 知识库的启用/停用行为在本次改动后必须有既有用例原样通过——用来证明
没有做全局替换。这一条不新增测试，靠既有的知识库用例覆盖即可。

**静态客户端要重新生成。** 改完后端接口描述后重新生成前端那份提交进仓库的客户端类型并提交，
确认文件里不再有「置空换版决策留痕」这句话。仓库没有任何检查会提醒这件事。

**改造清单（具体文件与行号在工单里写，本 spec 不列）。** 先改实现，再让受影响的测试红了就修。
有三份真库用例必须列进来：两份旧语义写得最死的（迁移、会话归属），以及那份要新增「登录被挡住」
与「启动拒绝复活」两条的认证用例。离线侧还要改账号管理用例（假 Service 的签名与调用者断言，
注意上面那个「目标就是调用者自己」的陷阱）、账号自助用例、列注释断言那条、以及建号用的夹具。
前端改账号管理那几个用例、登录接口用例、错误码文案表、查询键与概况统计，并重新生成静态客户端。
不预先通改一遍——漏掉的会被测试抓出来。

**文档与代码注释项要一起改，它们现在写的都是旧事实。** 这几处不在测试里，没有东西会提醒：

- **后端架构说明**：接口清单里那条删除接口写的「连带清会话归属与登录 Token」、改状态接口写的
  「改启用状态与**超级用户位**」（那个位不再可改）、以及环境托管保护段落里「不能通过 API 停用、
  **降级**或重置密码」与错误码列表；「会话数据分在两处」那一节里「连带清理由删账号完成」。
  另外它现在有一处指向本 spec 的引用——本 spec 交付时会被删除，那处引用要在那时改指向 ADR 0034。
- **能力地图**：用户管理那一行的能力名（现在写的是「增删改、改密、踢会话」）与它的测试列。
- **根与后端两份仓库常驻指令里的方法名清单**：两处都把账号管理的删除方法说成「删账号的唯一
  路径」——软删除一落地这句就是假话（它不再删行）。改法是**规则留下、方法名移走**：保留「连带删除
  逻辑集中在各聚合自己的 Repository/Service 里、改动前确认有没有第二条路径、测试也走这些路径」
  这条稳定规则，方法名清单归到后端架构说明里唯一的一份。理由：那份清单已经复制了两份且详细程度
  不同，其中一份括号里逐字写着硬删除的四个动作、本次全部失效；而且它本来就不全（任务执行到期
  清理那条路径也会处理父子关系，却不在清单里）。
- **代码注释里那批硬删除语义**：偏好模型的模块注释与偏好 Service 那个要删掉的方法的文档注释（都写
  着「删账号时由业务层显式删除这一行」）、账号管理 Service 的模块注释与删除方法的文档注释（那五步
  里写着「置空换版决策的操作者」）、以及给偏好表加列那条迁移的头部注释。本仓库把注释当契约管
  （本 spec 自己就要求新列带注释，理由是有用例断言每列都有注释），留着这些就是假话。

## 超出范围

- **恢复已注销的账号。** 第一版不做恢复入口。数据保留不等于可恢复。
- **注销的保留期与自动清理。** 不引入定时清理任务；`deleted_at` 只是把起点记下来，将来要用再说。
- **注销时匿名化或清理这个人的历史数据。** 会话归属与个人偏好保留原样。
- **邮箱回收。** 已注销账号的邮箱永远占用，不能建新号。
- **注销理由、操作者、状态历史表。** 不记这些。
- **决策记录里操作者身份的查询入口。** `actor_id` 保留在库里但没有任何接口把它变回人；要不要
  提供这个能力另议。
- **登录失败时区分停用与注销。** 保持通用文案。
- **真删账号的命令。** 见「不新增真删账号的命令」一节。
- **用量统计模块本身。** 本 spec 只保证「已注销账号能被查到是谁」这个前提；用量那边怎么显示由
  它自己的 spec 决定。

## 补充说明

**与用量统计 spec 已经解耦。** 两份 spec 自包含、互不阻塞：本 spec 保证注销后账号行与邮箱仍在，
用量那边因此不再需要「账号已删除」这个展示分支（那边已按此改过）。

**领域词汇。** 术语表的「账号与偏好」一节新增「**注销**」词条，更新「**停用**」词条。
「账号」那条不改——软删除之后「一个能登录的主体，邮箱是它的唯一标识」仍然成立。
术语表与决策记录的写入受仓库门禁约束，只在专门的访谈流程里改。

**一条依赖要写明。** 决策记录的 `actor_id` 原本是「置空」语义，理由是「账号行没了、指向不存在的
标识没意义」。本 spec 之后账号行还在，所以改成保留。这个反向变化要让后来的人知道是**刻意改的**，
不是漏改。

**工单。** 本 spec 定稿后拆成垂直切片，写在 `issues/` 下，进度和验收勾选写在工单里；上面那些
「具体文件与行号」的落点也写在那里。交付时随本 spec 一并删除。
