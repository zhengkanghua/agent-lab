# Agent 运行脱离浏览器连接

## 问题陈述

一次 Agent 运行的生命周期今天挂在浏览器的 HTTP 连接上：客户端拉响应体、响应体拉事件流、事件流拉模型，没有人拉，模型就不往下走。于是关掉页面、断网、切走会话，或者服务端连接超时，这次运行立刻被掐断。

被掐断的后果不只是「这次答案不完整」。落库发生在**每个节点完整结束时**，而不是每个 token：模型节点要等整个答案吐完才算结束，所以取消一个正在输出答案的节点，那一整格都不落库；已经在屏幕上显示出来的文字，断开那一刻只存在于浏览器内存和那条正在断的连接里，服务端拿不回来。而模型那边很可能已经把请求处理完并计了费。**钱花了，答案没了。**

同一条链路还压着一个约束：停止按钮今天之所以有效，靠的是它顺带断开了连接。也就是说「关页面」和「停止」走的是同一条路，用户无法只表达其中一个意图。把运行从连接上拆下来之后，这条路就不通了，停止必须另有一条通道，否则它会退化成假停止——界面看起来停了，模型继续烧钱。

## 解决方案

一次运行不再由浏览器连接驱动。请求受理后由服务端自己把事件流读到结束，HTTP 响应退化成它的订阅者：浏览器在就顺手把事件转发给它，浏览器走了照旧跑完，结果自然落进会话历史，下次打开会话就能读到完整答案。

运行过程中服务端自己累积一份模型输出。运行被中断时（用户停止、上游失败、超时），把**尚未落库的那部分**写进会话——差一点就丢掉的正是用户已经看见的那些字。**连接断开不算中断**，它只减少订阅者。

「停止」另开一条通道：用户点停止后服务端真的把这次运行停下来，已经输出的内容按截断保留在会话里。同一个会话同时只允许一次运行，第二次提交被拒绝。

## 用户故事

1. 作为登录账号，我想要关掉页面之后那一次运行继续跑完，以便下次打开能看到完整答案。
2. 作为登录账号，我想要断网或切走会话时运行不被打断，以便网络恢复后答案还在。
3. 作为登录账号，我想要刷新页面之后仍能看到完整答案，以便不用重新提问、再烧一次钱。
4. 作为登录账号，我想要手动停止时已经显示出来的内容留在会话里，以便停在哪里就是哪里，而不是回来发现全空了。
5. 作为登录账号，我想要停止按钮真的能停住服务端的工作，以便它不只是把画面冻住、模型还在后台烧钱。
6. 作为登录账号，我想要停止之后不再产生新的模型调用，以便不为一次已经放弃的回答继续付费。
7. 作为登录账号，我想要停止之后这个会话仍然能正常提问和续聊，以便不用新开一个会话。
8. 作为登录账号，我想要上游出错或超时时已经输出的部分也留在会话里，以便失败不等于白问。
9. 作为登录账号，我想要一个会话在运行中不能重复提交，以便不会出现两次运行互相覆盖、静默丢掉一次运行。
10. 作为登录账号，我想要重复提交被拒绝时看到明确的说明，以便我知道是「正在生成」而不是「出错了」。
11. 作为登录账号，我想要在运行期间（包括刷新之后那一次运行还在跑时）界面明确显示正在生成、发送按钮是灰的，以便我不会以为这次没有回答、也不会做出注定被拒绝的操作。
12. 作为登录账号，我想要删除一个正在运行的会话时它先停下来再删，以便不会留下查不到也删不掉的残留。
13. 作为登录账号，我想要服务端重启或崩溃之后这个会话能自动恢复，而不是永久不能提问，以便一次崩溃不会把这个会话弄废。
14. 作为登录账号，我想要部署期间被中断的那一次运行最终如实表现为没有回答，而不是永久卡在生成中，以便我知道该重新提问。
15. 作为登录账号，我想要被中断的那一次运行就是停在哪儿显示到哪儿，以便不用先读一行提示才知道内容被截断了。
16. 作为运维者，我想要删除会话或注销账号之后不留下查不到也删不掉的运行残留，以便数据不会越积越脏。
17. 作为运维者，我想要一次卡住的检索不会让这个会话长期没法提交新提问，以便我不用等到有人按停止或进程重启才能继续在那个会话里提问。

## 实现决策

**运行驱动者。** 新增一个与 HTTP 响应解耦的后台执行单元，职责是把事件流读到结束并完成收尾；HTTP 响应变成它的订阅者，浏览器断开只减少订阅者，不影响执行。它必须能在没有任何订阅者的情况下独立跑完。

「被中断」的判据是**事件**，不是异常：事件流的翻译层把已分类的失败（含上游超时、限流）翻成 `error` 事件后是正常返回、不抛异常。用「事件流抛异常」判断被中断会漏掉失败与超时这两条本来要补写的路径；终态只能看事件。

**停止是协作式的。** 运行单元在等待下一个事件时用短超时轮转，每次轮询都看一眼内存里的停止标志；发现有人要求停止，就自己取消那次模型调用、关闭事件流、写入已输出内容、正常发出终态事件。关键是**运行单元本身不被取消**，收尾写入因此发生在完全正常的上下文里，没有任何取消在传播。只有进程被强制关闭那一种情况才需要在被取消的上下文里写库，而那时本来也救不了。

**停止接口是对外契约，必须新增。** 它与对话接口同级，是一个普通的 JSON 接口（POST），请求体包含会话 id 与**运行 id**，成功响应表示已受理。改动之后前端原来那条「中止本地请求」的路对服务端不再有任何作用，没有这个接口停止就是假的。

请求体必须带运行 id：只带会话 id 时，服务端只能对「当前在途的那一次」置停止标志，而停止请求可能迟到（用户先点停止 → 旧运行已收尾 → 用户发下一次提问 → 迟到的停止到达），于是误杀掉新开始的那一次运行。服务端只在**在途运行的 id 与请求里的运行 id 相等**时才写停止标志；不相等一律幂等返回成功（视为「没有要停的运行」）。会话不存在或不属于当前账号，按既有 404 形状。

前端点停止后调它，并**保持连接直到服务端发来终态事件**，用服务端给出的内容与状态渲染；本地不再自建一套结局状态。这样「点停止时看到的」与「刷新后看到的」是同一套口径，也避开了「服务端推出去的」与「浏览器收到的」在断网瞬间的差字问题。

**收尾写入。** 被中断的运行在收尾时把**尚未落库的那部分**模型输出写进会话。

累积口径是「尚未落库的部分」，不是「整次运行」：一次运行里模型节点会被调用多次（每次工具调用后都要再问一次），先完成的那些节点已经把文本落库了，而累积器里同样有它们；按整次运行累积会把已落库的文本再写一遍，回放出的答案出现重复。实现上以「最近一次已落库的模型消息」为界。驱动者需要在事件流里能看到这个边界——当前翻译层只转发带工具调用的模型消息，所以要额外发一个只给驱动者看的节点完成信号，不进对外事件契约。

累积的是服务端**推出去**的文本，不是浏览器实际收到的，断网瞬间未送达的字节也会被写入；这是刻意选的方向。**没有文本就不写**：写一条空的模型消息会把那一次运行变成「有回答但内容为空」的怪状态。写入的消息要能归到本次运行，并标成**未完成**——截断是事实，标成完成会让半句话看起来像完整答案。

**界面不再给截断提示。** 现有的两处提示（「已停止 / 回答未完成」与「以上内容不完整」）连同样式一并去掉；被中断的那一次运行就是停在哪儿显示到哪儿。这两处本来也覆盖「达到处理上限」等其他截断情形，一并去掉。

**运行状态与僵尸判定。** 会话记录上新增两样：**在途运行的 id**（为空表示没有运行在跑）与**停止请求的时刻**（为空表示无人要求停止）——后者在下一次占位时清掉，理由见「同会话串行」那一段。这两列就是全部真相，没有第二份状态副本。

**停止标志怎么送到正在跑的那次运行。** 每个 API 进程有一个小协程，按固定节奏（初值每秒）做一次**批量查询**：把自己手上在跑的每一次运行的这两列读一遍，写进内存标志；运行单元自己不碰数据库，每次轮询只看那个内存标志。用批量查询而不是逐个运行查一次，是为了让负载与「一个进程挂了多次运行」无关。停止请求不直接取消运行——请求可能落在另一个进程上。

判活的依据是会话的**最后活动时刻**，由运行驱动者按固定节奏往库里更新。超过阈值没有更新就视为那次运行已经中断并释放这一会话（进程崩溃时没有任何清理动作会执行，所以「标记永久有效」本身就是要防的故障）。**阈值由「多久往库里更新一次活动时间」决定，不由操作超时决定**：更新是驱动者自己的循环在做，与「一次模型调用跑了多久」无关。初值取「更新间隔的四倍余量」：读状态每秒一次、最后活动时刻每 30 秒落库一次、僵尸阈值 2 分钟。常量按既有约定放进 Agent 层的常量模块，不进环境配置。

**刷新之后怎么知道这一次运行还在跑。** 「有运行在途」是服务端才知道的事，刷新后前端必须能重新拿到它；否则会出现自相矛盾的组合：界面显示「这一轮没有留下回答」，用户再发一条却被服务端以「还在生成中」拒绝。

所以读取会话历史的接口要在响应里带上**当前在途运行的 id**（为空表示没有运行在跑）——这是它唯一的用途，不是把运行状态暴露给用户看。前端据此：最后一次运行没有回答、而会话有在途运行——显示「正在生成」、禁用发送，并每隔几秒重读一次会话历史，直到服务端不再报「有运行在途」；到那时这一次运行自然换成没有回答，或者换成已经写好的内容。**不由前端自己设一个放弃上限**：失活判定会结束服务端的上报，所以这个轮询必然终止；而前端设的上限如果短于服务端的失活窗口，就会出现界面与服务端相反的情况——界面已经放弃「正在生成」，服务端却仍以「还在生成中」拒绝提交。轮询只用来知道它什么时候结束，不接续正在生成的实时文字。

**同会话串行的占位必须原子。** 判断「这个会话有没有在途运行」与占位必须是一次条件写入，不能先查后写：先查后写会把这个竞态原样留下，而且比现状更隐蔽（现在两次运行的结果都能看到，改完是拒绝形同虚设、静默丢掉一次运行照旧）。占位之后的任何失败路径都必须释放这个占位，否则会话要等僵尸阈值才解锁。这次条件写入还要**顺势清掉上一次留下的停止请求**：只在运行收尾时清是不够的——进程可能在清之前就被杀掉，留下一个陈旧的停止标记，于是刚起步的新运行一开场就被它停掉。那恰好是写入端用运行 id 比对想防的事，只是从写端挪到了读端。

**工具调用必须有超时。** 一次不返回的工具调用会让这次运行卡住，而这次运行仍然算「活着」（最后活动时刻照常续期，不会被判成僵尸），于是这个会话一直没法提交新提问——只能等用户按停止或进程重启。给它加一个超时上限就能自动收场。超时后走现有的工具错误路径（模型收到安全文案，自行决定重试或作答）；注意工具错误表里**没有超时对应的规则**，它会落到兜底的那句「未预期错误」——安全，但对模型来说不是「可以重试」的语义。是否给它单独一条文案由实现定，不是本次必需。初值 30 秒，与同类检索超时同量级。本次**不加运行级时长上限**——一直在推进的运行不该被打断。

**删除正在运行的会话。** 先请求停止并等它收尾（轮询在途运行 id 是否已释放），等不到就按已中断处理，然后走现有的两步删除（先清会话历史、再删归属记录）。不能无限期等：删除请求挂住比留下一次未完成的运行更糟。

**数据库结构变更。** 会话表新增上述两列，需要一次新的迁移，并同步更新列注释；最后活动时刻那一列的语义从「最后一次提问时刻」扩为「最后活动时刻」，相关决策记录随之更新。**升级数据库按仓库规矩需要老板明确同意后才执行。**

**错误契约。** 重复提交返回 409，并新增稳定错误码 `agent_run_in_progress`（前后端必须用同一个字面量，所以在这里定下）；该码要按既有要求在前端文案表同步登记。注意 Agent 链路的错误规则表不在跨表不变量的测试覆盖范围内，所以「同一错误码对应同一句话」这条在 Agent 链路上靠人守，不是靠测试。

**事件流收尾的注释修正。** 现有代码里「断开时 ASGI 服务器会关闭本生成器」的说法与实际不符：服务端声明的事件流协议版本走的是取消作用域那条分支，生成器体内收到的是取消异常、不是正常关闭。本次要改这段生成器，顺手改正这句注释。

## 测试决策

好测试的标准：断言**外部可观察的行为**——用户看到的答案内容、会话是否还能提交、错误码——而不是内部函数调用次数或私有状态。

**主要接缝只有一处：HTTP 层**（现有最高的接缝）。用真实应用、假模型与内存会话历史断言用户可见的结果：客户端在流中途断开后运行继续跑完、随后回放能读到完整答案；重复提交返回 409；停止接口幂等；停止之后的内容与终态正确；回放响应带出在途运行 id（刷新后前端据此显示「正在生成」）。

**为什么不能沿用现有的进程内传输来造断连**：它要等响应完成才报告断开，响应体也先全部收集再一次返回，所以「客户端在流中途断开」这个动作在那个传输上不存在——这样写出来的测试在改动前就会通过、改动失败也不会变红，等于没测。改为直接驱动真实应用的 ASGI 调用入口：声明与服务器一致的协议版本，读到首帧后返回断开事件，这就是真实的断连路径。它不连数据库、不连向量库、不调真实模型，开销与普通单测相同。这也是本次唯一新增的测试手法。

断连测试的等待方式：**轮询那个回放接口**直到这一次运行出现答案（短间隔 + 一个总时长上限，上限只用于防止用例自己挂住，不是产品行为），不要依赖应用内部的句柄，也不要用固定 `sleep` 去猜——前者会为测试多开一个内部读数点，后者会变成不稳定用例。用假模型与内存会话历史时这一次运行在毫秒级结束，一两次轮询就够。

其余断言落在既有的离线接缝上（假模型 + 内存会话历史），不新增测试基建：

- 回放断言补写的答案被认成这一次运行的回答，并断言累积口径不重复（用一个「先吐字、再要求调工具」的假模型复现，那是最常见形态）。
- 工具超时用一个会挂住的假工具，断言模型收到安全文案而不是整次运行失败。
- 会话归属与删除断言有运行在跑的会话先停后删。

## 超出范围

- **在途逐字续看**：刷新后不接续正在生成的实时文字，跑完为准（与 ChatGPT / Claude 一致）。不建进度快照、不做事件续流；刷新后能看到「正在生成」并等它结束，但中间的字不会实时补发。
- **结局标签**：不给任何结局做持久化标签，界面上也不做「已停止 / 回答未完成 / 内容不完整」这类提示（前端现有两处渲染一并删掉）。
- **账号级并发上限**：不加。拆开连接后原本由「关页面即取消」提供的粗放反压消失，一个账号可以同时让多个会话各跑满模型调用额度；这一条只作为已知缺口记录，不引入限制（收窄正常使用能力的代价大于当前的故障风险）。
- **补写工具调用与工具结果**：它们本来就在各自节点结束时独立落库，中断不会丢，无需补救。
- **运行历史**：不记录每次运行的起止与耗时。用量统计由另一份工作负责，两处都存会形成两个真源。
- **把 Agent 搬进任务队列**：进程重启导致的运行中断在本期不解决。
- **部署参数调整**：不属于本 spec。

## 补充说明

**部署期间的中断是已知边界，不掩盖，而且它有窗口。** 脱离请求的后台任务不在「等在途请求」的范围内，所以部署、崩溃、内存耗尽都会让正在跑的那一次运行中断，收尾也来不及。

进程被杀之后，会话记录上的在途标记**不会被任何人立刻清掉**——只能靠失活判定（初值 2 分钟）自动释放。所以在这段窗口内：回放接口仍报「有运行在途」，界面显示「正在生成」、发送键是灰的，用户提交新提问会被拒绝；窗口结束才解锁，那时界面上的表现是这一次运行没有回答。**这个窗口已确认接受**：它不是可以修掉的缺陷，而是「无法区分进程已死与运行很慢」的必然结果；把它写出来是因为 story 13/14 容易被读成「要求立刻反应」，从而去加 spec 没设计的快速失活检测。

**删除正在运行的会话有一条已知代价。** 如果那次运行在等待窗口内没有停下来（正好卡在一次调用里），删除会按「已中断」继续执行：先清会话历史、再删归属记录。而那次运行随后仍可能把收尾内容写回同一会话，于是留下一条有历史、没有任何归属记录的残留（术语表里的「孤儿会话」），只能靠运维命令清理。这是「不无限期等」换来的代价；不必为它加机制，但要如实记录。

**未在真实环境验证的结论，实现时按不确定处理**：

- 「取消路径上能完成异步写」只在内存 checkpointer 上实测过，未在真实数据库 checkpointer 上验证；真实数据库的异步写入与取消之间存在竞态窗口。
- 「并发写同一会话不抛异常、静默丢掉一次运行」同样只在内存 checkpointer 上实测过。
- 两个 API 进程能支撑多少并发运行没有实测。按配置推算，真正的约束是数据库连接数，而不是 CPU；运行是 I/O 密集的，数据库连接只在写会话历史的瞬间被占用。**最先撞到的墙几乎肯定是上游模型服务的并发与额度**，那在代码之外。
- 一个附带的好处：「同时在跑几次运行」这次变得可观测（会话记录上有在途运行 id），上线后应按真实数据判断是否需要扩容。

**实施顺序的建议**：先做「断开不取消 + 后台驱动」并验证主诉求（关页面跑完、下次能读到），再加「收尾写入已输出内容」，然后是「同会话串行」，最后才是「跨进程停止」。这样每一步都能独立验证，也让「停止暂时不可靠」这个中间状态的时间尽量短。

**与并行工作相关的措辞风险**：本 spec 说「删账号时的连带清理沿用现有路径」，而当前代码里删账号仍是硬删除（软删除在并行未落地的那份 spec 里）。两条 spec 若并行施工，这句话会在施工时分叉；按当前代码实现即可。
