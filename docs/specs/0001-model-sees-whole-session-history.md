# 主模型接收会话完整历史

## 问题陈述

Agent 在一个会话里记不住自己说过什么。用户问「刚才那个是多少」「你上一条引的那份资料」，模型答不上来——因为它每次被调用时，历史里只有用户问过的话；它自己答过什么、上一轮查到了什么、之前有没有被压缩过，全都看不到。

这套裁剪当初是为了防一件事：同一个会话允许切换知识库范围，切到新范围之后模型可能拿只属于旧范围的事实作答。但它没有区分「换了范围」这个罕见情形和「范围从头到尾没变」这个常态——绝大多数会话从不换范围，却在替最罕见的情形付账，代价是模型完全没有多轮记忆。

## 解决方案

撤销那条裁剪：模型每次调用都收到这个会话此前的完整往来。防「旧范围事实被当成新证据」这件事改由**证据层**承担——它本来就在承担：只有本次运行、允许范围内的工具结果才会被认作证据，旧引用一定核验不出来。裁剪额外压住的只剩「模型偷懒、不重新检索就复述旧结论」，那是通用的偷懒问题，范围不变的多轮会话里同样存在，用提示词治，不靠删历史。

为了让上下文不被撑爆，压缩从「按消息条数」改成「按模型窗口占比」，并且在压缩之前先清掉旧的检索原文——清够了就不做摘要。**用户看到的东西不变**：回看读的是会话历史那张业务表，它在运行收尾时写下、此后永不清理，所以被清那段在**模型那一侧**变成了占位文字，在**用户那一侧**仍旧是原文。

## 用户故事

1. 作为会话使用者，我想要在同一轮里用「刚才那个」指代前面聊过的东西，以便不必重复描述。
2. 作为会话使用者，我想要模型记得它自己上一轮答过什么，以便我能追问、纠正或者接着往下问。
3. 作为会话使用者，我想要模型看得见它**最近几轮**检索到的原文片段，以便追问细节时不用重新查一遍。
4. 作为会话使用者，我想要模型在长会话里仍然知道我们一开始聊到哪，以便不用重新交代背景。
5. 作为会话使用者，我想要在我切换了知识库范围之后，模型仍然理解我们之前在聊什么，以便自然地接着问。
6. 作为会话使用者，我想要模型不会把上一个知识库里的事实当成这次范围内的证据，以便答案的出处可信。
7. 作为会话使用者，我想要答案里出现的引用都是本次真的取到的，以便我点开就是原文。
8. 作为会话使用者，我想要模型抄不到上一轮的引用标识，以便我的答案里不会出现一堆点不开的引用。
9. 作为会话使用者，我想要长会话不会因为上下文撑满而失败，以便我能一直聊下去。
10. 作为会话使用者，我想要压缩之后模型仍然记得我们的偏好、查到哪儿了、还有哪些没解决，以便对话不断线。
11. 作为会话使用者，我想要压缩不会在模型正用着某次检索结果的时候把那段抽走，以便它当场给出的结论仍然站得住。
12. 作为会话使用者，我想要换取更长的记忆不必付上「答案出处变模糊」的代价，以便我在同一个会话里既能连贯地聊，又能核验结论。
13. 作为会话使用者，我想要压缩别每几轮就来一次，以便模型不被反复打断。
14. 作为维护者，我想要压缩的触发与保留按模型窗口的比例算而不是按消息条数算，以便换了模型之后它自动跟着变。
15. 作为维护者，我想要窗口值在每次调用时读取而不是在进程启动时写死，以便按会话选择不同模型。
16. 作为维护者，我想要压缩动作留下「它发生在哪一轮之前」的痕迹，以便界面以后能如实标出模型记忆的边界。
17. 作为维护者，我想要这次改动不动表结构（表由会话历史那次改动负责），以便两件事的职责分开、各自可验证。

## 实现决策

**撤销裁剪。** 主模型每次调用接收会话 checkpoint 里的整份上下文记录：历史提问、历史回答、历史工具结果、历史摘要。负责裁剪的那个中间件保留另一半职责——给模型消息盖完成态标记（那是「这一轮答完没有」的真源，终态与回放都读它）。这次是拆，不是删。**它原本还有一个短路：本次运行没有知识库范围时整段跳过、什么都不盖——撤掉裁剪之后那个短路没有存在理由，一起去掉。**那个标记现在也是会话历史表的切分依据（每一条消息属于哪一次运行），所以每一次运行都必须盖。**这样的短路其实是两处，两处都要改**：一处是那个中间件给助手消息盖标记（只影响助手行），另一处是**提问消息自己的构造**——本次运行没有范围时它连 `run_id` 都不带，而切分与运行元数据（范围快照、模型快照）全挂在提问行上，只改中间件那一处等于没改。**同一个理由，摘要中间件那道「运行中不压缩」的守卫也要去掉它按范围判断的条件**——它防的是「运行中途把这次回答的证据压掉」，跟本次运行有没有范围无关；留着那个条件，无范围的会话在运行中仍可能被压缩，而下面「放大正文上限」那条的计算正是以「一轮之内不压缩」为前提的。

**发送副本剥掉旧引用标记。** 送给模型的那一份里，`[[E1a2]]` 形状的旧引用标识替换成 `[出处已失效]`。**「旧」的界是「本次提问之前的那些消息」**——本次运行自己的工具结果里带着同形状的标识，那是模型唯一能拄的东西，一个字都不能动（与下面「先清后压」同一个界）。替换只作用于发送副本，checkpoint 里存的原文一字不动——用户回看那一轮时当年的引用仍然点得开（回放是拿那一轮的答案文本对它自己的证据去解析的）。替换用单层方括号，不与只认 `[[E...]]` 的引用正则相撞。

**系统提示词那一句重写。** 现在那句「历史问题只帮助理解意图，旧回答、摘要和旧引用都不是本次证据」在撤销裁剪之后是假的——模型手里明明有这些内容。改成从「描述历史里有什么」翻向「约束历史怎么用」：说明能看到完整往来，但历史里的回答、摘要和引用都不是本次事实的依据，本次的事实性结论必须来自本次工具返回的内容并原样引用本次标识，历史内容里标着 `[出处已失效]` 的地方不要复用。范围那两句（只用允许目录中的资料、名称有歧义先询问）继续留在有范围时注入的那一段；**而「历史不是本次证据」那半句要拿出来、无条件注入**——它讲的是整段对话里的旧内容，与本次运行有没有范围无关，而按范围短路正是这次要拆掉的东西。

**压缩口径改为模型窗口占比**：触发取窗口的 80%，压缩后保留 30%。上游的摘要中间件原生支持按窗口比例配置，不另造。

**先清后压。** 压缩触发后、调摘要模型之前，先把较旧的工具结果正文清掉：保留消息、保留工具调用与结果的配对，只把内容换成占位文字。工具调用与其结果成对是上游接口的硬要求，删掉一边请求会被拒。下面三个边界要写死，否则实现者会挑一个后果不同的做法。

**清理写回 checkpoint 状态，不是只改发送副本。** 因为上游的摘要中间件在 `before_model` 里按 state 里的消息计量触发：只改发送副本的话，「清完重新计量」这一步看不到效果，「够用就不调摘要模型」就不成立。

**「较旧」的界是「本次提问之前的全部工具结果」**，**从最旧的开始清、越新的越晚清**（近期那几次检索结果对当前这轮最有用），清到计量降到触发线（窗口的 80%）以下就不再调摘要模型——不是「最近 N 条」。每条正文**只保留头 512 字符与尾 256 字符，中间换成 `[... tool result middle pruned ...]`**（这两个数按我们自己的工具输出上限选，不是照搬外部默认值：读取全文的正文上限在本次改成随窗口算（见下面那条），检索一次几段原文；头尾留到几千字符就等于清不出量，「清够了就不调摘要模型」那一支就永远不会发生；**正文长度不超过「头 + 尾」之和时原样保留、不清理**，不能把短的反而拼长——工具失败时返回的几十字安全文案就属于这一类；模型仍然知道每一次调用了什么工具、传了什么参数，因为参数据在助手消息里、不归清理管）。**清理只动工具消息的正文，引用证据原样留着**——那里存的是归属、版本与来源，回放的引用核验读的就是它。顺序有语义：**先清、再计量、最后才决定要不要摘要**；而摘要的切点（保留 30%）也按**清理之后**的计量算——触发与保留用同一把尺子，不然后者会把刚清出来的余量又填回去。

**压缩的切点仍然要对齐到一轮的提问处**（既有的回溯逻辑保留）。改成按窗口比例之后切点会落在任意位置，不对齐就会切出「没有提问、只有工具结果」的轮次，而上游接口要求工具调用与结果成对、回放也按提问分轮。

**清理影响的是模型看到的东西，不该影响用户看到的。** 用户回看读的是会话历史业务表，那一份在运行收尾时写下、**此后永不清理**；所以被清走的那段工具正文，模型看到的是占位文字，用户看到的仍是原文。**这条可见性有硬前提：会话历史业务表必须和这次改动一起落地。** 只做其中一件的话，用户回看读的还是 checkpoint，那一轮会像今天一样整块消失（压缩是破坏性的），「用户看得到完整对话」就不成立——那也正是 [0043](../adr/0043-session-history-outlives-summary.md) 要的东西。

**把给模型读的正文上限与窗口绑起来。** 今天的 6000 是拍出来的定值（它自己就已经是 32k 窗口的约 18%），而「一轮之内不压缩」意味着每轮只有「1 − 触发线」= **窗口的 20%** 余量留给「本轮工具结果 + 回答」——所以单次上限必须与窗口成比例，否则窗口小的模型一次读取就能把这一轮顶出窗口。规则：**单次上限取窗口的 20%，封顶 20000 字符、保底 2000 字符**，它作用在**一次工具调用交给模型的文本总长**上——今天只有读全文那条是拍出来的定值，检索那条靠「最多几篇 × 每篇几段」间接约束，本次一并按同一个上限管。于是窗口 32768 时约 6500 字符（略高于今天），窗口 100k 以上按封顶的 20000。**「窗口填小了只是压缩得更早」这个说法是错的**：窗口填小同样会让工具输出把这一轮顶出去。

**最坏情况仍可能越窗，这条要明说。** 一次满额读取就会吃掉整轮余量的大部分（今天的定值也是这样），所以一轮里再调一次工具就可能越窗——那时上游报错、这一轮按失败收尾。这是既有的、已接受的边界，本条不引入新机制去拦它。

**引用机制不动，但证据里那份正文副本去掉。** 先分清两件事：引用机制本身——答案里的标识、点开引用、无法核验的提示——就是「用户能自己核对」这件事，**保留**；去掉的只是**弹窗里那段「当时引用的片段」**。

它今天确实在用：点开引用时阅读器会显示「当时引用的片段」，与下方现取的当前原文对照，并在正文改过时给出提示。所以这不是「删一段没人看的代码」，而是**去掉一个已交付的界面区块**。依据是：那段正文**在同一张轮次卡片下面的工具轨迹里本来就有，而且是完整的**（轨迹存的是当时交给模型的正文，比这份片段还全），业务表落地后被压缩掉的旧轮次也一样查得到——留着它等于在同一屏里放一份「更短、更差、重复」的副本。**这也是为什么它必须和业务表同一次落地**：在业务表之前删，被压缩过的旧轮次就再也看不到当时的内容了。

要一起去掉的东西列清楚：证据模型上那个正文片段字段与它的「是否被截断」标记、前端那个区块与它专用的结构类型、前端的字段校验、由接口生成的前端类型，以及那条已交付的前端断言、流程文档里那句「阅读器显示当时取得的片段」、架构文档里两处（一句是「实际 Tool 结果带应用生成的引用标识及 artifact，保存原文片段和对应 `content_hash`」，另一句是「引用阅读另外展示当时取得的片段」，两处的「片段」都是被去掉的字段）。**引用标识、文档归属、正文版本与来源链接全部保留**——「这篇文档改过了」那个提示靠的是正文版本，不是这段片段。**这条修订了两份 ADR 里写死的存储清单**：[ADR 0045](../adr/0045-model-sees-whole-session-history.md) 那句「随同一条消息保存归属、`content_hash` 和片段」与 [ADR 0044](../adr/0044-session-history-in-own-table.md) 那句「引用证据（文档归属、`content_hash`、片段、来源）」——两处的「片段」都要去掉，两份 ADR 已同步改过，不要静默绕过。

**实现位置有硬约束：清理逻辑放进既有的那个摘要中间件里，不得新增带 `before_model` 的中间件。** 上游按「列表里第一个带 `before_model` 的中间件」给图的入口节点命名，而今天的入口节点就是那个摘要中间件（实测节点名 `RunSafeSummarizationMiddleware.before_model`）——新加一个排在它前面会让入口节点改名，部署撞上在途运行就接不上手，丢掉那一次运行。放在同一个中间件里天然生效，因为计量本来就在那里做。

**摘要输入不再截断。** 上游默认只把被折掉那一段的末尾送去摘要，改成全部送去。前提是摘要模型的窗口不小于主模型——按「触发 0.8、保留 0.3」推算，被折掉的那段在触发点最多占窗口的一半，上下文更大时最多约七成，两种情况都装得下。

**摘要送给模型。** 它从此是模型对被压缩那一段的唯一记忆。摘要提示词保持现有要求（保留问题、偏好、查询方向、未解决疑问；丢弃大段原文；不制造可点击的引用标识），只补一句：被标注为已清理的工具结果不必在摘要里提及。

**窗口值按调用期读取。** 中间件在每次模型调用前从本次运行取窗口，用按协程隔离的上下文变量往下传——图是进程共享的，把值挂在中间件实例上会有并发串。来源是**可用模型**条目上的窗口值（模型目录见 [spec 0002](0002-model-catalog-and-user-model-choice.md)）——那一列必填、不允许留空，新建表单预填一个保守的默认值。**构造时也得有一个非空值**，而且要经客户端对象带进去（上游在构造摘要中间件时就校验窗口存在，缺了直接抛异常、进程起不来）：构造时先用一个固定值（取 **32768**）就位，运行时再按调用期取到的覆盖它——**这个数的唯一职责是通过上游的构造校验**，它不参与运行期的任何计算，取多少都不影响行为，所以不要拿它当真值去推任何结论。**窗口值跟当轮选定的那个模型条目一起进运行上下文**（它本来就是那条目的属性），不按模型 id 回查目录——回查会在目录已被改过、而运行又在排空接手时给出与冻结那一轮不同的值。

**但运行期的真实窗口不靠客户端对象上那个字段提供**。那个字段是构造期按值拄下的（连用量采集包装都只能按值对齐它，因为它是字段、做不成委托属性），逐调用改不动。所以运行期由**覆写「取窗口」那个方法**来提供——摘要中间件每次计量都会调它，覆写版改成从按协程隔离的上下文变量里取当轮的值。客户端对象上那个窗口值**只为通过上游的构造校验而存在**。这是这套参数最脆的地方，别把它做成“只靠上下文变量”。

**摘要消息记下分界。** 记的是**被折掉那一段里最后一次提问的 `run_id`**，语义是「这一轮及其之前的轮次，模型只剩摘要」——轮次在本仓库就是靠 `run_id` 对齐的（回放按它分轮、排空接手也按它找那一轮），后续的界面与业务表才能据此画线。**如果被折掉的那一段里一条提问都没有**（第二次及以后的压缩可能出现：保留段刚好从摘要之后的第一条提问起），就**沿用上一条摘要记的分界**，让这条痕迹跨多次压缩延续下去——记空等于这条痕迹白记，而它事后推不出来。写进摘要那条消息的附加字段。**同一个口袋里还要记一个「产生它的运行 id」**——摘要消息压缩一次之后就一直留在状态头部、不会自己消失，会话历史表需要一个判据区分「这是本次运行刚产生的」与「这是沿用下来的旧摘要」，不然每一次后续运行的收尾都会把它重写一行。这件事必须在这一刻做——它是事后推不出来的，只能在压缩发生的那一刻记下。

**几件明确不做的事**：不按知识库范围筛选历史、不强制换范围时开新会话、不给旧内容贴范围标签。理由见 [ADR 0045](../adr/0045-model-sees-whole-session-history.md) 的三条被否选项。

## 测试决策

**主接缝：离线图加脚本化模型加内存 checkpointer。** 跑真的中间件流水线，断言模型实际收到了什么。这次几乎全部行为都能在这里测：历史三类内容确实进了模型、旧标记被剥掉而回放里的引用仍能解析、压缩按窗口占比触发、先清后压之后工具调用与结果仍然成对、清够时不调摘要模型、摘要确实被送给模型、窗口按调用期读取。这就是既有测试文件用的那套夹子，不新开接缝。

**辅助接缝：模型客户端构造参数的断言。** 只断言构造出来的客户端带上了窗口信息，不发起网络请求；这是既有测试文件已经定下的用法。

**另有一条记录性断言必须单独钉住**：分界痕迹记的是「被折掉那一段里最后一次提问的 `run_id`」，而且第二次及以后的压缩**要沿用上一条摘要记的分界**（那一段里可能一条提问都没有）。这条痕迹事后推不出来，所以它的正确性只能靠断言发现，不能靠交付后回看发现。

**要重写或删掉的既有断言**：那条钉住「换范围时旧回答、旧工具和摘要都不进模型输入」的契约测试——它钉的正是本次要推翻的行为，改成断言这些内容**确实**进去了；以及同一文件里那两条断言「旧秘密不出现在模型输入里」「近期工具结果不出现在模型输入里」的断言。

还有一类**不在推翻之列、但同样必然变红**的：**三处靠「40 条消息」自己构造输入来逼出压缩的用例**——它们分别护着压缩后的回放结构、摘要消息的形态契约、以及用量记账；改成窗口占比之后，它们构造的那个条件不再触发压缩。要改的是**构造方式**，不是它们的断言。其中那条**钉住上游摘要消息形态**的契约测试尤其不能删：本次改动正依赖那个形态（靠一个上游私有标记把摘要从用户提问里区分开）。**改成窗口占比之后，那两个按条数的压缩常量会变成没人用的孤儿，一起删掉**；它们同时被架构文档引作压缩口径，那句要跟着改（属于交付时同步文档，不是施工步骤）。

**离线测试用的假模型必须带上窗口信息。** 用窗口占比之后，摘要中间件在**构造时**就会校验窗口存在，假模型没有它会直接抛异常——所有用假模型跑中间件流水线的用例会在构造期就红，而不是跑到断言才红。给假模型补上窗口信息是这次改动的一项前置。

**不能动的**：「不同会话之间不共享历史」那条断言，它保护的是会话隔离，与本次无关。

**什么算好测试**：断言模型实际收到的消息（可观察的外部行为），不断言中间件的内部方法、调用顺序或参数名。压缩是否触发用「摘要模型被调了几次」观察，不去读中间件的内部状态。**另外要钉住一条容易漏的：清理生效但「够用、不调摘要模型」那一支，仍然要把清理后的消息写回状态**（不能返回空、当成没发生），而这条断在「摘要模型没被调」上照样会通过，所以必须单独断言模型随后收到的旧工具正文已经是占位文字。

## 超出范围

**会话历史业务表**（[ADR 0044](../adr/0044-session-history-in-own-table.md)）。本次的清理写在 checkpoint 上，所以「用户能回看完整对话」这件事只能由它来保证——**它的实施必须与本次一起落地，不能只做其中一件**（见上面「清理影响的是模型看到的东西」那条）。

**前端分界线。** 今天画这条线是误导的：线上应当是「用户能看全、模型只有摘要」，而今天用户看不到线上那部分。

**回放接口新增字段。** 本次不加没人消费的接口字段，分界的痕迹先只落在 checkpoint 的摘要消息里。

**模型目录表、按会话选择模型、装配期那个「按运行上下文解析」的客户端包装、模型客户端缓存。** 已另立 [spec 0002](0002-model-catalog-and-user-model-choice.md)，与本次一起施工；本次只留「窗口按调用期读取」这个位置。**注意那是一件客户端包装，不是中间件**——0002 明确不新增「替换请求上的模型」的中间件，那会掉进本次「不得新增带 `before_model` 的中间件」那条硬约束。

**分级清理的加强形态**（例行清理，而不只在压缩前清）。本次只做压缩前那一步。

**给旧内容贴范围标签。** 已明确否决。

## 补充说明

模型对同一会话的记忆从「只有用户问过什么」变成「完整往来」，代价是每次调用的输入 token 明显变长，费用与延迟都会上去；压缩改用窗口占比就是给这件事设上限。另外三条已知代价记在 [ADR 0045](../adr/0045-model-sees-whole-session-history.md) 的 Consequences 里：「模型偷懒不重新检索」只剩提示词约束、而且这种失败在界面上是静默的；被压缩那段的原文细节不进摘要，模型要细节只能重新检索；窗口占比依赖近似 token 计数，上游不报用量时会偏早或偏晚。
