# 自助账号页与刷新 404 回落

## 问题陈述

老板遇到三个问题。

**一、普通账号改不了自己的密码。** 超级用户建号时设了初始密码，被建的那个账号自己永远改不掉它，只能再找超级用户代改。后端 `/auth` 下只有登录、退出和读当前账号三个接口，所有改密能力都在 `/admin/users` 下、只对超级用户开放。

**二、账号管理入口只有一个地方能进。** 通往账号管理的入口只挂在语义检索页，Agent 对话页没有。超级用户在对话页时得先退回检索页才能去管账号。老板希望「点用户信息就进管理界面」，而现在顶栏那串邮箱只是一段不可点的文字。

**三、线上刷新页面 404。** 点击跳转正常，按 F5 就白屏。原因是前端用 History 模式路由，服务器按 URL 找文件时找不到 `/admin/users` 这个文件。修法是 OpenResty 的 `try_files` 回落，仓库里没有任何配置能保证它被配上。老板已在生产环境配好并验证通过；本 spec 只补文档，不碰服务器。

## 解决方案

新增一个人人可进的自助账号页 `/account`：任何账号都能在这里看到自己的邮箱、角色和创建时间，并修改自己的密码。改密码要求输入旧密码，成功后踢掉自己在其他设备的登录、保留当前这一个。

顶栏那串邮箱变成通往 `/account` 的入口。超级用户在 `/account` 里多一个通往 `/admin/users` 的入口，Agent 对话页顶栏也补上账号管理图标入口。

`/admin/users` 这一页保持原样：它管的是别人，性质是浏览、筛选、反复操作，还带停用和降级这类破坏性动作。自助页管的是自己，一次性、低风险、改完就走。两者分开，不合并。

`docs/container_deployment.md` 补上可直接抄的回落配置，让下次重装不必重新推导。

## 实现决策

### 后端

- 新增 `POST /auth/me/password`，挂在 `auth` 路由下，依赖当前启用账号（不是超级用户）。请求体两个字段：当前密码、新密码。
- 复用既有密码强度校验（`auth/manager.py` 的 `validate_password_strength`），不另写一套规则。
- 旧密码校验失败、新密码不合强度要求，都返回稳定 code 与安全中文 detail，沿用 `api/error_contract.py` 的既有错误响应构造方式。**任何情况下不回显请求体内容**——请求体含明文密码，路由要挂 `SanitizedValidationRoute`，与 `api/user_admin.py` 同样处理。
- 改密成功后删除该账号除当前 token 以外的全部 access token。既有 `UserAdminService.revoke_sessions` 删的是某账号的全部 token，本接口需要「排除当前这一个」，因此在服务层增加一个带排除项的能力，不改既有方法的语义。
- 环境管理员调用本接口一律拒绝，返回既有的 `environment_admin_protected`。理由与 `user_admin_service.py` 里那条既有约束一致：它的凭据由部署环境托管，服务启动时会同步回去，允许自助改密会造成「改了但下次重启又变回去」这种无声矛盾。
- 契约变更后前端重新生成 `src/api/generated/openapi.ts`，不手改。

### 前端

- 新增路由 `/account`，`meta.requiresAuth` 为真、不要求超级用户。落在既有 `router.ts` 的守卫体系内，未登录会被送去登录页并带上 `redirect`，这是守卫已有行为，不新增逻辑。
- `/admin/users` 路由、`UserAdminPage.vue` 及 `features/user-admin/` 下所有组件与 composable 不改。本 spec 的前端新增物放在新的自助账号领域目录下，不塞进 `user-admin`：那一族的语义是「管别人」。
- 自助页复用 `AppShell` 外壳与 `shared/ui/` 既有基础组件（`BaseButton`、`BaseField`），不新造输入框或按钮。
- 页面只做路由级组合，请求收敛在 `src/api`、状态收敛在 `src/features/*`，遵循 `frontend/AGENTS.md` 代码约束 3。
- 表单校验规则与 `features/user-admin/model/admin-validation.ts` 是同一套（同一个后端强度校验的前端镜像），复用它，不复制。
- 顶栏那段账号邮箱由纯文本改为通往 `/account` 的 `RouterLink`。`AppShell.vue` 里那段 `.account-identity` 的既有样式与窄屏隐藏行为保留；导航入口一律用真的 `a`/`RouterLink` 而非 button，理由见 `AppShell.vue` 里 `.topbar-nav-link` 那段既有注释。
- Agent 对话页的 `navLinks` 补上账号管理项，`visible` 绑到 `is_superuser`，与检索页现有写法一致。
- 颜色只用语义层 token，不碰色阶层、不写裸色值（ADR 0007）。成功提示属于新语义：现有语义层里只有 `--danger*` 和 `--warning*`，没有表示成功的一档。优先复用 `--accent*` 表达成功，确实不够再按 ADR 0007 的规矩新增一个语义 token，不在组件里引色阶。
- 正文一律用文本插值，不用 `v-html`。

### 开发时登录预填

- 前端读 `.env.local` 里的开发用邮箱与密码预填登录表单，整段代码在 `import.meta.env.DEV` 门内，生产构建时被静态替换并摇掉。
- **不做任何跳过认证的开关。** 登录流程、Cookie、后端校验全都是真的，仓库里不存在「可以不登录」的代码路径。这是明确的取舍，见待写 ADR。
- `.env.local` 已被 `frontend/.gitignore` 忽略，凭据不进仓库。`.env.example` 里补上这两个键的说明，值留空。

### 文档

- `docs/container_deployment.md` 现有那条「必须有 `try_files` 回落」的要求下面补：可直接抄的 `location` 片段、必须排在 `/api/` 之后的顺序说明、面板伪静态预设里 PHP 方案不适用且可能与既有 `location /` 撞成 duplicate 的坑、以及「`nginx -t` 加浏览器刷新两处验证」的验证方式。
- `docs/FEATURE_MAP.md` 增加两行能力：自助改密、自助账号页。
- `CONTEXT.md` 的账号、超级用户、环境管理员三条术语已在本次会话写入，本 spec 不再改动它。

### 待写 ADR

两条，编号从 0011 起，动手前写：

- **自助页与账号管理页并存，不合并成一页。** 取舍是「一个统一入口」对「两种性质不同的操作各有其页」。合并会让超级用户每次改自己密码都要从一张长表里找到自己，正是本 spec 要解决的痛点的翻版。
- **不提供跳过认证的开发开关。** 取舍是开发便利对「一个配置错误就全站敞开且无任何报错」的风险。改用真登录加表单预填，代价是本地要保留一份凭据文件。同时记下登录会话默认 8 小时且是 Cookie，把本地时长调大即可，这个便利本身的必要性不高。

## 测试决策

好测试只断言外部可见行为：HTTP 状态码与响应体、数据库里的实际状态、用户在页面上看得见的东西。不断言函数被调用了几次、不断言内部状态形状。

四处改动全部复用既有接缝，不新增接缝：

- **`POST /auth/me/password`** 走 `backend/tests/` 的 FastAPI HTTP 测试，用 `tests/auth_helpers.py` 的依赖覆盖提供已登录账号，先例是 `tests/test_user_admin.py`。覆盖：旧密码正确则改密成功且新密码可用、旧密码错误则被拒且密码未变、新密码不合强度则被拒、环境管理员被拒、未登录被拒、其他会话的 token 被删而当前 token 仍在。

  **这一处与既有先例有一个差别要处理**：`auth_helpers.py` 里测试账号的 `hashed_password` 是一个假串（现有测试都不需要验密码），而本接口的核心行为就是校验旧密码，必须是真实哈希。用真实哈希构造测试账号，仍不做数据库 I/O，不改 `auth_helpers.py` 现有两个角色的行为以免影响既有测试。

- **`/account` 页** 走 `src/pages/*.spec.ts` 组件测试，先例是 `src/pages/UserAdminPage.spec.ts`。覆盖：自己的信息渲染、两次新密码不一致时提交前拦住、提交中按钮忙碌且不可重复点、成功提示、失败提示、普通账号看不到管理入口、超级用户看得到、任何角色都看不到停用或降级自己的控件。
- **Agent 页账号管理入口** 在既有 `src/pages/AgentChatPage.spec.ts` 里加断言，不新建文件。覆盖超级用户可见、普通账号不可见。
- **顶栏邮箱入口** 在既有 `src/layouts/AppShell.spec.ts` 里加断言。覆盖邮箱渲染为指向 `/account` 的链接。

不单独测两处，理由是它们没有独立行为：表单校验规则与 `admin-validation.spec.ts` 覆盖的是同一套规则；登录预填只在开发模式生效、生产构建里代码不存在，测它等于测 Vite。

组件层禁止裸色值由既有 `src/styles/shared-styles.node.spec.ts` 守着，本次新增样式会被它自动覆盖。

Playwright route mock 只用于隔离看样式与交互，不作为后端已更新或部署成功的依据（`frontend/AGENTS.md` 代码约束 4）。

## 超出范围

- **看和踢自己的登录会话。** 本次自助能力只有改密码一项。超级用户已能替任何账号踢会话，保底路径是通的。
- **停用或降级自己。** 后端目前不阻止，前端有事后善后逻辑，这个现状不改；这两个动作只留在账号管理页。
- **公开注册、忘记密码、邮箱验证。** 后端明确不挂载这些路由，本 spec 不改变这个立场。
- **改自己的邮箱。** 邮箱是账号的唯一标识，改它牵涉登录凭据迁移，不在本次。
- **`/admin/users` 与 `features/user-admin/` 的任何改动。** 包括排版、交互和文案。
- **深色模式。** ADR 0007 铺好了语义层但没实现，本次不碰。
- **前端体检清单里的改进项。** 那份清单单独交付，只列不做，由老板挑选后另开工。
- **OpenResty 配置本身。** 老板已配好并验证；本 spec 只补文档。仓库不产出 nginx 配置（ADR 0008）。
- **Hash 模式与构建时预渲染。** 两条替代路线均已评估并否决：Hash 模式用 URL 变丑换配置省事且与 ADR 0008 的既定前提冲突；预渲染要求为每个 URL 在构建时生成真实文件，而会话 id 是运行时产生的 UUID，构建时不可知，`/agent/:threadId` 刷新仍会 404。

## 补充说明

**改动量不对称，这是有意的。** 后端新增一个接口、前端新增一个页面，而既有的账号管理那一整族一行不动。这样切是为了让这次改动的风险集中在新增物上：出问题只影响 `/account`，超级用户已经在用的管理流程不受牵连。

**三段交付的顺序。** 第一段是文档补充与 Agent 页入口，几乎零风险，先做完可以立刻验证。第二段是本 spec 的主体。第三段的前端体检清单不在本 spec 内，只交清单不开工。

**「以前的项目没配 try_files 也能刷新」这件事没有结论。** 已排除托管平台自动回落（那个项目同样是自建 nginx 加 dist）。剩下的可能是 Hash 模式、没有子路由或用查询参数切页、或那份 nginx 配置里本来就带着这一行而当时没留意（助手认为最可能）。在那台服务器上跑 `grep -rn "try_files" /etc/nginx/` 可定案。这不影响本 spec 的任何决定，记在这里只为免得下次再翻一遍。
