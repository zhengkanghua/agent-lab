# Docling 统一文档处理与人工审核

创建日期：2026-09-08。

状态：实施中。2026-09-08，老板明确授权开启目标模式、完成本需求及测试，并分批 commit。此前仅完成规格与只读核验；后续按下方工程记录逐项推进，不将文档状态当作运行验证结果。

## 问题陈述

老板正在把项目建设为通用向量库。目前上传支持 MD、TXT，FreshRSS 提供 HTML 正文，但 Markdown 结构在提取过程中被压平，后续统一递归切分，不能可靠保留多级标题与正文之间的关系。接入更多格式后，如果解析、切分和向量化仍互相依赖具体实现，替换组件会牵动多个调用方。

当前流程也缺少原始资料留存、解析失败记录、人工审核和已采用历史。FreshRSS 的单条解析异常可能阻塞同页正常资料；来源更新会直接覆盖正文；现有单篇索引替换可能覆盖旧 Chunk，无法保证新结果失败时旧版本继续可用。

本次要同时解决结构化处理和处理结果的采用问题，让正常资料自动进入检索，异常资料可以检查、修正和重试，同时明确哪些正文已经生效、哪些仍是候选。

## 解决方案

本期接入 Docling，上传继续只开放 MD、TXT，FreshRSS 的原始 HTML 进入同一套处理能力。原始资料保存在 MinIO/S3 私有存储，处理状态、候选正文、已采用版本和审核记录由 PostgreSQL 管理，Qdrant 保存用于检索的 Chunk 与向量。

上传原件或保存人工草稿后，可靠保存资料与处理待办即返回；后台生成解析正文、标题目录和 Chunk 预览。解析报错、没有有效正文或 Chunk，以及可检测的内容丢弃等异常进入人工处理，其余结果自动进入采用流程。成功结果也可以主动复核。

人工在统一管理界面查看原件、修改 Markdown 或纯文本、重新生成预览，并选择采用或拒绝。确认采用后，后台先准备新索引，成功后才切换正式版本；准备失败时旧已采用版本继续可用。FreshRSS 新内容不能覆盖人工草稿或已采用的人工修正结果。

保留每个已采用版本、对应原始资料和审核结论，人工草稿仅保留最新编辑内容。拒绝停止资料的后续使用，管理记录保留；明确删除或符合条件的定时清理删除资料、原件、历史和索引。待审核、失败、拒绝记录不自动到期清理。

现有开发资料允许在切换时清空后重新导入，本期不建设旧正文迁移或新旧处理流程并存能力。

## 实现决策

### 1. 范围与现有契约

- 上传格式继续限定为 MD、TXT，保持现有 UTF-8/BOM、2 MiB 大小边界；FreshRSS HTML 是既有来源输入，不因此开放 HTML 文件上传。格式和大小等接收校验先完成，解码或解析失败的已受理原件进入处理记录。
- 复用现有文件上传与按 ID 替换的用户入口。老板未要求固化当前方法名、Python 签名或所有 HTTP 字段；按新处理语义调整必要契约，并同步前后端与测试。
- 文档处理能力位于 `backend` 内部，界面位于 `frontend`；两者通过 HTTP/OpenAPI 协作。解析器、对象存储、Embedding、Qdrant 均由后端访问。
- 沿用 Source 与 KnowledgeBase 的准入、停用和归属规则。审核、草稿、原件及版本管理要求超级用户；普通读取仅返回当前可用的已采用版本。
- 保留搜索结果的文档唯一性、分组数量、每篇命中数、原始 Cosine score 与排序责任，前端不通过去重补救后端混版或重复结果。
- 旧检索结果打开全文时继续比对 `content_hash`，提示其后发生的正式版本变化。保留管理历史不等于新增从 Agent 引用打开历史全文的能力，也不改写已经保存的 Agent 回答或引用片段。

### 2. 组件职责与替换边界

| 组件职责 | 输入与输出 | 实现约束 |
| --- | --- | --- |
| 资料接收 | 文件或来源条目，输出原始资料引用与持久处理回执 | 负责来源身份、归属、幂等与接收，不执行结构切分 |
| 原件存储 | 原始字节与元数据，输出可校验的对象引用 | S3 SDK 与存储地址细节留在适配器内 |
| 结构化解析 | 原始资料或编辑正文，输出正文、结构和质量信息 | Docling 为首个实现，TXT 使用保留纯文本语义的适配 |
| Chunk 生成 | 结构化结果与切分规格，输出确定的 Chunk 清单及问题 | 同时服务审核预览、自动采用、人工采用和重建 |
| 向量化 | 已确定的向量化文本清单，输出对应向量 | 复用现有 Ollama 能力；不知道来源接收、审核或数据库状态 |
| 采用与索引 | 待采用快照，输出准备结果与正式版本切换结果 | 编排版本隔离、条件确认、重试与清理，不内嵌解析算法 |
| 管理与读取 | 用户命令或查询，输出管理视图或可用正文 | 通过上述契约协作，不直接构造第三方处理对象 |

- 延续已有端口、适配器和装配方式。现有 Chunk、Embedding 抽象能复用的继续复用，补齐结构化结果、切分规格、候选索引准备与正式采用能力。
- 项目契约显式承载正文格式、内容块类别、阅读顺序、章节父子关系、标题路径及版本内来源标识；不以一个正文字符串代替全部解析结果。
- Docling 对象、异常和 SDK 调用留在对应适配器内部，由适配器负责与项目结构化结果之间的转换；第三方对象不能成为 HTTP、ORM、审核或向量化的公开输入。
- 公开方法集中维护输入、输出和错误语义；内部实现变更尽量不影响调用方。通过装配选择实现，本期不做动态插件加载、网络微服务或通用审批框架。
- 索引规格由独立数据契约描述解析和切分规则版本、tokenizer 身份、文本预算、Embedding 模型及 Payload 版本，配置不再从某个具体切分器类导入默认常量。

### 3. Docling 解析与 Chunk

- MD 和 FreshRSS HTML 使用 Docling 的文本解析路径。输入为已保存的内容，不把文章 URL 当作待下载文档；关闭图片、本地或远程引用资源获取、浏览器页面渲染、OCR 与图片模型增强。本期不为解析引入生成式模型判断。
- 官方当前实现会把 TXT 归入 Markdown 输入。TXT 应通过纯文本适配构造结构化内容，不允许 `#`、反引号或列表符号改变原有纯文本语义。
- FreshRSS 处理选定的 `content` 或 `summary`，不拼接两份正文；避免 HTML 首个标题之前的正文被当作页眉等非正文内容丢弃。现有确定性正文规范化规则保留在合适阶段，不通过压平结构来复用它们。
- 使用结构感知切分，优先尊重章节和内容块，必要时再按 token 预算拆分。保留多级标题上下文、内容顺序、代码和表格文字；同名标题不能充当章节唯一身份，不跨不同章节因正文相同而去重。
- 以 Docling `HybridChunker` 为首个实现，默认不跨不同章节身份合并。超长表格、代码或章节允许拆分；可重复必要标题或表头，但不能静默丢正文来满足预算。
- Chunk 同时保留展示正文、章节信息、实际向量化文本及其 token 数。向量化文本使用标题上下文增强，标题也计入预算；不能预览正文一种切法，采用时再独立重新切另一份。
- 对齐现有 BGE-M3 Embedding 的 tokenizer 家族，明确传入 token 上限并记录 tokenizer 版本。先以 512 token 作为本期样例评估基线，最终预算由样例与实际 Ollama 接口验证后锁定到索引规格；不沿用默认 MiniLM tokenizer 或未经核对的 `cl100k_base` 计量。
- 只为计数准备 tokenizer 资源，不因此在应用内加载 Embedding 模型权重。依赖安装和 tokenizer 首次准备的网络需求写进部署说明，不能因为文本解析不运行 OCR 就宣称依赖完全离线。
- 解析报错、无有效正文或 Chunk，以及可检测的标题或正文因预算被忽略等转人工。标题跳级、表格、合法短快讯本身不拒绝；“仅剩标题”需与有效正文区分。
- 章节定位使用版本内稳定的元素身份与关系，不能把标题文字或 Docling 的数组位置当成跨版本永久身份。不承诺 MD/HTML 原始字节的精确字符高亮。
- `content_hash` 对应正式全文所使用的那份正文；原始字节摘要、草稿修订号、解析规格和向量化文本摘要分别表达，不混成一个版本字段。

### 4. 数据与记录

采用现有 Document 主记录加三类新增业务记录的基线，物理列和索引随实现补全；不为满足“只多一张表”混合可变草稿与不可变历史。

| 数据 | 主要职责 | 修改与保留规则 |
| --- | --- | --- |
| `documents` | 文档身份、归属、当前已采用版本与实际索引实例指向、停止使用和删除状态 | 一篇资料一条主记录；首次采用前允许没有正式正文 |
| `document_processing_records` | 原件引用、来源摘要、候选及最新人工草稿、结构与 Chunk 清单、处理待办、领取与失败、候选索引准备及清理进度 | 每份需要独立处理的输入保留身份；同一人工草稿原位修订，不按每次保存生成永久正文历史 |
| `document_versions` | 已完成采用的正文、元数据、结构、Chunk 清单、原件引用，以及采用时的处理规格与索引身份 | 成功采用时创建不可变快照；重建或旧向量回收不覆盖历史正文 |
| `document_review_records` | 对目标候选及其修订的采用或拒绝决定、操作账号、时间与结论 | 追加记录；决定采用与采用执行成功分开表达，自动采用明确标记自动来源 |
| 既有删除待办 | 整篇资料的待清理范围、远端确认和失败信息 | 扩展原件与版本引用，完成前保留恢复依据；旧索引实例回收进度留在对应处理记录中 |

- 已采用版本、人工草稿与最新来源内容分别关联；一个 Document 同时存在旧正式版本、正在编辑的草稿和较新的来源候选是合法状态。
- Document 对外 `revision` 表达正式业务版本；人工草稿使用独立修订号。编辑、保存预览和来源接收不提前推进正式正文版本。
- 采用时冻结正文、元数据、Chunk 清单和处理规格。正在采用的候选只读，迟到的预览或处理结果必须按目标与修订条件确认，不能覆盖更新结果。
- 原始资料对象不覆盖写。版本引用准确的对象键、字节摘要、大小和必要的对象版本标识，不使用文件名作为唯一身份，不把 S3 ETag 一概当成原件内容摘要。
- 审核记录绑定确定的候选修订和内容摘要；编辑不会重写过去结论。已采用历史、被审核对象及尚待处理的失败资料仍保留必要依据，未被引用的中间产物才可回收。
- 后台待办直接由处理记录表达，复用现有写资源协调，不新增独立的通用任务队列表或消息中间件。

### 5. 持久接收与 FreshRSS 同步

1. 校验入口权限、文件边界或来源身份与 KnowledgeBase 准入，为本次接收确定幂等身份和不可变原件对象键。
2. 在执行对象写入前保存可追踪的接收意图，写入原始资料并核验结果；成功后在短事务中确认原件引用、处理待办和所需元数据。任何未完成接收都不能返回“已保存”。
3. FreshRSS 一页中的各条先完成原始资料接收；处理记录与 checkpoint 在同一业务事务中确认。再次锁定并检查 Source、KnowledgeBase 与预期 checkpoint，不能只依赖网络请求前的状态。
4. 原件和记录已可靠保存后，解析失败留给后台与人工处理，继续接收正常资料；任一条没有可靠保存则不得使 checkpoint 越过它。相同来源身份与原始字节摘要可以复用原件引用；复用处理候选还必须比较影响索引的元数据，标题等字段变化不能被误判为重复接收。
5. 对象写入成功但数据库确认失败时保留接收意图；后续核对或重试同一对象。对象写入结果不确定时记录待核实状态，不通过无记录的新键重试制造无法追踪的对象。

- FreshRSS 的正文质量检查从“整页保存前的解析门槛”移到持久接收后的处理阶段。无法识别条目身份、来源或续读位置的协议错误仍不盲目跳过，也不能伪造失败条目的文档身份。
- 来源原始资料和可索引元数据均相同时，不覆盖人工正文、不反复生成同一个待复核候选；仅可索引元数据变化也按独立候选处理，不能绕过人工版本保护。
- 自动管理的资料收到新内容可以按正常流程自动采用。已有人工修正、处于人工复核或明确拒绝的资料，来源更新不能自行恢复自动使用。
- 存在人工草稿时另存最新来源候选并提示更新，人工选择继续采用草稿或基于最新来源重新生成；换用来源必须是显式操作。旧已采用版本持续可用，除非被明确拒绝或删除。
- 手动同步、定时同步与文件入口调用同一接收和处理应用能力，不各自维护一套解析规则；现有一次性 Pipeline 入口应复用这些阶段并如实报告已接收、待审核与已采用数量。

### 6. 后台处理与审核状态

- 处理阶段与资料可用性分开。处理记录表达接收、待解析、解析及预览、待审核、待索引、索引准备、已完成和失败；Document 表达有无已采用版本、是否停止使用或正在删除。
- 一次正常自动处理依次完成解析、Chunk 与质量检查、冻结候选、索引准备和采用。人工草稿即使检查正常也等待人工确认，不能因为重新生成预览成功就自动采用。
- 复用现有独立 scheduler 进程承载文档待办消费器，业务逻辑和装配保持独立；消费待办不以老板手工新建 cron 配置为前提。多 worker API 只接收请求，不各自在内存重复消费同一份工作。
- 数据库条件领取和草稿修订防止重复执行结果互相覆盖。CPU 解析和 token 计算移出 HTTP 事件循环；网络调用期间不保持长事务。
- 页面关闭、刷新或 API worker 重启不取消已保存待办。尚未领取的工作继续可领取；纯计算结果可以在明确的领取代次校验下重新生成。
- 解析、切分及采用失败显示失败阶段、稳定原因和适用的重试或编辑操作，不作为正常自动采用候选无限重领。业务异常等待人工处理，与尚未处理的持久待办区分。
- 远端写入结果不确定或持久写占用所属进程失联时，沿用已有人工核实后释放的规则。不得以心跳过期为由自动抢占 Qdrant、删除或其他共享写资源；“可恢复”不等于所有中断都会无人介入地自动重试。
- 采用决定绑定已生成的最新预览及处理规格。正文或规格变化使预览失效；采用失败后的重试使用同一冻结目标，编辑修正后则产生新的待采用目标。

### 7. 索引准备、可见性与采用

- 每份冻结候选分配独立索引实例身份，Chunk ID 包含该身份与 Chunk 序号。相同目标重试幂等，不同正文或元数据版本不会覆盖同一个 Point；只加正文 hash 不足以区分元数据版本。
- 在任何候选 Point 写入前，PostgreSQL 必须已有对应索引写入意图。准备接口仅写该候选，不删除当前已采用版本；原有“按整篇替换并删除其余 Point”的接口不能直接承担候选准备。
- 候选索引准备要核验期望的 Point 身份、数量、Payload、向量维度及完整性，不能仅凭一个上传请求返回就宣布准备完成。
- 准备完成后，在短事务中核验候选修订、审核决定、当前已采用版本和删除或拒绝状态，创建已采用快照并切换 Document 当前指向。失败或条件冲突不改变旧指向。
- 新版本切换后才回收旧向量；旧正文、原件和审核历史继续保留。旧向量清理失败单独记录，不把已完成的采用反转为失败，也不允许旧向量重新参与正式结果。
- 拒绝或删除先持久改变使用资格，使其停止后续正式读取；清除向量可以随后恢复执行。来源同步不得自行撤销拒绝。
- 搜索范围仍由 KnowledgeBase 解析。检索使用版本可见性快照，在 Qdrant 查询前精确排除可能存在 Point 的未采用及已退休索引实例；不能因为资料正在更新而排除整个 Document，否则旧版本也会消失。
- 查询前的排除信息、当前采用指向以及会影响它们的修订在一致的数据库快照中读取。写入意图建立、正式采用、拒绝和删除等可见性变更必须可被查询收尾检测；避免“查询先读状态，候选随后写入”的空窗。
- 内部命中保留索引实例身份，返回前批量核验 Document 当前可用版本并检测可见性是否变化。检测到变化时重新取得状态并补查；不能把过滤后的不足数量直接当成正常最终结果。
- 分组必须在版本筛选可靠后进行一致性判定，不能先把新旧 Chunk 混为一组再由展示层过滤。一次结果仍需满足每篇同版、文档唯一、数量边界和既有排序规则。
- 可见性核验只批量读取身份与状态，不逐篇加载全文，不使用整库已采用 ID 列表拼接每次查询。排除记录在确认对应 Point 清理完成后回收，避免把全部历史永久变成查询过滤参数。
- PostgreSQL、Qdrant 没有共同事务，本期不承诺物理跨库原子提交；通过先准备、条件切换和读取校验实现用户可见规则。持续冲突或状态无法核实时给出可重试失败，不能以返回未经核验的候选降级。
- 一次读取以完成可见性校验的时刻解释；其后发生版本切换时，旧检索记录仍按现有 hash 对照提示。拒绝不撤回已经交付给用户的文本或既有会话快照。
- 本次索引与 Payload 升级到新规格。全量重建继续使用既有 generation/Alias 发布机制，只重建当前可用的已采用快照，不为每次单篇采用重建整个知识库。
- 重建复用已采用快照中冻结的 Chunk 清单及实际向量化文本，核验其与目标索引规格兼容；新的物理 generation、索引实例和实际规格由索引处理记录及当前索引指向表达，不改写采用时的历史快照，也不因此推进正文业务版本。
- 若新规则要求改变正文、章节结构、Chunk 边界或向量化文本，需从原始资料或已保存的人工正文生成候选并走正常采用流程；重建不得绕过预览和采用，静默用另一份切分结果替代已采用清单。Alias 发布与数据库索引映射不在同一事务内，发布结果不确定时沿用已有恢复规则。

### 8. 管理界面与 HTTP

- 统一管理列表覆盖上传、FreshRSS、接收失败和解析失败记录，可按 KnowledgeBase、来源种类及处理状态筛选，保留分页。不能仅依赖有文件名的 Document 查询来承载审核入口。
- 文件上传和替换入口保留。新增统一处理记录详情、保存草稿、生成预览、采用、拒绝、重试、历史查看和原件下载能力；具体路由命名在实现时集中定义，不复制业务逻辑。
- 接收或保存成功返回处理回执与可查询状态，耗时操作采用后台受理语义。客户端定时查询在途状态，完成后停止；请求超时先核对结果，不自动重复上传或重复采用。
- 桌面审核视图能对照原件与编辑结果，正文、标题目录、Chunk 和审核记录可切换；移动端使用同一资料的分视图，避免将所有面板挤在一屏。
- MD 与 FreshRSS 使用 Markdown 编辑，TXT 使用纯文本编辑；复用现有安全 Markdown 渲染能力。原始 HTML 展示为转义文本或安全视图，不能直接执行脚本或加载引用资源。
- Chunk 预览显示标题路径、正文、顺序、实际向量化文本和 token 预算情况，支持定位到对应结构内容；未知原始偏移不伪造精确高亮。
- 编辑后提示预览需要更新，后台旧结果不能覆盖新编辑。采用处理中显示冻结状态，失败后允许针对失败阶段重试或修正。
- 来源更新与人工草稿同时存在时展示明确状态，换用最新来源会替换当前草稿，必须由用户发起；仅打开原件或预览不代表采用或拒绝。
- 拒绝操作明确说明会停止整篇资料使用，不能让用户误以为只是关闭一个新候选；明确删除则清除原件与全部文档历史，两者分别呈现。
- 保存草稿、采用、拒绝、替换和删除携带目标修订，冲突时返回稳定错误并刷新可用状态，不静默覆盖其他修改。界面保留可恢复的本地编辑内容供用户处理冲突。
- HTTP 错误继续使用集中脱敏契约，日志不输出正文、原始 HTML、对象凭据或完整第三方响应；OpenAPI 变更后同步生成前端类型。

### 9. MinIO/S3 与删除

- 使用私有桶或项目专属前缀，环境之间隔离；原件下载经后端权限检查，浏览器不接收 S3 密钥、不直接连接存储管理服务。
- 原件读写接口集中提供保存、读取、核验和删除能力，采用官方 S3 兼容 SDK 的适配器实现。配置包括 endpoint、bucket、region、寻址方式及服务端凭据，实际名称由实现统一确定。
- 对象键不可变，应用管理文档版本；部署优先使用不启用对象锁的存储范围。若桶开启版本控制，必须记录并删除具体对象版本，不能把新增删除标记当作物理清除全部原件。
- 不使用会越过应用保留规则的桶级到期清理删除在用原件，否则会违反待审核、失败和拒绝记录继续保留的要求。
- 明确删除先记录删除意图并停止使用，冻结目标以阻挡同步、预览或采用重新写入；随后删除其全部索引实例和被引用原件，逐项保存确认，最后条件清理业务记录。
- 原件被同一 Document 的多个版本引用时按实际引用集合删除；不能删除仍由其他保留记录使用的对象。本期不新增跨 Document 全局内容去重。
- 定时清理保持既有 KnowledgeBase 范围和日期基准：有发布日期取发布日期，否则取首次创建时间。仅选择已采用且完成索引、没有待审核或失败候选且未被拒绝的资料；不因旧版本到期连同待处理内容删除。
- 整篇删除覆盖原件、草稿、已采用历史、审核记录及向量。删除失败保留独立待办，可以重试已经开始的清理；任务历史裁剪不能删除未完成的恢复依据。
- 接收意图、候选准备和索引回收均须能定位本次创建的对象或 Point，不通过宽泛的桶清空或 Collection 删除来处理单篇失败。

### 10. 开发资料重置与交付边界

- 老板已允许现有开发资料清空后重新导入，实施阶段不再建设历史正文回填。清空范围为本项目文档数据、对应索引与确有必要重置的来源续读位置；保留账号、KnowledgeBase、Source 绑定、任务配置和 Agent 会话等无关数据。
- 实际操作前核对目标环境、文档资源范围和写入停止状态，列出预演结果。现有授权不能解释为删除整个 PostgreSQL 实例、共享桶或其他项目的 Qdrant Collection。
- 新 schema、处理消费者、对象存储配置、tokenizer 资源和新索引规格准备完成后才执行切换；避免旧写入口与新版本规则混跑。
- 重置 checkpoint 后沿用 FreshRSS 既有首次同步与分类范围，不扩大成抓取全部历史资料的平台。重新导入数量和可取得范围在切换记录中说明。
- 源码、依赖、迁移、前端契约和部署说明需要一起更新，但本 spec 编写不执行这些动作。MinIO/S3 尚未接入，具体配置由老板部署时提供，凭据留在服务端环境。

## 测试决策

### 主要测试入口

以用户可观察的文档生命周期作为主要验收入口：通过管理 HTTP 接收原件或保存草稿，由实际处理应用消费待办，再通过处理状态、预览、正式检索和全文读取断言结果。FreshRSS 使用同一应用能力，外部源可替换为固定条目；不为每层私有方法建立独立测试接口。

老板已授权助手自行准备样例。优先复用现有文件资料生命周期、FreshRSS 增量同步、索引写入、搜索分组、定时清理和前端文件管理测试结构。解析算法与多存储恢复具有独立失败风险，需要少量直接验证，不用界面模拟结果代替实际组件能力。

### 必须覆盖的行为

| 验收组 | 场景 | 可观察结果 |
| --- | --- | --- |
| 结构解析 | MD 多级、同级、跳级、重复标题，标题后回到上级，长章节 | 标题归属正确，正文不被孤立标题替代，不跨同名章节误合并 |
| 内容块 | 列表、引用、围栏代码、表格、超长表格行、混合中英文 | 内容顺序与必要上下文保留，超限拆分或异常可见，不静默丢弃 |
| TXT | 含 `#`、反引号、列表符号、BOM 和不同换行 | 保持纯文本语义，原件字节可下载核对 |
| HTML | 无标题片段、先正文后标题、实体、列表与表格 | 首段不丢失，不抓取外部图片或本地文件，不拼接 content 与 summary |
| 异常处理 | 解码或解析报错、仅标题、空结果、标题预算耗尽 | 原件与失败记录保留，进入人工处理，不生成正式可用版本 |
| Token 预算 | 标题上下文很长、正文很长、BGE-M3 tokenizer | 实际向量化文本整体不超过锁定预算，预览与采用清单一致 |
| 持久接收 | S3 写入失败、写成功但数据库确认失败、重复请求 | 不虚报保存成功，恢复能定位同一对象，不产生不可追踪孤立数据 |
| FreshRSS | 一页混合正常和异常条目，重复同步 | 已保存原件的解析异常不堵塞正常资料，接收失败不推进 checkpoint |
| 来源元数据 | 正文不变但标题、标签等可索引字段变化 | 原件可以复用，仍产生正确候选，不绕过人工版本保护 |
| 人工版本 | 来源重复、来源新内容、编辑中收到更新 | 人工正文与草稿保留，新内容另列，换用必须显式操作 |
| 草稿并发 | 两个编辑者、旧预览迟到、保存后采用旧预览 | 冲突可见，不覆盖较新草稿，不采用失效预览 |
| 采用成功 | 旧版可用，新索引准备并核验成功 | 切换前旧版可用，切换后新正文与新 Chunk 一致 |
| 采用失败 | Embedding 失败、Qdrant 部分写入、确认失败 | 旧版始终可用，候选不泄露，失败有可恢复记录 |
| 查询并发 | 查询前后发生候选写入、采用、拒绝、删除或旧 Point 清理 | 不混版、不泄露、无错误的名额丢失，必要补查或明确可重试失败 |
| 首次采用 | 无旧版本，解析成功但索引尚未完成 | 管理可见，普通全文、检索和 Agent 暂不可用 |
| 拒绝 | 拒绝已采用资料，随后来源更新和索引重试 | 后续读取停止，管理记录保留，不被自动恢复 |
| 历史 | 多次采用、反复保存草稿、旧向量回收 | 已采用正文与审核结论完整，草稿不按每次编辑永久累积 |
| 全量重建 | 同一已采用快照重建新 generation，或目标规格要求改变 Chunk | 兼容重建不改历史；改变清单必须走候选采用，不能静默重写预览依据 |
| 明确删除 | 原件、多个版本和索引存在，任一删除阶段失败 | 最终全清，失败可恢复，不提前丢失对象引用或删除无关资料 |
| 保留期 | 指定库、日期边界、无发布日期、待审核/失败/拒绝 | 沿用日期规则，只清理合格资料，保护待人工处理内容 |
| 后台恢复 | API 重启、消费者重启、领取冲突、远端写入不确定 | 已受理记录不丢，旧结果不误覆盖，保留人工恢复边界 |
| 权限与读取 | 未登录、普通账号、停用库、越范围请求、恶意原始 HTML | 管理和原件权限有效，普通读取只见已采用结果，脚本不执行 |
| 现有功能 | 文件替换、知识库范围、Agent 引用、分组排序与重建 | 本期未调整的公开行为继续成立 |

### 验证层次与先例

### 技术验证顺序

1. 先完成 Docling 文本输入及结构切分验证，锁定依赖和 tokenizer 资源，证明多级标题、TXT 语义、HTML 首段和预算规则可满足。
