# 模型目录与用户可选模型

## 问题陈述

平台只有一个模型：上游地址、凭据和模型名全部写死在部署环境变量里，进程启动时构造一个客户端，失败时降到一个同样写死的备用模型。用户没有任何选择；超级用户想接入一个新的模型来源，要改部署配置并重启；某个上游整体不可用时，平台只能靠那个备用模型兜底，而那次调用的内容会顺着用户没选过的另一个上游发出去。

用户要的东西很朴素：**自己能挑一个模型来用**。

## 解决方案

平台在后台维护一个模型目录——若干**上游渠道**（显示名、接入类型、地址、凭据），每个渠道下面挂若干**可用模型**（上游模型名、展示名、上下文窗口）。用户在会话里挑一个用，没挑就用标着默认的那一个。凭据在后台填一次、加密入库，读取接口永不返回它。

备用模型整个删掉：用户既然能自己换模型，平台就不必再替他兜底换一个上游。

## 用户故事

1. 作为使用者，我想要在一个会话里挑选用哪个模型，以便按自己的需要选。
2. 作为使用者，我想要我选的模型被这个会话记住，以便下一次提问不用再选一遍。
3. 作为使用者，我想要在提问前换一个模型，以便从这一轮起都用它、下次打开这个会话仍然是它。
4. 作为使用者，我想要没选模型时有一个可用的默认，以便我不必先选才能提问。
5. 作为使用者，我想要在同一个会话里前后几轮用不同模型，并且回看时能看出每一轮用的是哪个，以便我知道那条回答是谁给的。
6. 作为使用者，我想要我选的模型不可用时得到一句能照着做的话（换一个模型），而不是一句「服务端的配置需要维护」，以便我自己就能走出去。
7. 作为使用者，我想要在我选的模型失效之后会话里**如实**告诉我「原来的模型已不可用，请重新选择」，而不是悄悄把我换到别的模型上，以便我知道自己现在用的是哪个。
8. 作为使用者，我想要选择列表里出现的都是能用的模型，以便不必靠试错。
9. 作为超级用户，我想要在后台新增一个上游渠道（显示名、接入类型、地址、凭据），以便接入新的模型来源。
10. 作为超级用户，我想要在一个渠道下面挂多个模型并给每个填上下文窗口，以便一个凭据覆盖多个模型、而历史压缩能按各自的窗口算。
11. 作为超级用户，我想要凭据只在我填写时以明文出现一次、之后任何读取接口都不返回它，以便它不会顺着界面或日志泄漏。
12. 作为超级用户，我想要编辑渠道时留空就表示不改凭据，以便改地址时不必重新输入密钥。
13. 作为超级用户，我想要停用某个模型或某个渠道，以便出问题时能立刻把它从可选列表里拿掉。
14. 作为超级用户，我想要在停用正被当成默认的那个模型时被拦住，以便不出现「默认模型不可用」这种状态。
15. 作为超级用户，我想要停用一条渠道时它下面的模型一起不可用，以便不必逐个去关。
16. 作为超级用户，我想要把某个模型标成默认，以便没选模型的会话有一个确定的去处。
17. 作为超级用户，我想要改完一条已有配置不必等重启，以便修错了能马上改回来。
18. 作为超级用户，我想要新建一个模型之后用户立刻就能选到，以便不必等一个生效周期。
19. 作为维护者，我想要每条被用到的模型只构造一次客户端并被复用，以便不为每次模型调用付一次连接池与 TLS 握手的钱。
20. 作为维护者，我想要删掉备用模型这条路径连同它的配置项与部署变量，以便不留一个看起来还在起作用、实际已经没用的开关。
21. 作为维护者，我想要用量记录里记的是上游模型名，以便账本和上游账单对得上。
22. 作为维护者，我想要配错的模型不阻断保存，以便上游抖动时超级用户仍然改得动配置。
23. 作为维护者，我想要历史轮次里显示的模型名是当时那个名字的快照，以便条目后来改名或停用不会改写历史。

## 实现决策

**两张新表。** 上游渠道：显示名、接入类型（决定用哪个客户端类）、地址、凭据（密文）、启用状态（新建默认启用）、时间戳。可用模型：所属渠道、上游模型名、展示名（可空，缺省回落到上游模型名）、**上下文窗口（必填、不允许留空，新建表单预填 32768）**、是否默认、启用状态（新建默认启用）、时间戳；同一渠道内上游模型名唯一。渠道与模型之间是**业务层维护的逻辑外键**，库上不建约束；上游渠道停用时它下面的模型一起不可用，**不逐个改模型的启用位**（两份状态必然漂移）。**后台的管理接口沿用既有的超级用户权限门**（和知识库、来源、账号那几处是同一道），不新开一档权限。

**默认值的唯一性**：后端在同一事务里先把其它行的默认标记置假、再把这行置真；库里另建一个**部分唯一索引**兜底并发。索引不属于「不建外键约束」那条限制。**默认标记只能被「把另一条设为默认」这一条路径改写**：请求直接把当前默认的标记置假要拒绝——否则「有可用模型、却没有默认」这个被声明为不可达的状态就可达了（自动补默认只挂在「某条变为可用」这个事件上，不会被触发），而那一刻「会话没选模型」的提示与「当轮窗口值取哪一条」都没有定义。**并发落败的那一方返回一个明确的冲突错误让超级用户重试**，不静默重试、也不自动改选一个默认。

**不变量：目录里只要有「自身启用且所属渠道也启用」的可用模型，就恰好有一个默认。** 下面几条规则合起来维持它，把能走到「有可用模型但没有默认」或「有一个不可用的默认」的路径都堵上：

- **新建时不允许给一个不可用的模型打默认标记**（自身启用、所属渠道启用两个条件都得满足）。
- **目录里还没有默认时，第一条变为可用的模型自动成为默认**——「变为可用」包括新建时就是启用的、后来被置为启用的、以及**所属渠道被启用之后它跟着变得可用的**；所以「先建停用的渠道、在里面建启用模型、再启用渠道」这条路也不会漏出空档。**同一批里有多条同时变为可用时，取最早添加的那一个**（按添加时刻，同一时刻按 id）——「先添加的先当默认」是管理员能预期的规则；不写这一句的话默认会落到哪个模型上取决于实现者怎么排，而用户没选模型时拿到的就是那一个。

**窗口这个数填错了两个方向都有后果，页面上要说清。** 填大了：请求可能超过上游的真实窗口、整轮以失败收尾。**填小了不是无害的**——它同时是两件事的分母：压缩什么时候触发（按它的比例算），以及**一轮里单次工具输出能放多长**（上下文策略那次改动定为它的 20%，封顶 20000 字符、保底 2000 字符）。所以表单里要提示「填你确认过的最小值」，而不是「保守就行」。
- **把某个模型设为默认时，它必须当前可用**（自身启用、所属渠道也启用）。
- **默认模型自身、以及它所属的渠道，都不允许被停用**（渠道停用会让它下面的模型一起不可用，把默认一起带走）。
- **可用模型的所属渠道可以改，但改后必须仍可用**（目标渠道处于启用状态），否则拒绝——否则「把默认改挂到一条停用渠道下」会绕过上面几条。

于是这个状态不可达，spec 不必再为它定义错误码；实现者也不用在两个都跑得通的做法里挑（一种是静默换到别的模型，正是 ADR 0046 否决的事）。真正需要**面向用户的文案**的只剩两类：**目录为空或全部停用**（用户没法自救，文案指向超级用户）与**这一轮选中的模型不可用**（用户自己能换，文案告诉他换一个）。后者按请求里给的 id 存不存在分映射 404 与 409，但**文案只有一条**。

**只停用，不删除。** 与知识库的「停用保留数据」一致。选过某个已停用模型的会话**不改动数据、只如实提示**：选择器读到那个 id 已不可用，显示「原来是 xxx，该模型已不可用，请重新选择」。

**会话侧**：会话表加一列「当前选择的模型」（可空，逻辑外键）。为空表示用默认模型。它的写入与读取都照会话知识库选择那一套。

- **两条写入路径，都落到同一列**：选择器一改就保存（走一个专门的保存接口，照知识库选择那条既有路径，运行中改选也照样保存），提问请求体里带的那份也写回会话行。即「改了就是记住」——不存在「只对这一次」的单次覆盖。**保存这一步不校验模型当前可不可用**（否则同一个失效选择会有两条不同的提示）；可用性只在「开始运行之前解析」那道门上判。
- **每轮实际用的那一份要冻结下来**，位置与范围快照**同一个口袋**：提问消息的附加字段里（范围快照今天就写在那里，回放按它逐轮读出）。快照**连展示名与上下文窗口一起存**——窗口在运行期要用（压缩按它算），而接手续跑那一轮**不许回查目录**（目录可能已经被改过），所以它必须跟着冻结；照知识库展示快照「改名后不改写历史记录」的做法：条目后来改名或停用，已经发生过的那几轮显示不变。
- **读回来有两处**：一是回放逐轮读出并经回放接口暴露（像每轮的范围那样），前端在轮次上显示「本次模型：xxx」；二是运行被排空、由别的进程接手时重建上下文也要读同一个地方——否则接手那一轮会悄悄改用当时的默认模型，正是「不静默换模型」要禁的。**快照里的模型在部署排空期间被停用时，仍旧用它跑完**——接手路径（从提问消息的快照重建运行上下文）不过「开始运行之前解析」那道 HTTP 门，那道 409 兜不住它；这一轮的用户是带着那个模型开始的，接管是平台内部的事，不该在中途给他换一个（要停止那次运行，就停用整个会话或让上游自己失败）。

**选择在开始运行之前解析**，与知识库范围同一条路径：失败走 HTTP 状态码而不是流里的事件，并保证模型一次都没有被调用。**只校验这一轮实际生效的那一份**（请求里给了就用请求的，没给才用会话里存的），另一份失效不影响这一轮。**可用性判定直接读目录表，不经过客户端缓存**——否则刚停用、刚下线的模型最多还能被选中 60 秒，而故事 13 要的是「立刻拿掉」。请求里给的 id 在目录里不存在映射 404；这一轮实际生效的那个模型已停用（含所属渠道停用）映射 409。

**模型配置的唯一事实源是目录表。** 环境变量里那几项（接入类型、地址、凭据、模型名）**退休**、不再被任何代码读取；温度、超时、UA 仍然从环境变量读，因为它们不属于「某一个模型」。**升级走清空既有会话 + 由超级用户在后台重新配置**（见「补充说明」那节）——所以不需要「把环境变量搬进目录」的一次性初始化命令，那会留下第二份事实源。**渠道凭据允许为空，但只在接入类型本来就不需要凭据时**（本地自托管那条路径今天就不需要）。接入类型要求凭据而凭据为空时，**保存被拒绝**——否则这条渠道会在第一次被选中时以「构造期失败」的形态炸出来，而那个失败不属于任何已有的错误码，用户只能拿到一句没法照做的服务错误。编辑时「留空 = 不改」的规则与它配套：把一条没有凭据的渠道改成需要凭据的接入类型，必须在同一次保存里把凭据补上。其余进程级参数（温度、超时、UA）仍从环境变量读，因为它们不属于「某一个模型」。**目录为空或全部停用时提问返回一个明确的错误码**（照既有「没有启用的知识库」那一条的形状），不退化成 500、也不回头去读环境变量兜底——那会造出第二个事实源。

**模型替换由装配期那个「按运行上下文解析」的客户端包装完成，不新增中间件。** 交给图的客户端是这样一个包装：装配期它不读环境变量、也不发请求（所以目录为空时进程照样起得来）；每次调用时它从**当前运行的上下文**里取出当轮选定的客户端并转交过去（模型层够不到请求对象，但能通过运行时上下文拿到当前运行——用量采集就是这么拿账号与会话的），取不到（没有选择、目录为空或全部停用）就明确失败，**绝不静默拿一个没人选的模型去回答**。解析读的就是运行时上下文，它本身按协程隔离；**不要把值挂在包装或中间件的实例上**，图是进程共享的，两个会话用不同模型时会互相覆盖。这样也就不需要任何「替换请求上的模型」的中间件——顺带避开新增带 `before_model` 的中间件的风险。**摘要那一次调用也跟随会话模型**：摘要中间件构造时拿到的是同一个装配期对象（同一条包装链），所以它每次调用解析到的也是当轮选定的客户端；窗口值另由覆写「取窗口」的方法提供（见 [0001](0001-model-sees-whole-session-history.md)）。「运行中不压缩」那条既有守卫继续保证摘要那次调用拿到的是当轮那个模型。

**客户端构造**：一行渠道就是一份现成的模型配置对象，直接交给现成的客户端构造函数——客户端这一层不新造抽象。**缓存以模型 id 为键**：未命中就查库（所以新建的模型立刻可用），命中后信任 60 秒，超时只重新校验那一行的内容，内容没变就继续复用同一个客户端；**行没了或内容变了就重建或淘汰，而「只是被停用」要保留**——接手一条在途运行还要用它跑完（停用后的模型不会再被新的选择解析到，那道门会先拦住）。判断「内容没变」要比的字段：地址、接入类型、凭据、上游模型名、上下文窗口。

**凭据闭环**：后台表单里明文提交一次，后端加密落库；读取接口只回「已配置 / 未配置」；编辑时留空表示不改。明文不写日志、不进 `repr`、不进异常消息。主密钥从环境变量读。

**删掉备用模型**：整步中间件、`fallback_model` 配置项与部署变量一起清掉。重试保留；重试中间件的失败行为必须继续显式写成向上抛，因为外面已经没有兜底再拦一道，写成默认值会让失败伪装成成功。

**压缩那一次调用跟随会话选的模型**：压缩比例乘的是所选模型的窗口，用另一个模型做摘要等于拿两把尺子量同一件事。

**用量记录不改**：记的仍是上游模型名（今天那一列就是这个），用量页显示的就是这一列，**不做「反查当前展示名」**——账本记什么就显示什么。轮次里显示的模型名是当时的快照，与用量页可能不同，但那两件事问的不是同一个问题：一个问「当时叫什么」，一个问「花了多少」。

**从目录构造出来的客户端要经过既有的用量采集包装，而且整条链只包一次。** 采集是靠把客户端包一层实现的，模型名与用量都从被包的那个客户端上读：中间件若把一个未包装的客户端塞进请求，账本会静默少算，而且现有测试变不红；反过来重复包又会让摘要那次调用被记两条。层次见下面「包装层次」那条。

**包装层次要写死：用量采集那层在最外面，解析包装在它里面。** 采集靠被包对象读模型名与用量（它会把窗口值按值拄下来，因为那是字段、做不成委托属性），所以**塞进图里的必须是包过采集的那个解析包装**——塞一个没包过的，主模型那一路的调用会一条记录都不进账本，而且静默。目录客户端与解析包装都不再重复包采集，否则摘要那次调用会被记两条，破坏「每次调用恰好一条记录」。**解析包装要把可观测属性委托给当轮解析到的客户端**，至少 `model_name`、`model`、`profile` 与 `_get_ls_params` 这几项——账本取模型名走的正是 `_get_ls_params`，不委托这一列会静默变成缺失，而列出的必测失败路径里没有一条能发现它（上游包装类自己的模块说明已经把「可观测属性必须逐项手工委托」写成了规矩）；`profile` 也在清单里，因为装配期的摘要中间件构造校验读的正是它。运行期真实窗口也不能依赖采集那层拄下来的字段，由 0001 那条「覆写取窗口的方法」提供。

**前端**：选择器与后端共用同一份事实。会话列表与选择器加载后是有缓存的，**选择器每次打开时重新拉取目录**，否则用户会看到一个刚下线的模型、或者刚建的模型迟迟选不到（故事 18 要求「立刻就能选到」，所以要一个可验收的拉取时机，不能只写「能重新拉取」）。选择器遇到「当前选择指向一个已停用或不存在的模型」时，显示失效态与重选入口，**不静默回落到默认模型**。凭据表单里留空表示不改凭据，不要把它当成「清空凭据」。

**错误处理**：保存时不试调、不校验模型支不支持工具调用。新增**两条**面向用户的文案（与上面「不变量」那节的两类一一对应）：「当前没有可用的模型，请联系管理员配置」与「你选的模型已不可用，请换一个模型再提问」——后一条覆盖选择解析失败的两种状态码（404 与 409），文案只有一条。另外给「上游说没有这个模型」和「上游认证失败」两条既有文案补上「请联系管理员，或换一个模型试试」——只改文案，码与行为不动。前端新增码时两边一起改。

## 测试决策

**接缝一：HTTP 层。** 管理侧的增删改查与凭据不回显、会话侧的选择与覆盖，都在这层测。先例是既有的知识库管理接口测试与账号偏好接口测试；选择失效那条照既有的「范围失效」测试形状写——**断言失败发生在开始运行之前，且模型一次都没有被调用**。

**接缝二：离线图加脚本化模型。** 断言模型实际收到了什么、窗口值是否跟着选择变，用既有那套夹子，不新开接缝。

**接缝三：前端组件测试。** 用户故事 1～8 全是界面行为——会话里挑模型、提问前临时换、选择失效时提示重选、后台表单填凭据——要在前端已有的测试夹子里覆盖（页面级与 feature 级的 `.spec.ts` 都有先例）。至少覆盖两处最容易做错的：**选择器的失效态**（当前选的模型已不可用时显示「原来是 xxx，请重新选择」，而不是静默回落）与**凭据表单的留空语义**（留空 = 不改，不是清空）。

**什么算好测试**：断言对外可观察的行为，不测实现细节。凭据那条断言「读取接口不返回密钥」，不要去断言密文的形状或者加密算法的细节——那会把测试钉在实现上，将来换加密方式就红。缓存的断言用「第二次用同一个模型时客户端被复用了」这类可观察事实，不要去看缓存字典。

**必须覆盖的失败路径**：停用正被当默认的模型被拒；停用渠道之后它下面的模型一起不可选；把默认模型改挂到一条停用的渠道被拒；选择里给了不存在的 id 与给了已停用的 id 各自的状态码；两个请求同时设默认时不会出现两个默认。

**不动的**：会话隔离那条既有断言，以及「不同来源的调用各记一条用量」那组断言——备用模型删掉之后它们仍然成立。

**删掉备用模型后必然变红、要一并改或删的既有用例**：主备共享设置那条构造断言、离线图夹具上那个备用模型参数、系统装配处的假设置、以及用量与运行时集成测试里几处带备用模型的配置。这些会在删掉配置项的同时直接报错（不会静默走错），但要在同一个改动里一起清掉，否则剩下来的那一半会长期红着。

## 超出范围

- **按账号分配可用模型**。目前所有账号都能用全部启用的模型；将来真需要再补关联表。
- **从上游动态拉取模型名**。模型名由超级用户手填；上游的模型列表接口在绝大多数兼容实现里也不给上下文窗口，拉回来仍然要人补。
- **模型能力标签与成本提示**（视觉、上下文长短、免费/付费）。用户只是选模型，不显示这些。
- **健康度探测与自动摘除**。配错或上游挂了靠错误码如实告知，不做探测。
- **配额与限流**。平台凭据的调用不对账号限额。
- **删除条目**。只提供停用。
- **保存时试调**（理由见 ADR 0046：启动时对模型的自检已经被移除过，保存时试调是同一类东西）。

这份 spec 与 [0001](0001-model-sees-whole-session-history.md) 一起施工：0001 里「窗口值按调用期读取」那条的来源由本 spec 决定（可用模型条目上的窗口值），0001 已经同步改过。两份 spec 各自独立验证，交付时各自删除。

已知代价记在 [ADR 0046](../adr/0046-model-catalog-and-user-model-choice.md) 的 Consequences 里，其中最容易在验收时被忽略的是三条：平台不再有兜底渠道；配错的模型只会在有人用到它时才暴露；停用一个模型会表现为「一批会话被打开时提示重选」，而不是自动修复。

**这是一次要清空既有数据的升级**——目录取代了环境变量里那份唯一配置，而改动之前建立的会话里没有模型快照。清空的具体动作与升级顺序写在 [spec 0003](0003-session-history-in-own-table.md) 的补充说明里：那是同一次升级，三份改动一起落地、一次清空，不在这里重写一遍。
