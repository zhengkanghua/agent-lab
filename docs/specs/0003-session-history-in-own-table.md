# 会话历史落业务表

## 问题陈述

用户能回看的对话，今天是从 LangGraph 的 checkpointer 里读出来的。而压缩是破坏性的——它把当前状态里的早期消息整批删掉、换成一条摘要，所以被压掉的那些轮次**在界面上真的没有了**，界面今天那句「较早消息已压缩，原始问答不再提供回看」是实话。

这带来两件不该有的事：用户能查到什么，被模型的上下文预算牵着走；而回放这种「给用户看的记录」的读取路径，绑在一个归上游所有、会随压缩重写、还会被运维命令整体删掉的状态存储上。

## 解决方案

会话历史搬进我们自己的一张业务表，**一条消息一行**，界面从此读它。checkpointer 退回它本来的角色——只存模型看到的那份上下文记录，压缩怎么改都与用户看到的东西无关。

压缩仍然发生（模型需要它），但它的痕迹变成界面上一条分界线加一句实话：**线以上的对话，模型只保留摘要；线以下的，模型保留完整的问答与工具轨迹**。用户看到的原文永远是完整的。

**但「完整保留」对工具原文不总成立，这句话不能写成那样。** 上下文策略那次改动会在压缩**之前**先清一遍较旧的工具原文（清够了就不做摘要）——所以：一次压缩可能根本没发生、分界线也不动，而较旧的工具原文已经在**模型那一侧**被换成占位文字；那些轮次就落在分界线**以下**。所以界面那句话**只讲模型那一侧保留什么**：线以上只剩摘要；线以下保留完整问答与轨迹，但较早的工具原文可能已被清理成占位文字。**用户那一侧不受影响**——回看读的是这张业务表，它在收尾时写下、此后永不清理。不能让界面承诺模型做不到的完整性，但也不必把模型侧的限制写成用户侧的损失。

决策记录见 [ADR 0043](../adr/0043-session-history-outlives-summary.md)（会话历史不随摘要缩减）与 [ADR 0044](../adr/0044-session-history-in-own-table.md)（会话历史落业务表，checkpointer 只管上下文记录）。

## 用户故事

1. 作为使用者，我想要在界面上回看到一次会话的全部轮次，不管中间压缩过多少次，以便我核对我说过什么、它答过什么。
2. 作为使用者，我想要压缩之后早期轮次的原文仍然逐字可看，以便我指着很久以前那句话继续追问。
3. 作为使用者，我想要工具调用与工具返回的内容也留在记录里，以便我知道早期那些回答当时查没查资料、查了什么。
4. 作为使用者，我想要在时间线上看到一条分界线，以便我知道模型从哪一轮开始只剩摘要、哪些内容它可能记不清。
5. 作为使用者，我想要分界线上那句话说的是实话——既不让人以为记录丢了，也不承诺模型保留了它其实已经清掉的东西，以便我不会把「模型忘了」误当成「界面坏了」。
6. 作为使用者，我想要点开引用时看到这篇文档、它的版本与来源，并能看出正文改没改过，以便我核对结论的出处。
7. 作为使用者，我想要每一轮的记录里带着当时的范围和当时用的模型，以便我知道那条回答是在什么设定下产生的。
8. 作为维护者，我想要回放的读取路径彻底离开 checkpointer，以便压缩策略、checkpoint 的保留策略将来怎么改都不影响用户能看到什么。
9. 作为维护者，我想要写入只发生在运行收尾那一刻，以便不用处理运行中途的半截状态。
10. 作为维护者，我想要写入按「会话 + 运行」整组替换，以便收尾被执行两次也只写一份。
11. 作为维护者，我想要一次运行被停止、上游失败、被放弃、被别的进程接手这几种收尾都写进同一张表，以便用户看到的每一轮都是完整终态。
12. 作为维护者，我想要这张表不建外键约束、删会话时由业务层在同一事务里连带删除，以便和仓库既有约定一致。
13. 作为维护者，我想要这张表和会话行一起被删掉，以便不留下查不到也删不掉的孤儿记录。

## 实现决策

**表是消息级的。** 一条消息一行；**轮次不是数据，是读的时候按运行组装出来的视图**，不落库。唯一的细化：助手消息带来的**每一个工具调用各占一行**、**每一个工具结果各占一行**，不把工具调用挂成助手行里的一段 JSON——工具结果本来就要单独成行，调用跟着独立成行才能按调用 id 配对（并发工具调用的返回顺序不保证，靠顺序配对是错的）。

**列**（表名 `agent_thread_messages`，列名照这个语感定）：

| 列 | 语义 |
|---|---|
| `id` | 主键 |
| `thread_id` | 会话归属，逻辑外键（库上不建约束） |
| `run_id` | 这条消息属于哪一次运行；**切分与组装都靠它** |
| `seq` | 会话内递增的顺序号，读的时候按它排序 |
| `role` | `question` / `answer` / `tool_call` / `tool_result` / `summary` |
| `text` | 正文（提问、回答、摘要、工具结果的返回内容都放这里） |
| `tool_name` | 只有工具调用行有 |
| `tool_arguments` | 只有工具调用行有 |
| `tool_call_id` | 工具调用行与工具结果行各自的配对键 |
| `failed` | 只有工具结果行有，表示这次调用失败 |
| `evidence` | 该次工具结果的证据块：**该次调用实际使用的范围**（模型可以在本次范围内再收窄，事后推不出来，而界面上那条「实际范围：…」读的就是它）+ 引用证据（文档归属、正文版本、来源）；只有工具结果行有（正文片段与「是否截断」两个字段随上下文策略那次改动一起删掉，不再列） |
| `run_meta` | 运行元数据：当时的范围快照、是否完整作答、**当时用的模型（含展示名与上下文窗口）**；只有该运行的提问行有 |
| `memory_boundary_run_id` | 压缩边界标记；**只有摘要行有** |
| `created_at` | 写入时刻 |

`role` 把移交说明里的「工具」拆成 `tool_call` 与 `tool_result` 两类——因为两者各占一行，用同一类角色会把「这一行是调用还是结果」变成隐含状态（靠哪个列非空去猜）。正文为空串的助手消息不单独成行（它对回放没有贡献，回放本来就是把这轮所有助手正文拼起来）。摘要行存正文但界面不展示它，它这一行存在的意义是**承载分界标记**。

**顺序号取消息在快照列表里的位置。** 消息对象身上有个 id，但那是 checkpointer 落盘时赋的随机 UUID、不是单调序号，现有代码从头到尾靠的都是消息在快照列表里的下标。所以 `seq` 就是「写入时消息在快照列表里的位置」换算成**会话内递增的整数**：从该会话已有的最大 `seq` 加一开始、按消息在快照里的先后逐个加一；读的时候只按 `seq` 排序。整组替换时按同样顺序重排，相对次序不变。

**运行元数据带上当时用的模型。** 范围快照、是否完整作答是原有的；模型那一项是模型目录那次改动新加的（每轮实际用的是哪个模型，连展示名一起冻结进提问消息的运行元数据）。这一列要一起装它，否则回看里那句「本次模型：xxx」就没了。

**压缩留痕**：摘要行带「压到哪一轮之前」的标记，记的是**被折掉那一段里最后一次提问的 `run_id`**——语义是「这一轮及其之前的轮次，模型只剩摘要」。如果被折掉的那一段里一条提问都没有（第二次及以后的压缩可能出现），**沿用上一条摘要的标记**，让这条痕迹跨多次压缩延续下去。

**写入点只有一个：运行收尾。** 在「把已产出但还没落库的内容写回 checkpoint」之后，读一次 checkpoint 快照、把本次运行的消息整组写进这张表。覆盖全部收尾形态：正常答完、用户按停止、上游失败或超时、放弃收尾、被别的进程接手续跑后完成。**排空到可交接边界时不写**——那次运行还没结束，写由接手方在最终收尾时做，这样「运行确定不再继续」是写入的唯一前提。运行期间不写，界面显示「正在生成」，与今天一致。

**整组替换**：同一事务里先按（会话，运行）删掉旧行、再按顺序插入，并在（会话，顺序号）上建唯一键兜底（不把运行 id 放进唯一键：`seq` 是会话内递增的、读的时候只按它排序，那才是这张表的语义）。收尾被执行两次，结果与写一次相同：**重复收尾时该组的顺序号沿用第一次写入的那一组**（删之前先把原来的顺序号读出来、按原样回填）——不这样做的话，先删后插会把一条较早运行的行排到更晚的轮次之后，回看顺序变了。这一组的内容完全相同，所以顺序号也应当完全相同。

**怎么切出「本次运行的消息」**：现有回放的分轮逻辑已经实现了这套切分——从一条非摘要的提问开始、到下一条提问之前的全部助手与工具消息归同一轮，运行 id 就取提问消息上的那个。接手续跑产生的新消息属于同一个运行 id，所以接手场景下这套切分仍然成立；返回时按（运行，消息）列给写入方。

**写入方只写表里还缺的那些运行组，已经写过的组一字不动。** 这一条同时解决两件事：一是**本次运行那一组当然在内**（不要读成「把快照里能组出来的轮全部重写」——那会把更早轮次的工具正文——在 checkpoint 里已经被换成占位文字的那份——盖回表里，与「用户看到的仍是原文、且此后永不清理」正好相反）；二是下面那条没有收尾机会的运行有地方补。

**进程被强杀、OOM、断电那一次运行没有任何收尾代码会执行**，它的提问与已产出的内容只留在 checkpoint 里，而回放已经改读表——所以它不会自己落表。归宿是：**下一次进入这个会话、任何一次运行的收尾都会把缺的组补上**（整组替换是幂等的，补的就是缺的那些）。如果用户再也不回来，那一轮就不落表——那是仓库既有的「没有收尾机会的故障」边界（那一轮本来就是靠用户重新提问），接受；界面在那之前会显示成「正在生成」，与今天一致。

**补写那一组的工具正文可能已经是占位文字，要照实写。** 被强杀那一次运行的旧工具正文，会在它之后某次运行触发清理时被换成占位；而补写读的就是同一份 checkpoint，所以表里落的就是占位。这不是 bug，是「那一次运行没有收尾机会」的代价，要写进验收口径：**「已经落表的内容此后永不修改」是硬保证，而「用户看到的是当时交给模型的原文」只对「收尾那一刻就落了表的」那几轮成立**。

**但摘要行拿不到，要单独取，而且要认得出「它是不是这次产生的」。** 那套切分逻辑会把摘要消息跳过（它不属于任何一轮），而分界线唯一的来源就是摘要行——照字面复用切分，摘要行永远不会落到表里。规则写死一条：**摘要行的写入判据与它所属的那一组绑定**——写某一组时（无论是本次运行那一组，还是上面说的补写那一组），把「产生它的那次运行 id」等于**该组运行 id** 的摘要行一起写；头部沿用下来的旧摘要（它的产生运行是更早的某一次，不属于本组）跳过。写出的这一行 `summary` 的运行 id 也记**产生它的那次运行**（「这条消息属于哪一次运行」这条列语义对摘要行同样成立），而它覆盖到哪一轮由 `memory_boundary_run_id` 表达，两者不要混。**这里有个坑：摘要消息在一次压缩之后就留在状态头部、不会自己消失，所以之后每一次运行的收尾都能「找到」它**——照「找到就写」实现，每个后续运行都会凭空多写一行，同一会话里会累积一串。最多只有一条：压缩会重建整个消息列表，头部只放一条摘要。

**运行 id 必须无条件盖在消息上。** 今天盖运行元数据的地方**有两处**短路：本次运行没有知识库范围时直接跳过、什么都不盖——一处是给助手消息盖标记的地方，另一处是**提问消息自己的构造**（那时它连 `run_id` 都不带）。两处都要去掉，只改一处等于没改：提问行是切分与运行元数据（范围快照、模型快照）的唯一载体，它没有 `run_id` 时这张表根本组不起来。撤掉历史裁剪之后这两个短路没有存在理由了，所以**盖元数据不再依赖本次运行有没有范围**，每一次运行都盖。这是本 spec 对上下文策略那次改动提出的唯一要求。

**读取路径彻底离开 checkpointer**：回放接口改为查这张表并组装轮次。**前端拿到的形状不变**——每一轮的问答、工具轨迹、引用、状态、范围字段逐个保持原样（前端是逐字段消费的，`traces` 里的工具名、参数、返回内容、是否失败都要照旧）。**唯一的例外**是引用里那个正文片段字段：它随上下文策略那次改动一起去掉（那时业务表已经留住了完整原文），所以引用项会少这两个字段；另外**多一个**每轮实际用的模型（含展示名）——那是模型目录那次改动的验收面，本来就要逐轮读出。响应里**多一个「模型从哪一轮开始只剩摘要」的标记**，供界面画那条线——**取会话里 `seq` 最大的那一条摘要行的标记**（摘要行一次压缩写一行、旧行不删，而分界标记在后来的压缩里可能是沿用上一条的值，所以只有最近那一行的标记是对的；取最旧一条会把线画得比实际早）。同时**去掉 `summarized` 与 `summary` 两个字段**（界面不再展示摘要正文，分界线靠那个新标记就够了；留着就是没人消费的接口字段）。

**但「离开 checkpointer」只针对回放接口这一处。** 同一条组装逻辑还有另外两个消费方，它们必须继续走 checkpoint：**终态事件**（一次运行结束时把最终答案、完成状态与引用发给前端）与**接手时重建「本轮冻结的范围与模型」**（部署排空后由别的进程续跑，要从提问消息上的运行元数据重建上下文）。这两件都发生在运行收尾前后，那时这一轮可能还没写进表。所以：**回放读表、终态与接手读 checkpoint，两边的组装口径必须一致**（同一套分轮、同一套引用核验），不得各写一套——今天它们共用同一套正是为了防“Done 与刷新后的回放各说一套”。

**先后要写死的是这一条：写表必须在释放会话位之前。** 终态事件仍然在**释放之后**才发——**这是仓库既有的保证，不能反过来**：用户拿到「答完」之后立刻追问，如果会话位还没释放，会撞上刚结束那次运行的占位、拿到一次莫名其妙的「这个会话已有运行在跑」；既有代码里就写着这条理由。写表插在收尾里、在释放之前，中间那段窗口里刷新页面则靠会话行上的在途运行标记显示「正在生成」，不会当成「这一轮没有回答」。

**界面**：时间线上一条分界线加一句实话——**此处之前的对话，模型只保留了摘要；此处之后的问答与工具轨迹完整保留，但较早的工具原文可能已被清理成占位文字**。这句话只讲**模型**保留什么；用户那一侧看到的原文始终是完整的（回看读的是这张表）。两件事要分开说，因为它们是两个不同的机制：分界线记的是**摘要边界**，而清理是在压缩之前先省空间、它**在分界线以下也生效**，不单独画线。**删掉现在的「查看背景摘要」折叠块**（摘要正文不展示），并**改掉现在那句错文案**——「原始问答不再提供回看」在本次之后就是假的了。

**约束**：不建外键约束，`thread_id` 是业务层维护的逻辑外键。**删除有多个出口，每一个都要连带删这张表**，全部由业务层在同一事务里先删消息行、再删主体行：

- **用户删会话**（删除接口）：接在既有的删除入口上，与删会话行同一个事务；整体顺序仍保持「先把 checkpoint 历史清掉、再删业务行」，那是仓库既有的可自愈顺序（反过来会留下删不掉的孤儿）。
- **清理旧会话那个运维命令**：它现在是两步（先清 checkpointer、再删业务行），这张表要接在它删业务行的那一步里，同一个事务。
- **清理孤儿会话那个运维命令**：它删的是「checkpointer 里有、业务表里没有归属行」的会话，而这张表归会话行管——**这条路径上的行在升级之后会反复产生，不是历史存量**，所以命令必须能按 thread_id 把这张表的行一起删掉，而且**候选集不能只看 checkpointer**：删会话时「清 checkpoint」与「那次运行又写回表行」的先后可以颠倒，所以残余可能只有表里的行、checkpointer 那边什么都没有。候选集 = 没有归属行的 `thread_id`，从两边取并集。残余从哪来：删一个正在运行的会话时，等它停下的上限是 10 秒，超时就继续删（那次运行随后仍会把收尾内容写回去）——这是仓库已确认并写在流程文档里的代价；而收尾写这张表时**不核对会话行是否还在**（库上也没有外键兜底），于是那批消息会写进去，留下一批没有归属行、界面上查不到、也删不掉的行。**这正是用户故事 13 要排除的东西**，所以不能指望升级时清一次就完了。

**存量不留、不回填**：现有会话全部清掉（开发阶段，已确认）。清空是这次升级的第一步，具体动作与顺序见「补充说明」。

## 测试决策

**接缝一：HTTP 层。** 回放接口与删除接口都在这层测，用既有那套夹具。要断言的是**对外的 `turns` 形状与今天逐字段一致**（问答、工具轨迹、引用、状态、范围），新增的只有那个分界标记；以及删会话之后这张表里那一会话的行也没了。

**接缝二：离线图加内存 checkpointer 加真实数据库的写入路径。** 断言「跑完一次运行之后，这张表里的行组成了那一轮」：提问、助手正文、每个工具调用、每个工具结果、以及（压缩发生时）摘要行与它的分界标记。这一层也断言收尾形态——停止、失败、放弃各写出一轮完整终态。

**什么算好测试**：断言用户能看到的东西（回放接口给出的轮次）与表里的事实，不测实现细节。**整组替换那条要断言「收尾执行两次，表里的行只有一份」**，而不是去数 SQL 语句。

**必须覆盖的失败路径**：收尾重复执行不产生重复行；排空交接的运行在交接那一刻**不写**、接手方收尾时才写；跨会话删除只动自己那一会话的行；表里没有对应行时回放接口返回空轮次而不是报错；**删会话等了 10 秒没停下来、那次运行随后又写回来的那一批行，能被子清理命令按 thread_id 删掉**。

**先例**：回放形状照既有那份回放测试；删除连带照文档保留那条「同一事务里先删依赖、再删主体」的测试；迁移列注释照既有的列注释同步测试。

**要重写或删掉的既有断言**：**回放接口那一处**拿 checkpointer 当数据源的断言——它们钉的是本次要换掉的读取路径。终态事件与接手那两条路径的断言**不动**（它们继续读 checkpoint，只是口径要与表一致）。特别是那条钉住「上游摘要消息形态」的契约测试：摘要消息的形态仍要在**写入侧**被钉住（写入方要能认出 `lc_source=summarization` 的伪提问），但断言的对象从回放结果变成写进行里的内容。

## 超出范围

**压缩发生时把被移除的原文归档进业务表。** 那会把写入点塞进压缩中间件内部——那是个今天零数据库依赖的纯逻辑模块，要往里引入连接、事务与失败重试；而且归档与 checkpoint 写入跨两个连接池，无法用一个事务覆盖，失败时会重复归档或丢一段。**否决。**

**不删状态、只在模型调用前裁剪。** checkpoint 会无界增长：上游每走一步都把消息全量写一份。**否决。**

**只保留问答文本、丢掉工具轨迹与引用。** 会让用户以为早期回答当时没查资料。**否决。**

**运行中增量写**（刷新页面能续看半截回答）。这是新功能，不属于本次修复；老板已同意以后单独立项。

**历史回填。** 存量全部清掉，不做迁移。

**摘要在界面上展示。** 分界线说明「模型只保留了摘要」，但摘要正文不展示。

## 补充说明

**三份改动一次部署、一次清空。** 它们之间有内部依赖：**这张表必须先存在**，上下文策略那次改动才成立——它会把旧轮次的工具正文换成占位，而用户回看读的是这张表；表不在，那一轮在界面上就整块消失。所以**施工顺序**上先建表、再改上下文策略，但**不要拆成两次部署**：那会在中间留出一段窗口，里面既有「有业务表行、却没有模型快照」的会话，也有「有业务表行、却要等下一版才有分界线」的会话。[模型目录那次改动](0002-model-catalog-and-user-model-choice.md) 依赖的是同一次清空。

升级步骤：**清空既有会话 → 由超级用户在后台把上游渠道与可用模型配好 → 之后正常使用**。清空**不写代码**，写成一次性运维动作（开发阶段只做这一次，为它永久加一条命令属于「以后可能需要」）：手工清掉两处——checkpointer 里的历史与业务表里的会话行，顺序按既有的「先 checkpoint、后业务行」，因为反过来会留下删不掉的孤儿。**不要拿既有的清理命令凑**：它的天数下限是 1 天，清不干净，而留下没有业务表行的会话会让用户点开一片空白。

**分界线的可见性只在这一步之后成立。** 如果只做了 [上下文策略那次改动](0001-model-sees-whole-session-history.md)、没做这次，用户回看读的还是 checkpointer，被清掉的那一轮会像今天一样整块消失。

**收尾写这张表失败时，行为跟既有的收尾写入一致**：只记日志，不回滚、不重试、不中断收尾——那几处写入都是可自愈的。代价要记住：这里的后果比那几处重一点，那一轮不会出现在回看里。用户刚看过流式输出，所以不是「凭空少一轮」，但刷新之后就没有了。**不为它引入重试**：重试解决不了「同一个事务写不进去」，只会把收尾拖长；而这条代价已经由「收尾写入只记日志」这个既有约定承担了。

**这条痕迹必须现在记。** 压缩边界标记只能在压缩发生的那一刻写下，事后推不出来；而它写进的是摘要消息，随收尾一起进这张表，所以这一次落地之后就不再有「压过但没留痕」的会话。
