# 部署改成先起后停：零停机与秒级回滚

## 问题陈述

现在部署一次就是「停掉旧容器 → 跑迁移 → 起新容器 → 健康检查」，整个过程里宿主机端口是关着的：新请求直接被拒（点发送报错、刷新页面接口报网络错），典型三十到六十秒。其中最长的那一截是「等旧容器把手上的运行跑完」（最长 360 秒，而且用户关掉页面就救不回来），**那一截已经由 `0002-run-handover-on-deploy.md` 的排空交接去掉**（旧容器把在途运行交给新版本接着跑，排空以秒计）。所以本规格要消掉的是**剩下那三十到六十秒**：迁移、起容器、等就绪检查——把它们都挪到旧版本还在服务的时候做。

这期间**已经在看的那条回答不会断**，断的是**新请求**：浏览器里点发送会失败、刷新页面时接口报网络错，用户看到的是「服务挂了」而不是「正在更新」。

同时今天**没有任何回滚能力**：镜像标签恒定，部署脚本末尾还会把被顶替下来的旧镜像当无名镜像清掉，想回到上一版只能重新构建旧提交再发一次。还有一条隐式的安全边界：入口端口靠「只绑本机回环」保护，任何部署方式的改动都不能把它暴露到公网。

## 解决方案

后端的三个进程改成由 Swarm 服务管理，部署用「先起后停」：先起新容器，迁移与起容器都在旧版本还在服务的时候完成，旧容器只在新任务启动判定成功之后才被停掉；它手上还有在途运行就先排空到可交接的边界、交给新版本接着跑完（上限 120 秒、通常几秒，见 `0002-run-handover-on-deploy.md`）。于是部署期间新请求不中断；顺带拿到「一条命令切回上一版镜像」的秒级版本回滚。

**「先起后停」不等于「就绪之后才切流量」。** Swarm 的入口不会等健康检查通过才把新任务加进转发集合（社区实测的直接现象），所以零停机不是它替我们等出来的，而是靠**把「被加进流量」到「真能服务」之间的窗口压到最小**（见实现决策）。「正在跑的回答不被打断」也不是本规格的功劳——那条由 `0002` 的排空交接解决。

新版本能不能接班由一个**只读的就绪端点**判定——业务库能查、checkpointer 连接池能取到连接；不复用现有那个刻意的「进程活着、数据库能连」健康检查。容器编排界面从 1Panel 换成 Portainer：它只看与应急，写入者始终是 CI。

## 实现决策

**编排形态。** API、Beat、Worker 三个进程一起改成同一份编排文件里的 Swarm 服务：一份定义、一个部署命令、图形界面里一个堆栈看全。不给后端单独换形态、另外两个留在旧的编排方式里——同一份文件被两种命令解读会带来「改了没生效」这类看不见的错。

**更新顺序与停止宽限期按服务分别声明。** API 是「先起后停 + 就绪检查 + 排空」，这就是本方案本身；它的排空上限由 `0002-run-handover-on-deploy.md` 定（120 秒、通常几秒），所以停止宽限期取 **180 秒**即可，不再按「一次运行能跑多久」推算。Beat 必须「先停后起」，它只在到点时投任务，先起后停会让两个调度器短暂同时活着、同一个周期任务可能被投两次；它没有手上活要收尾，宽限期取 **30 秒**。Worker 用「先起后停」，与「先停后起」的差别只是后者有一段没人领任务的消费空窗——正在跑的文档批次在两种顺序下都会被允许跑完（Celery 收到终止信号是温和退出，先做完手上任务），**它的宽限期不能跟着 API 一起降**：文档批次可能远长于两分钟，压到 180 秒会让批次半途被中断、留下需要人工确认的待核实记录，而那正是用户故事 12、13 要避免的事，所以它保持今天的 **360 秒**。宽限期在编排文件里按服务分别写，不共用一个数。

**必须把「被加入转发目标」到「真能服务」之间的窗口压到最小。** Swarm 的入口会把流量发给健康检查还在启动中的任务（社区实测的直接现象），而 uvicorn 是先在生命周期启动里把应用装配完、之后才开始接请求——所以新容器一旦被加入转发目标，落到它身上的新请求会在容器里排队等生命周期跑完，表现为这几秒内一部分请求变慢。今天启动路径里最重的那一项是对上游模型服务发一次「列模型」的自检（超时 5 秒），它不属于能服务的前提，所以要从关键路径上移出去（改后台或惰性），把窗口压到毫秒级；顺带把启动路径上其余外部调用也核对一遍。**不为此新增代理组件**（入口指针由 Swarm 拿，这个窗口靠压缩启动时间来消，而不是靠额外的健康检查层）；**除非开工前那条实验量出的是「请求真的失败」而不是「请求变慢」**——那时才把自建代理（只把流量发给已就绪容器）放回范围，见测试决策第 0 条。

**就绪判据是新增的，不是把健康检查做深。** 现有健康检查刻意只回答「进程活着、数据库能连」，理由是别让健康检查本身成为故障来源，这条理由继续成立，所以它保持原样、继续给运维与云监控用；新增一个只读的就绪端点，判据是业务库能执行一次最小查询**加上** checkpointer 连接池能取到连接——后者是独立连接池，业务库探活探不到它；**「服务检索但 Agent 不可用」这个状态是刻意允许的**（装配失败不致命，进程照起、只有对话链路返 503），但它必须表现为**未就绪**，否则部署会把旧版本换成一个聊天用不了的版本。注意就绪判定能拦住的是「要不要停旧任务」这一步（而这一步对「容器退出」类失败由更新器的回滚策略管），拦不住「新任务已经被分到一部分流量」——后者由压小启动窗口负责，见上。**上游大模型不纳入判据**：上游抖动是外部故障，把它变成部署门禁只会让别人的故障挡住自己的发布。

**更新策略。** 一次一个任务、失败时回滚、更新后留一段监视窗口以捕获「起来就崩」。**API 的停止宽限期不再由「一次运行能跑多久」推算**：排空只需要等一个 superstep（上限 120 秒），宽限期取 180 秒；Worker 的宽限期单独取值，理由仍然是让手上的文档批次做完（见上）。要分清两件事：**「流量什么时候开始分给新任务」由入口决定，不等就绪**（见上一条）；**「旧任务什么时候被停」由更新器按任务是否启动成功判定**，`失败即回滚` 管的是「容器退出」这一类，判不出「起来了但不健康」——后者只能靠就绪端点被看见，所以「服务检索但 Agent 不可用」必须如实报未就绪。

**入口端口与安全边界。** 对外端口号不变（编排界面那层不用改）。绑定从「只绑本机回环」变成「全网卡监听」——Swarm 的路由网格不支持只绑回环，这是它的已知行为；安全边界因此从端口绑定换成机器防火墙（只放 80、443、SSH）。改造后必须验证一次：端口显示为全网卡，而从外网访问不通。

**镜像清理。** 把「清理所有无名镜像」改成「只删 7 天前的无名镜像」：保留被顶替下来的上一版够回滚用，同时不让磁盘无限涨。

**写入者与界面边界。** CI 是唯一写入者；图形界面只用于查看、看日志、手动重启和手动回滚（回滚命令写在部署手册里）。原来管这三个服务的面板入口要清理掉：面板里旧的编排项目删除，容器页不要用来停这些容器（Swarm 会把它们补回来，看起来像「打不死」）。

**迁移纪律（与部署方式无关，本次只记成规则）。** 删列、改列名、改语义、拆约束的迁移拆两次发布：先发「代码不再用它」，下一次发布再删。回滚只回代码；做过破坏性迁移之后回滚退路就不存在了，只能按部署手册那条「恢复备份」处理。不引入机械门禁。

**文档落点。** 决策记进一条 ADR（已写）。部署手册要改三处：把日常部署一节从旧流程改写成新流程（迁移 → 起新 → 切换 → 排空 → 停旧）、写明回滚命令与「退回旧部署方式」的逃生路径、补两条排查知识（哪种迁移会关掉回滚退路；某个 API 进程卡住时的表现与恢复办法）。

**改造要动的具体位置（原来没写清、开工时会撞上的）。** 服务器上要先把这台机器加入集群（一次性动作，此前没提）；编排文件从「普通容器」形态改成「服务」形态：容器名这类字段不再合法、重启语义改由服务的重启策略表达、Worker 扩容从命令行参数改成副本数声明；**原来那些一次性容器要换一种跑法**——文件变成编排文件之后，用原来那条命令跑迁移与建表初始化不再合适，改成以同一镜像直接跑一次性容器；候选编排的校验与提交换成集群版的两条命令（校验 + 部署，并注意从文件里删掉的服务不会自动消失）；部署工作流里 Beat/Worker 的就绪检查原打在容器上，现在要打到「任务」容器上；部署手册里「后端先、前端后」那条规则的理由要重写（蓝绿之下旧后端仍会服务在飞连接，顺序不变，但「不会出现新前端调老后端」这句话不再准确）。**本规格自己**不动运行行为、接口契约与数据表结构（往会话行加一列属于 `0002-run-handover-on-deploy.md`），所以架构文档与术语表也不因本规格而改。

## 测试决策

**好测试的标准**：只断言外部可观察的行为——端口上能不能服务、流量有没有被切过去、旧容器手上的回答有没有跑完——不断言内部调用顺序或私有状态。

**主要接缝（既有，最高层）：HTTP 层。** 就绪端点用现有的离线应用工厂加请求传输来断言：正常时返回就绪；把 checkpointer 连接池换成取不到连接的替身时返回不就绪；上游大模型不可用时仍然就绪（这条是反向断言，防止后来人把外部依赖塞进判据）。现有健康检查的用例保持不动。

**新增的第二条接缝（结构性，离线）：对编排文件做结构断言。** 断言 API 声明了就绪检查与「先起后停」、Beat 声明了「先停后起」、镜像清理不再是无条件清理、API 与 Worker 的停止宽限期是分别声明的（不共用一个数）。之所以值得加：这些都是一行声明，删掉不会有任何测试变红，而后果（切换时停机、周期任务重复投递、回滚失效）只有在真机上才暴露。做法照仓库里对迁移文件的结构测试（按路径读文件、断言关键声明），不起容器、不连数据库。

**真正的验收只能在服务器上做**，它是八条演练，每条都要能失败：

0. **开工前先量出「新容器什么时候开始收流量」（10 分钟，不碰生产业务）**：用两个占位服务（一个 nginx 类镜像即可，带一个先失败后就绪的健康检查）做一次先起后停更新，循环请求同时记录失败与耗时。要回答两个问题：更新期间有没有请求失败；有没有请求变慢、慢多久。**结论决定实现**：若只是变慢，压缩启动窗口就够了；若真的失败，就要把「自己一个带主动健康检查的小代理」放回范围（它是唯一能保证只把流量发给已就绪容器的做法）。失败的样子：没测就开工，到演练 2 才发现。

1. **改造本身**：服务起来、静态站点照旧可访问、端口显示为全网卡、**从外网访问该端口不通**、图形界面里能看到这个堆栈。失败的样子：外网能连上；页面打不开。
2. **普通发布零中断**：边部署边持续请求，**同时看失败与延迟**（只看失败会漏掉「请求都慢几秒」这种形态）。失败的样子：出现任何一次失败，或延迟明显超过平时的量级。
3. **版本回滚**：切回上一版后仍在服务、行为如旧。失败的样子：命令报错（镜像已被清掉）或旧版本报错。
4. **坏版本不接班，分两条测——它们回答的是两个不同的问题，不能合成一条：**
   - **4a 启动期就失败（容器退出）**：故意让新版本起不来（比如让它连不上数据库）。期望：**旧任务没被停、更新自己回滚、用户无感**。**判据是「旧版本还在不在服务」，不是「流量有没有分过去」**——后面那个指标混了两件事，测不出这件事。失败的样子：旧的被停了，或更新没回滚。
   - **4b 起来了但就绪检查一直不过（进程不退）**：故意让就绪端点一直返未就绪。要观察两件事：**旧任务有没有被停掉**、**不健康的新任务还收不收流量**。失败的样子：旧的被停了、而且流量还打到那个坏版本上（那意味着一个「检索能用、聊天用不了」的版本替掉了好的版本）。**这一条的数据决定口径**：若旧的没被停，剩下的只是「慢几秒」（口径 A 就够）；若旧的被停了，就要改用口径 B（自己拿指针、只把流量发给已就绪的容器）。
5. **排空与接手**：在新编排形态下重跑 `0002-run-handover-on-deploy.md` 那条真机验收（起一个长回答再部署）。失败的样子：回答没有被新版本接着跑完（内容不完整、或会话历史里那一轮是未完成），或旧容器的排空不是秒级。**它的触发路径与 0002 那次不同**（那边是断连，这里是切流量之后 SIGTERM），所以要重跑。
6. **退回旧部署方式**：验证通过后真的切回旧方式一次、确认能用，再切回新方式。失败的样子：切不回去——那说明这条逃生路径只是纸上的。

**既有回归**：后端全量离线测试、前端构建与测试照旧；这次改造不动应用行为，除就绪端点外不应有测试改动。

## 超出范围

- **前端静态文件的两版本共存**：停留旧页面的用户点懒加载路由会拿到 404，这是今天就有、与 API 切换无关的另一个问题，本次不做。
- **把 API 改成「一个容器一个进程 + 多副本」**：它能让就绪探针从抽样变成全量，但那是拓扑决策、不由这次改造引入，留到有用户之后再评估。
- **就绪判据里加入上游大模型**：上游抖动是外部故障，不做成部署门禁。
- **迁移纪律的机械门禁**：不把迁移按「扩展/收口」分目录、不在流水线里拒绝混发；这次只记成规则。
- **平台级蓝绿**（Kubernetes、云厂商负载均衡或托管 PaaS）：本次只换编排形态，不引入集群或云产品。
- **运行级时长上限**：本次只定「部署愿意等多久」，不给一次运行本身加时长上限。
- **运行被强杀后的丢失**：进程被强杀、或排空超过上限时，那次运行照样丢，收尾靠失活判定——这是既有边界，本次不解决（正常部署那一类已由 `0002-run-handover-on-deploy.md` 的排空交接解决）。
- **账号级并发上限**：不引入（既有缺口，本次不动）。

## 补充说明

**前提**：本规格按 `0002-run-handover-on-deploy.md` 已落地写（顺序是先二档、再本规格）。二档把「旧容器等服务到结束」换成「排空到可交接的边界、交给新版本接着跑」，所以本规格里所有与排空有关的数字都按它取值：停止宽限期 180 秒、验收第 5 条、以及下面那条「双活不是让部署变快」。

**首次改造要停一次机，也只有那一次。** 旧方式占着宿主机端口，新方式要发布同一个端口，先停后起躲不掉；现在还在开发阶段、没有用户，所以这是最便宜的时机。改造前的编排与旧容器留着，出问题按手册退回去。

**「零停机」的口径是「用户感知不到」，不是数学上的零。** 窗口内落到新容器的请求会被启动耗时拖慢（见实现决策），严格意义上的「一个新请求都不受影响」只有自己拿指针（自建代理）才做得到。所以验收按「成功率 100% + 延迟不出现数量级劣化」取值，而不是「绝对没有影响」。

**双活不是让部署变快。** 改造后 CI 仍然会等旧容器排空（秒级到两分钟以内，上限见 `0002-run-handover-on-deploy.md`），只是这份等待从用户视线里移走了。

**秒级回滚的边界。** 它只回代码、不回数据库；做过破坏性迁移之后它就不存在了。要它可用，必须同时满足三件：「上一版镜像还在」与「这次迁移对旧版本安全」，以及**图状态结构没变**——与接手（排空续跑）同一条前提：旧代码接不了新形状的 checkpoint，形状变了的发布既不能接手也不能回滚。

**三个心跳不要混。** 运行的心跳（驱动者定期续活跃时间）、连接的心跳（服务端事件流）、以及这次新引入的容器健康检查，用途完全不同，取值也都独立。

**就绪探针的抽样性质。** 一个容器里两个 API 进程时，探针只代表被问到的那一个；发现手段（卡住的进程不再打日志）与恢复办法（重启这个容器）写进排查手册。这是既有事实，不改拓扑就不消除。

**顺带的收益。** 换成 Swarm 之后，以后要加机器只需要让新机器加入集群，而不必重做部署方式；而且「同时有几个运行在跑」这类问题在图形界面里直接可见。
