# 部署改成先起后停：零停机与秒级回滚

## 问题陈述

> **需求原话（老板）**：「我们 spec 0001 的目的就是做到蓝绿部署，尽可能 0 停机的更新，仅此而已。」

**本规格要交付的就是这条**：把后端做成 Swarm 服务、先起后停、就绪了才停旧任务，并顺带拿到「一条命令切回上一版」的能力。「在途运行不被打断、由新进程接手」是**另一条需求**，已经落地并交付（决策与后果见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)，它那份规格已按完成条件删除）——**本规格不重复设计它，也不以它为施工依据**。

> **评审口径（写给接手评审的人）**：本规格的目标就是上面那两段。**如果评审输入里的需求是「在途运行不被打断、由新进程接手」，那是另一条、已交付的需求**（[ADR 0040](../adr/0040-run-handover-on-deploy.md)，它那份规格已按完成条件删除），**不要把它算成本规格的缺口**——本规格只在验收第 5 条把它当回归复核。归属有疑问时，先让老板确认以哪条为准，再判合格与否。

现在部署一次就是「停掉旧容器 → 跑迁移 → 起新容器 → 健康检查」，整个过程里宿主机端口是关着的：新请求直接被拒（点发送报错、刷新页面接口报网络错），典型三十到六十秒。其中最长的那一截是「等旧容器把手上的运行跑完」（最长 360 秒，而且用户关掉页面就救不回来），**那一截已经由 [ADR 0040](../adr/0040-run-handover-on-deploy.md) 的排空交接去掉**（旧容器把在途运行交给新版本接着跑，排空以秒计）。所以本规格要消掉的是**剩下那三十到六十秒**：迁移、起容器、等就绪检查——把它们都挪到旧版本还在服务的时候做。

这期间**已经在看的那条回答不会丢**——连接会在旧容器退出时断一次，界面短暂显示「正在生成」，随后接回完整答案（那是另一条需求已交付的行为，见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)）；**断掉的是新请求**：浏览器里点发送会失败、刷新页面时接口报网络错，用户看到的是「服务挂了」而不是「正在更新」。

同时今天**没有任何回滚能力**：镜像标签恒定，部署脚本末尾还会把被顶替下来的旧镜像当无名镜像清掉，想回到上一版只能重新构建旧提交再发一次。还有一条隐式的安全边界：入口端口靠「只绑本机回环」保护，任何部署方式的改动都不能把它暴露到公网。

## 解决方案

后端的三个进程改成由 Swarm 服务管理，部署用「先起后停」：先起新容器，迁移与起容器都在旧版本还在服务的时候完成，旧容器只在新任务启动判定成功之后才被停掉；它手上还有在途运行就先排空到可交接的边界、交给新版本接着跑完（上限 120 秒、通常几秒，见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)）。于是部署期间新请求不中断；顺带拿到「一条命令切回上一版镜像」的秒级版本回滚。

**「先起后停」不等于「就绪之后才切流量」。** Swarm 的入口不会等健康检查通过才把新任务加进转发集合（社区实测的直接现象），所以零停机不是它替我们等出来的，而是靠**把「被加进流量」到「真能服务」之间的窗口压到最小**（见实现决策）。「正在跑的回答不被打断」也不是本规格的功劳——那条由 [ADR 0040](../adr/0040-run-handover-on-deploy.md) 的排空交接解决。

新版本能不能接班由一个**只读的就绪端点**判定——业务库能查、checkpointer 连接池能取到连接；不复用现有那个刻意的「进程活着、数据库能连」健康检查。容器编排界面从 1Panel 换成 Portainer：它只看与应急，写入者始终是 CI。

## 实现决策

**编排形态。** API、Beat、Worker 三个进程一起改成同一份编排文件里的 Swarm 服务：一份定义、一个部署命令、图形界面里一个堆栈看全。不给后端单独换形态、另外两个留在旧的编排方式里——同一份文件被两种命令解读会带来「改了没生效」这类看不见的错。

**网络与依赖可达（开工第一步就会撞上的硬阻塞）。** Swarm 服务只能挂 `scope=swarm` 的网络，而今天三个进程挂的 `1panel-network` 是 1Panel 建的本地 bridge（编排文件里声明为 external），拿去 `stack deploy` 会直接报「not in the right scope: local instead of swarm」。所以新形态**自己声明一张 swarm 作用域的 overlay（`attachable: true`），名字用 `agent-lab-net`**，三个服务挂它；名字在编排文件里**显式写死**（不靠栈名前缀自动生成，否则你敲命令时得先查实际叫什么）。**这张网在编排文件里声明成 external，不能等 `stack deploy` 才建**：接 Redis 需要网已经存在，而接 Redis 又必须发生在首次部署的自检之前——「建网交给部署命令」和「先接 Redis」两条放一起就是死循环。所以**建网与接 Redis 是同一次手工准备里的两条命令**（建网一次、接 Redis 一次），之后每次部署只是引用它；网被误删时部署会报「网络不存在」而停下（响的，不是静默的），重建也是一条命令。**这里要说清为什么不能直接把面板那张拿过来用**：拦路的是网络的 **scope**，不是某个开关——bridge 驱动建出来的网 scope 是 `local`，Swarm 服务只认 scope 是 `swarm` 的（overlay 驱动）。`attachable` 走的是**另一个问题**：它让普通容器（面板管的那些）也能插到 overlay 上，所以它是新拉那张网时要打开的开关，而不是把已有 bridge 改成 swarm 能用的手段。而且**已经建好的网改不了**：Docker 没有改网络的命令（只有 create / connect / disconnect / rm），想换 driver 或 scope 只能删掉重建，而那张网是全机应用共用的，重建等于全机断网——所以只能新拉一张，代价小得多。**需要跨过去的容器内依赖只有 Redis**（其余都不是 docker 网络里的东西：业务库与用量库走 tailscale 域名、Ollama/Qdrant/大模型走 https 域名，原件存储按 `S3_ENDPOINT` 的地址形态）。**这里要说清我们并不改 Redis**：不重启、不动它的配置、不搬走、不换端口——Docker 的网络像一根共享插线板，今天面板上的应用（含 Redis 与我们三个进程）都插在面板那张上，而 Swarm 服务插不上那张，只能新拉一根；要跟 Redis 说话，就得让它也插到新那根上（它原来那张照旧，其他应用不受影响）。三个服务仍按原来的容器名解析它，`.env` 不用改。**开工第一步先核三件事（2 分钟）**：`1panel-network` 的 scope、Redis 容器的名字与它挂在哪张网、面板有没有把 Redis 端口发布到宿主机以及发布在哪个地址；顺便看 `1panel-network` 的成员里有没有第二个容器内依赖（有就按 Redis 的同一种接法处理），并在容器里确认那几个外部地址仍然能解、能连（tailscale 名字与 https 域名——今天能解，换网后要复验一次；跨主机名字靠的是宿主解析器转发，与容器挂哪张网无关，但它正是「本地能用、换网就怪」的那类东西）。然后按事实定路线：**默认（推荐）是「把 Redis 接上新那张 overlay 一次」——这一步由老板手工做一次，不由部署流程代劳**（部署流程不去动面板管的共享容器；命令与验证写进手册，见文档落点），接的时候顺手加一个固定别名（`--alias redis`），以后 `REDIS_URL` 想固定写成这个别名也行，不必跟着面板给容器起的名字走；备选是「走宿主地址或内网地址」（`REDIS_URL` 换成可达的那个地址；想用 `host.docker.internal` 这个名字的话，**Linux 上它不是现成的**，得在服务定义里显式写 `extra_hosts: host.docker.internal:host-gateway`，或者直接写宿主 IP），**只在确实发现它本来就发布在容器可达的地址上时才用**——这里要分清两种地址：**宿主的地址**（tailscale IP 或公网 IP 加已发布的端口）是稳的；**容器在 docker 网里的 IP 不稳**（面板重建 Redis 就换一个），写进 `.env` 等于埋下一个与「线丢了」症状一模一样的定时炸弹，不要用。随之两条事实写进手册：一是**这张 overlay 上只有三个服务与 Redis**，比今天「所有面板应用共用一张网」更窄，是收紧不是放松；二是**面板重建那个 Redis 容器会丢掉这次接入**，症状是队列与缓存报错而页面本身照常——手册里要有重新接入的命令，部署前那次 Redis 连接自检（它今天就在停旧进程之前跑）要能把这种情况挡住。原来那条运维约定「本项目不创建 Redis、专用网络或数据卷」因此改口为「不创建 Redis 与数据卷，创建并自持一张本项目的 overlay」。**一次性容器（迁移、建表初始化、部署前自检）也挂这张网**：它们与服务看到同一个世界，尤其**那条 Redis 自检跑在 `agent-lab-net` 上，验证的就是服务将来能不能够到 Redis**（迁移本身只需要数据库，不碰队列——接不接 Redis 都跑得起来；挂同一张网是为了口径一致，不是迁移需要它）。**顺序上有一个坑要先说清**：部署工作流在停旧进程之前会跑一次 Redis 连接自检，所以**开工那一次手工准备要把网建好、把 Redis 接通**（接一根线，或改地址）；不先做这步，那条自检（它跑在 `agent-lab-net` 上）会因为网不存在或 Redis 不通把部署挡住——挡住本身是好事（不会真停服），但会白跑一轮。

**更新顺序与停止宽限期按服务分别声明。** API 是「先起后停 + 就绪检查 + 排空」，这就是本方案本身；它的排空上限由 [ADR 0040](../adr/0040-run-handover-on-deploy.md) 定（120 秒、通常几秒），所以停止宽限期取 **180 秒**即可，不再按「一次运行能跑多久」推算。Beat 必须「先停后起」，它只在到点时投任务，先起后停会让两个调度器短暂同时活着、同一个周期任务可能被投两次；它没有手上活要收尾，宽限期取 **30 秒**。Worker 用「先起后停」，与「先停后起」的差别只是后者有一段没人领任务的消费空窗——正在跑的文档批次在两种顺序下都会被允许跑完（Celery 收到终止信号是温和退出，先做完手上任务），**它的宽限期不能跟着 API 一起降**：文档批次可能远长于两分钟，压到 180 秒会让批次半途被中断、留下需要人工确认的待核实记录，而那正是用户故事 12、13 要避免的事，所以它保持今天的 **360 秒**。宽限期在编排文件里按服务分别写，不共用一个数。

**必须把「被加入转发目标」到「真能服务」之间的窗口压到最小。** Swarm 的入口会把流量发给健康检查还在启动中的任务（社区实测的直接现象），而 uvicorn 是先在生命周期启动里把应用装配完、之后才开始接请求——所以新容器一旦被加入转发目标，落到它身上的新请求会在容器里排队等生命周期跑完，表现为这几秒内一部分请求变慢。今天启动路径里最重的那一项是对上游模型服务发一次「列模型」的自检（超时 5 秒）。**这里要把「能服务」与「已就绪」分开**：把这次自检从**生命周期的等待段**里拿出来，改成启动后立刻在后台跑，它的结论由就绪端点表达——**检查未完成或失败（模型名不在列表里）→ 未就绪；通过、或上游不回答（不回答时本来就放行，判据是「有没有证据说配置错了」）→ 就绪**。于是端口立刻能服务（窗口只剩连库那一小段），而「配置写错不许替掉好版本」这条判定仍然在。**不要把它改回串行等待**：上游卡住时那一步就是 5 秒，而并发等待只是把窗口从「相加」变成「取最慢」，验收 2 的延迟判据会因它不通过。顺带把启动路径上其余外部调用也核一遍。**它有一处必然后果要写下来**：配置写错不再让对话接口直接返 503（装配已经成功了），而是提问后收到 `llm_model_not_found` 的 error 事件——前端文案表里这个码本来就指向同一句「Agent 尚未就绪」，用户看到的几乎一样，但**那条钉住 503 的用例必须跟着改成断言新行为**（见测试决策）。**不为此新增代理组件**（入口指针由 Swarm 拿，这个窗口靠压缩启动时间来消，而不是靠额外的健康检查层）。**但这个窗口压不到零，因此本规格自带两条停手线**：开工前那条实验若量出「请求真的失败」，或验收 4b 量出「新任务不健康时旧任务照样被停」，都意味着核心一步（只把流量发给已就绪的容器）得自己拿指针——那时**本规格停在这里，另开一份规格覆盖代理的组件边界、门控方式、测试与安全边界**，不在这里留半个设计。

**就绪判据是新增的，不是把健康检查做深。** 现有健康检查刻意只回答「进程活着、数据库能连」，理由是别让健康检查本身成为故障来源，这条理由继续成立，所以它保持原样、继续给运维与云监控用；新增一个只读的就绪端点（**与 `/health` 同级：不鉴权；按部署文档那套反代配置，`/api/` 是整段转发的，所以它从公网以 `/api/ready` 也能命中——今天 `/api/health` 就是这样**。因此响应体只给状态、不给「哪一项没过」，也不放依赖名或错误原文，与 `/health` 的固定消息同一原则；真正的边界仍是端口与安全组，不是路径前缀），判据是**三样一起看**：业务库能执行一次最小查询、checkpointer 连接池能取到连接（后者是独立连接池，业务库探活探不到它）、以及**启动后那次后台配置校验的当前结论**（未完成或失败 → 未就绪）。**第三项不能省**：自检挪到后台之后装配会成功、连接池也建得起来，少了它就盖不到「配置写错」这个状态——那正是 4b 要防的事，而且八条演练里没有一条能替它试出来。**「服务检索但 Agent 不可用」这个状态是刻意允许的**（装配失败不致命，进程照起、只有对话链路返 503），但它必须表现为**未就绪**，否则部署会把旧版本换成一个聊天用不了的版本。**就绪端点是编排文件里 API 服务健康检查的目标**；除此之外只有开工前那次实验与 CI 会读它（都不是产品功能）。**编排文件里这组时间参数取初值：间隔 5 秒、单次超时 3 秒、连续 3 次失败判不健康、启动宽限 15 秒**（启动宽限要盖过正常启动耗时，否则容器一上来就被判不健康；开工前实验量出实际启动耗时后可以调它）。**它能不能拦住「停旧任务」这一步，取决于更新器是否采信健康状态**——这一条属于开工前实验要量的事实（见测试决策第 0 条第②问）：采信，则健康就是门禁；不采信，则它只能兜住我们自己的检查与演练判据，那种情形按停手线处理。无论哪种，它都拦不住「新任务已经被分到一部分流量」——后者由压小启动窗口负责，见上。**上游可用性不纳入判据**：上游抖动是外部故障，把它变成部署门禁只会让别人的故障挡住自己的发布；要区分另一件事：那句「列模型」自检**不是可用性探针**（上游不回答时它放行），它只拦「配置写错」，而配置写错会让这个容器在就绪判定里被判成不就绪——**这条链路要留住**（见上一条）。

**更新策略。** 一次一个任务、失败时回滚、更新后留一段监视窗口以捕获「起来就崩」（监视窗口初值 **60 秒**，要盖过健康检查判不健康所需的时间：间隔 5 秒 × 连续 3 次）。**API 的停止宽限期不再由「一次运行能跑多久」推算**：排空只需要等一个 superstep（上限 120 秒），宽限期取 180 秒；Worker 的宽限期单独取值，理由仍然是让手上的文档批次做完（见上）。要分清两件事：**「流量什么时候开始分给新任务」由入口决定，不等就绪**（见上一条）；**「旧任务什么时候被停」由更新器按任务是否启动成功判定**，`失败即回滚` 管的是「容器退出」这一类，判不出「起来了但不健康」——后者只能靠就绪端点被看见，所以「服务检索但 Agent 不可用」必须如实报未就绪。

**入口端口与安全边界。** 对外端口号不变（编排界面那层不用改）。绑定从「只绑本机回环」变成「全网卡监听」——Swarm 的路由网格不支持只绑回环，这是它的已知行为；安全边界因此从端口绑定换成 **云安全组/VCN 安全列表（只放 80、443、SSH）**：它在网络边缘拦，Docker 的 NAT/FORWARD 规则绕不过它（如果是配在宿主 iptables/ufw 上就会被绕过，需要改用 DOCKER-USER 链——当前不是这种情形）。验收要从**真正的外网侧**测一次（不能只在同一个 VPC 内的另一台机器上试，那会假绿）。这条以老板的确认（云安全组/VCN 安全列表）为准；**如果实际靠的是宿主防火墙，演练 1 会红**，那时要补一条 DOCKER-USER 链规则——所以这条不靠断言、靠那次演练兑底。

**镜像清理。** 把「清理所有无名镜像」改成「只删 7 天前的无名镜像」：保留被顶替下来的上一版够回滚用，同时不让磁盘无限涨。

**写入者与界面边界。** CI 是唯一写入者；图形界面只用于查看、看日志、手动重启和手动回滚（回滚命令写在部署手册里）；**它只绑本机、经 SSH 隧道访问**——它等价于这台机器的 root，不该有公网入口。原来管这三个服务的面板入口要清理掉：面板里旧的编排项目删除，容器页不要用来停这些容器（Swarm 会把它们补回来，看起来像「打不死」）。

**迁移纪律（与部署方式无关，本次只记成规则）。** 删列、改列名、改语义、拆约束的迁移拆两次发布：先发「代码不再用它」，下一次发布再删。回滚只回代码；做过破坏性迁移之后回滚退路就不存在了，只能按部署手册那条「恢复备份」处理。不引入机械门禁。

**文档落点。** 决策记进一条 ADR（已写）。部署手册要改三处：把日常部署一节从旧流程改写成新流程（迁移 → 起新 → 切换 → 排空 → 停旧）、写明回滚命令与「退回旧部署方式」的逃生路径、补两条排查知识（哪种迁移会关掉回滚退路；某个 API 进程卡住时的表现与恢复办法），**再补一条：Redis 的接入操作本身**（网名 `agent-lab-net` 下的接入命令、验证方法、断开命令、以及面板重建 Redis 容器后重新接入的命令与它的症状）——这条由人执行，手册要把命令给全，并把「不创建专用网络」那条运维约定改成新口径。

**改造要动的具体位置（原来没写清、开工时会撞上的）。** 服务器上要先把这台机器加入集群（一次性动作，此前没提）；编排文件从「普通容器」形态改成「服务」形态：**栈的加载器与普通 compose 不是同一套，它不认的字段要逐个换成等价写法**——容器名不再合法、重启语义改由服务的重启策略表达、Worker 扩容从命令行参数改成副本数声明、`env_file` 与相对路径的卷挂载也要换成显式写法（注入方式与挂载路径自己给，不指望它沿用原目录）；这批连同网络一起在开工第一步过一遍（栈既会报错也会静默忽略，两种都遇得到，别留到真机上第一次才发现）；**原来那些一次性容器要换一种跑法**——文件变成编排文件之后，用原来那条命令跑迁移与建表初始化不再合适，改成以同一镜像直接跑一次性容器（**并把它们接在同一张 overlay 上**；其中 **Redis 那条连接自检要保留**，理由见补充说明「自检留哪条」）；候选编排的校验与提交换成集群版的两条命令（校验 + 部署，并注意从文件里删掉的服务不会自动消失）；部署工作流里 Beat/Worker 的就绪检查原打在容器上，现在要打到「任务」容器上；部署手册里「后端先、前端后」那条规则的理由要重写（蓝绿之下旧后端仍会服务在飞连接，顺序不变，但「不会出现新前端调老后端」这句话不再准确）。**还有一处代码注释要跟着改**：启动那句「列模型」自检的 docstring 要补一句「它与其他启动工作并发、不串行等待」（它原本的理由不变：一次极轻的 GET 换掉一轮排查），否则后来人很容易把它改回串行、把启动窗口又撑大。**本规格自己**不动运行行为与数据表结构（往会话行加一列属于 [ADR 0040](../adr/0040-run-handover-on-deploy.md)）；对外接口契约**完全不变**（状态码、错误码、SSE 事件联合、回放形状都不改）：**新增的那个内部就绪端点不进对外 schema**（它是内部端点、产品侧没有消费者，所以前端的生成类型连重新生成都不需要；`/health` 留在 schema 里是既有选择，不动它）。架构文档与术语表不因本规格而改。

## 测试决策

**好测试的标准**：只断言外部可观察的行为——端口上能不能服务、流量有没有被切过去、旧容器手上的回答有没有跑完——不断言内部调用顺序或私有状态。

**主要接缝（既有，最高层）：HTTP 层。** 就绪端点用现有的离线应用工厂加请求传输来断言：正常时返回就绪；把 checkpointer 连接池换成取不到连接的替身时返回不就绪；上游大模型不可用时仍然就绪（这条是反向断言，防止后来人把外部依赖塞进判据）。现有健康检查的用例保持不动。

**既有的结构断言**（对编排文件的）范围只限「删掉就会静默改坏一条已定承诺」的声明：不断等价写法（以后换命令行参数或其他字段表达同一件事，测试要跟着改），不断字段拼写，不追求把编排文件格式钉死。之所以值得加：这些都是一行声明，删掉不会有任何测试变红，而后果（切换时停机、周期任务重复投递、回滚失效）只有在真机上才暴露。做法照仓库里对迁移文件的结构测试（按路径读文件、断言关键声明），不起容器、不连数据库。

**真正的验收只能在服务器上做**，它是八条演练，每条都要能失败：

0. **开工前把三个前提一次量完（10 分钟，不碰生产业务；结论写进开工那一批工单的验收记录——那批工单开工时用 `to-tickets` 从本规格拆出，不回写本规格）**：用两个占位服务（一个 nginx 类镜像即可，带一个先失败后就绪的健康检查）做一次先起后停更新，循环请求同时记录失败与耗时；同时用 `docker service inspect` 看镜像引用，并做一次回滚。要回答三个问题：
   - **① 窗口里请求是失败还是只是变慢**（变慢的话慢多久）；
   - **② 新任务不健康（健康检查一直不过、但进程不退）时，旧任务会不会被停**（这同时决定就绪端点有没有“停旧任务”这个消费者）；
   - **③ 服务定义里是否钉住了镜像摘要**（决定回滚能不能真的回到上一版代码）。
   **结论决定实现**：①里是“失败”或者②里旧任务会被停 → 本规格停手，另开一份规格补上代理（只把流量发给已就绪的容器）；③里若发现回滚回到的是同一个可变标签 → 另开一份规格做不可变标签方案，验收 3 才能成立。三条都过，就按本规格施工，验收 3 / 4b 退回成普通复核。失败的样子：没测就开工，到演练 2 或 4b 才发现。

1. **改造本身**：服务起来、静态站点照旧可访问、端口显示为全网卡、**从真正的外网侧访问该端口不通**（手机流量或另一网络；同一个 VPC 内的另一台机器不算）、图形界面里能看到这个堆栈。失败的样子：外网能连上；页面打不开；**或者服务起来了但够不着 Redis**——「页面打不开」的这两种原因要分得开（Redis 没通时 API 进程照样会起，只是队列与缓存报错）。
2. **普通发布零中断**：边部署边持续请求，**同时看失败与延迟**（只看失败会漏掉「请求都慢几秒」这种形态）。失败的样子：出现任何一次失败，或延迟明显超过平时的量级。
3. **版本回滚**：切回上一版后仍在服务、行为如旧，**并且能证明跑的就是上一版**——比对回滚前后服务定义里的镜像引用（含摘要）必须不同，否则命令成功也只是假绿灯。失败的样子：命令报错（镜像已被清掉）、旧版本报错、或镜像引用根本没变。**若发现回滚回到的是同一个可变标签（镜像引用没变），本规格停手**：那说明「可指认的上一版」需要一个不可变标签方案（每次构建多推一个带提交号的标签、保留最近若干个、回滚时显式指定它），那要另开一份规格，不在这里临时发明。
4. **坏版本不接班，分两条测——它们回答的是两个不同的问题，不能合成一条：**
   - **4a 启动期就失败（容器退出）**：故意让新版本起不来（比如让它连不上数据库）。期望：**旧任务没被停、更新自己回滚、用户无感**。**判据是「旧版本还在不在服务」，不是「流量有没有分过去」**——后面那个指标混了两件事，测不出这件事。失败的样子：旧的被停了，或更新没回滚。
   - **4b 起来了但就绪检查一直不过（进程不退）**：故意让就绪端点一直返未就绪。要观察两件事：**旧任务有没有被停掉**、**不健康的新任务还收不收流量**。失败的样子：旧的被停了、而且流量还打到那个坏版本上（那意味着一个「检索能用、聊天用不了」的版本替掉了好的版本）。**这一条与开工前实验量的是同一件事**：实验过了之后它就是复核；但复核与实验结论相反时以复核为准，仍然停手——若旧的没被停，剩下的只是「慢几秒」，按本规格继续；若旧的被停了，说明「坏版本会替掉好版本」，**本规格停手、另开一份规格把代理补上**（自己拿指针、只把流量发给已就绪的容器）。
5. **排空与接手**：在新编排形态下重跑一次「部署打断在途运行」的真机验收——起一个多轮工具调用的长回答，在它跑的时候部署。期望：答案完整、界面没出现错误提示、旧容器排空以秒计、会话历史里那一轮不是未完成。失败的样子：回答没有被新版本接着跑完（内容不完整、或那一轮是未完成）、界面报错、或排空不是秒级。**它的触发路径与那一份落地时验过的不同**（那边是断连，这里是切流量之后 SIGTERM），所以要重跑。
6. **退回旧部署方式**：验证通过后真的切回旧方式一次、确认能用，再切回新方式。失败的样子：切不回去——那说明这条逃生路径只是纸上的。

**既有回归**：后端全量离线测试、前端构建与测试照旧。**这次只有一处既有行为明确改变**：配置写错不再让对话接口返 503，所以那条钉 503 的用例要改成断言新行为（就绪端点报未就绪 + 提问后收到 `llm_model_not_found` 事件）；「Agent 装配失败仍然返 503」那条保持不动，它守的是另一半。除此之外不应有测试改动。

## 超出范围

- **前端静态文件的两版本共存**：停留旧页面的用户点懒加载路由会拿到 404，这是今天就有、与 API 切换无关的另一个问题，本次不做。
- **把 API 改成「一个容器一个进程 + 多副本」**：它能让就绪探针从抽样变成全量，但那是拓扑决策、不由这次改造引入，留到有用户之后再评估。
- **就绪判据里加入上游大模型**：上游抖动是外部故障，不做成部署门禁。
- **迁移纪律的机械门禁**：不把迁移按「扩展/收口」分目录、不在流水线里拒绝混发；这次只记成规则。
- **平台级蓝绿**（Kubernetes、云厂商负载均衡或托管 PaaS）：本次只换编排形态，不引入集群或云产品。
- **运行级时长上限**：本次只定「部署愿意等多久」，不给一次运行本身加时长上限。
- **运行被强杀后的丢失**：进程被强杀、或排空超过上限时，那次运行照样丢，收尾靠失活判定——这是既有边界，本次不解决（正常部署那一类已由 [ADR 0040](../adr/0040-run-handover-on-deploy.md) 的排空交接解决）。
- **账号级并发上限**：不引入（既有缺口，本次不动）。

## 补充说明

**前提**：排空与接手那一份已经落地并交付（它那份规格已按完成条件删除，决策与后果见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)）。它把「旧容器等服务到结束」换成「排空到可交接的边界、交给新版本接着跑」，所以本规格里所有与排空有关的数字都按它取值：停止宽限期 180 秒、验收第 5 条、以及下面那条「双活不是让部署变快」。

**首次改造要停一次机，也只有那一次。** 旧方式占着宿主机端口，新方式要发布同一个端口，先停后起躲不掉；现在还在开发阶段、没有用户，所以这是最便宜的时机。改造前的编排与旧容器留着，出问题按手册退回去。

**「零停机」的口径是「用户感知不到」，不是数学上的零。** 窗口内落到新容器的请求会被启动耗时拖慢（见实现决策），严格意义上的「一个新请求都不受影响」只有自己拿指针（自建代理）才做得到。所以验收按「成功率 100% + 延迟不出现数量级劣化」取值，而不是「绝对没有影响」。

**双活不是让部署变快。** 改造后 CI 仍然会等旧容器排空（秒级到两分钟以内，上限见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)），只是这份等待从用户视线里移走了。

**秒级回滚的边界。** 它只回代码、不回数据库；做过破坏性迁移之后它就不存在了。要它可用，必须同时满足三件：「上一版镜像还在」与「这次迁移对旧版本安全」，以及**图状态结构没变**——与接手（排空续跑）同一条前提：旧代码接不了新形状的 checkpoint，形状变了的发布既不能接手也不能回滚。

**配置写错会拦住接班，上游不健康不会。** 模型名写错时，那次后台配置校验的结论是「未就绪」，于是旧版本不被替掉；上游连不上时那句自检本来就放行（判据是「有没有证据说配置错了」）。驳回的是「拿上游可用性当部署门禁」，保留的是「配置写错不允许替掉好版本」——两件事不要合并。**对用户侧，配置写错的表现在本次变了**：从「对话接口直接返 503」变成「提问后收到 `llm_model_not_found` 的事件」；两处文案表本来就是同一句（`CONFIGURATION_COPY` 那条），所以前端不用改，但那条旧用例要改。

**三个心跳不要混。** 运行的心跳（驱动者定期续活跃时间）、连接的心跳（服务端事件流）、以及这次新引入的容器健康检查，用途完全不同，取值也都独立。

**就绪探针的抽样性质。** 一个容器里两个 API 进程时，探针只代表被问到的那一个；发现手段（卡住的进程不再打日志）与恢复办法（重启这个容器）写进排查手册。这是既有事实，不改拓扑就不消除。

**自检留哪条、为什么。** 只留 Redis 那条连通检查，其余不加：业务库不通时应用本来就起不起来（生命周期里同步环境管理员那一步会抛错、容器直接退出），用量库那条是**配置**校验而不是连通校验（建 Engine 不建连），模型名那条已经在别处说明。Redis 不同：它是刻意允许「消息代理暂不可用时 API 仍可持久受理和查询」的依赖，所以它坏掉的样子是**容器健康、页面照开、队列与缓存静默停摆**——那正是最危险的失败形态；它同时还是「新那张网络的线有没有接上」的检查，所以必须留。

**为什么用项目自己的网（`agent-lab-net`），而不是全机一张共享 overlay。** 一是暴露面：项目网里只有我们三个服务和我们明确接上去的东西（今天只有 Redis），别的项目看不见我们、我们也看不见它们；共享网等于把今天「全机容器互相可见」平移到 swarm 世界，隔离白拿回来又还回去。二是省不了事：Docker 不会让新容器自动加入已存在的网（面板新建的容器默认仍插在 `1panel-network`），所以**不管用哪张网，每加一个依赖都要显式接一次**，共享网换来的只是「接的目标统一」。三是以后加机器时，项目网正好是「我们的服务能跨机器互通、别的项目看不见」的边界。真要重估的时机是「这台机器上多数项目都迁到 Swarm、而且经常互相调用」——那时再拉一张共享网也只是多接一次的事。

**顺带的收益。** 换成 Swarm 之后，以后要加机器只需要让新机器加入集群，而不必重做部署方式；而且「同时有几个运行在跑」这类问题在图形界面里直接可见。
