# 后续检索 KnowledgeBase 范围

> 状态：第二阶段草案，当前未实施；老板要求先收尾第一阶段，再讨论本阶段。本文承接 [0001](0001-knowledge-base-architecture-and-data-model.md) 已明确排除在第一阶段验收之外的两个功能，不影响第一阶段的完成结论。本文及原 spec、review spec 均保留。

## 需求边界

- 普通检索页面增加 KnowledgeBase 选择器，只提供启用库；每次检索把选定 ID 显式传给现有 HTTP 接口。
- 检索记录保留该次查询的 KnowledgeBase 范围，后续切换不改变历史记录或已打开全文的实际归属。
- Agent Tool 增加可选 `knowledge_base_id`；传入时限定指定启用库，不传时检索所有启用库。未知或停用目标沿用稳定错误契约。
- Agent 页面不增加 KnowledgeBase 选择器，不把范围绑定到 Agent 会话；Tool 本身仍只读。
- 核心普通检索仍要求明确单库；跨库是 Agent 应用用例的显式例外，不能把空范围解释为无过滤地命中停用库。
- 复用既有 KnowledgeBase、Document、Payload、错误与装配契约，不新增存储、来源适配器、权限体系或后台管理功能。

## 施工前讨论

以下是待确认的交互与实现选择，尚未作为新增需求实施：

- 检索页面继续每次默认新闻库，还是记住上次选中的知识库；默认库停用时如何提示和选择。
- Agent 如何取得可选知识库的真实 ID 与名称：随请求提供启用库目录，或通过只读 Tool 查询；不让模型猜测 UUID。
- 检索记录和 Agent 引用如何展示知识库归属，避免跨库结果在用户看来无法区分。
- 沿用草案中“普通检索单库、Agent 不传参数时查询所有启用库”的分工，还是调整查询范围的用户控制方式。

## 验收清单

- [ ] 页面覆盖默认新闻库、选择其他启用库、加载失败、空列表以及查询前后停用/重新启用。
- [ ] HTTP 请求与检索记录保存一致的范围；切换不引起跨库结果混淆。
- [ ] Tool 有参数时仅命中该启用库，无参数时命中全部启用库且排除停用库。
- [ ] 全部库停用时在 Embedding/Qdrant 之前结束，不生成不受限查询。
- [ ] Tool 参数 schema、HTTP 契约、错误映射及假客户端回归保持一致。
- [ ] 前端交互、后端相关测试与必要工程检查通过，同步 ADR 与用户流程。

本规格只记录原定后续范围。实际施工前按当时的需求和现有设计核对，不预建空实现。
