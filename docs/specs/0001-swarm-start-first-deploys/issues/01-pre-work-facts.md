### ②的前提：启动窗口是「变慢」还是「失败」，由 `WORKER_COUNT` 决定

`.env` 里 `WORKER_COUNT=2`。uvicorn 0.52.1 在 `--workers >= 2` 时由父进程先 `bind+listen` 再 fork 子进程（`uvicorn/main.py` 的 `Multiprocess(config, sockets=[config.bind_socket()])`），而 `Server.startup()` 是先 `await self.lifespan.startup()` 才 `create_server`——所以启动窗口里端口已经在 listen，落进来的新请求是**排队变慢**；`WORKER_COUNT=1` 时端口要等生命周期跑完才 listen，那种形态才是**失败**。第 2 步实验按 `PREBIND=1` 复现生产的这一形态，另外用 `PREBIND=0` 顺带量一次另一形态作对照。

### 停手线判定

尚未判定，等第 2 步实验的②③与④结果。

### ② 先起后停的窗口：实测结论（实验 A，2026-09-30）

占位服务开启健康检查（指向自己的就绪探测，参数同规格初值：间隔 5s / 超时 3s / 连续 3 次 / 启动宽限 15s），`update_config` 为 `order: start-first` + `failure_action: rollback` + `monitor: 10s`；新任务故意用 12 秒才 accept（`PREBIND=1`，即 `WORKER_COUNT=2` 的形态）。切换窗口里逐秒延迟分布：**980 次请求，失败 0 次，切换窗口内最慢 3ms**（整轮 max 46ms）。

原因不是「请求排到了队但很快被消化」，而是**流量根本没发给新任务**：新任务在整个启动窗口里 `docker service ps` 显示为 `Starting`（不是 `Running`），容器健康状态是 `health: starting`。对照实验（C2，服务不声明健康检查）用来确认这一步归因。

结论：**只要服务的健康检查指向就绪端点，Swarm 就不会在它就绪前把流量分过去**——这与规格「Swarm 的入口会把流量发给健康检查还在启动中的任务（社区实测的直接现象）」的前提相反。

——已由对照实验坐实（C2）：把同一个占位服务的健康检查**去掉**后重新跑同一套更新，窗口里新任务立刻进 `Running` 并收流量：`t+1s` 一次请求耗时 **11911ms**（正好是 12 秒启动窗口）、另一次 `Connection refused`（容器刚起、Python 还没 bind 那一小段），t+2s–t+12s 没有新请求（负载循环被那个 11.9 秒的请求堵住）；整轮 542 次请求、失败 1 次。**规格的担忧是真的，但只在服务没有健康检查时成立**；API 会有健康检查（指向 `/ready`），所以那个窗口不会被用户碰到。

结论：**②的答案是「既不是失败也不是变慢，而是新任务在就绪前根本不收流量」**。规格里「把被加入转发目标到真能服务之间的窗口压到最小」那条担心的形态，在本系统的形态下不会出现；窗口（实测约 9.7 秒，见下）不再直接影响用户。它的代价变成另一件事：新任务要等健康检查通过才算 `Running`，所以部署切换比「容器一起就行」晚一段（那段里旧版本照常服务）。

### ③ 新任务一直不健康时旧任务会不会被停：实测结论（实验 B，2026-09-30）

新任务用「进程活着、永不响应」的形态起（`STARTUP_SECONDS=9999`，容器一直 `health: starting` → `unhealthy`）：

- 更新状态：`updating` →（约 +50s）`rollback_started` → `rollback_completed`，**更新自己回滚了**。
- 旧容器（真正在服务的那一个）**全程未被停**，直到观察结束（+90s）仍在 `(healthy)`。
- 新任务最终被 **agent 自己杀掉**：`probe-b_probe.1 Failed 44 seconds ago "task: non-zero exit (137): dockerexec: unhealthy container"`。它从未进入 `Running`，也从未收到流量（切换窗口内 980 次请求 0 失败、最慢 4ms）。

结论：**旧任务没被停 → 本工单的第一、第二条停手线都不触发。** 用户故事 4 要的行为（坏版本不接班、更新自己回滚）在实测里成立，而且比规格预期的更强。

### 必须记下的新事实：在 Swarm 里「健康检查不过」= 容器被杀

规格假设健康检查只影响显示与更新门禁；实测是 agent 直接给容器发退出（137）并标为 failed，之后再按重启策略拉起。三个后果：

1. 常规部署之外它也生效，且会变成崩溃重启循环（C3 实测，没有任何部署在跑）：容器 t+30s 变 `unhealthy`，t+40s 被 `Exited (137)` 杀掉，Swarm 按重启策略拉起新容器，新的又走一遍——**约 50 秒一个循环**（15 秒启动宽限 + 3 次 × 5 秒）。所以规格里「服务检索但 Agent 不可用是刻意允许的状态（进程照起、检索照服务）」在 Swarm 里**不会长期保持**：它就绪不过就会被杀掉重启。部署场景下这件事是好的一面（坏版本不接班、更新自己回滚），但「半坏状态长期在线」这个描述今后不成立，工单 03 的代码注释与工单 10 的手册要按实测写。
2. 工单 04 要给 Beat/Worker 沿用现有健康检查时，语义会从「给人看」变成「不过就杀」：Worker 手上的文档批次会被中断，正是用户故事 12/13 要避免的事。**老板已拍板：只在 API 上声明健康检查（指向 `/ready`）；Beat/Worker 不写 `healthcheck`，它们的检查由部署工作流用 `docker exec` 打到任务上（工单 05 已要求），语义与今天一致。**
3. 测试决策里的 4b「起来了但就绪检查一直不过（**进程不退**）」在 Swarm 里不可能成立：这种任务会被 agent 杀掉，于是它退化成 4a。工单 08 的 4b 按「旧任务会不会被停 + 坏任务收不收流量」实测，不按「进程不退」构造。

### ④ 镜像引用（已实测，结论：含摘要，回滚成立）

“不带 `--with-registry-auth` 时服务定义里只有可变标签”（B6 实测）：`crpi-.../agent-lab:backend-latest`，PreviousSpec 也是同一个标签。**带上 `--with-registry-auth` 后（D1/D2 实测）任务定义里是：**

```text
crpi-f8h2anjy882vm7jk.ap-northeast-1.personal.cr.aliyuncs.com/zkh_main/agent-lab:backend-latest@sha256:2915f9b8...
```

换镜像（`--image placeholder:v2`）再 `--rollback`，回滚后的引用就是上面那一份带摘要的引用（`回滚后` 与 `回滚目标` 逐字相同）——**回滚能真的回到那一版具体镜像**。

对施工的两条硬约束（写进工单 05 与工单 10）：

1. **部署命令必须带 `--with-registry-auth`**。不带就没有摘要，回滚变成「回到那个可变标签现在指的东西」，也就是假绿灯。这条不是可选项。
2. 顺带消掉了旧流程那个「tag 恒为 backend-latest，`up -d` 复用旧镜像」的坑：带摘要后，CI 推了新镜像 ⇒ 解析出的摘要变了 ⇒ 服务定义跟着变 ⇒ 任务真的被替换；不再依赖「先 `docker pull` 把本地 tag 换掉」这一步。

D3 还实测了退路：栈文件里直接写 `repo@sha256:...` 也被接受、任务能用（`pin4_pinned.1 Running`），将来若要改成「每次构建多推一个带提交号的标签」，这是一个现成写法。

### 附带事实：生产 API 真实启动耗时约 9.7 秒，其中 7.7 秒是子进程 import

```text
16:42:16.946  启动 uvicorn，worker 数量: 2
16:42:17.602  Uvicorn running on http://0.0.0.0:8000；Started parent process [1]   ← 端口在这里就 listen 了
16:42:25.349  Started server process [16]；Waiting for application startup.        ← 子进程 import 用了 7.7 秒
16:42:26.643  Application startup complete.                                       ← 生命周期只占 1.3 秒
```

即：容器起 → 可用 ≈ **9.7 秒**，而规格假设「窗口只剩连库那一小段」。生命周期里那次上游「列模型」自检只占约 1.3 秒内的一部分（它在并发里），把它挪到后台对总窗口的收益远小于规格的预期。工单 03 仍然要做，但它的理由从「抢时间」变成「当门禁」：没有就绪判据，一个「检索能用、聊天用不了」的版本会被健康检查放行、被更新器认定成功，从而替掉好版本。

### 一条待澄清的旧容器时间线（已定性：运维插曲，不是排空没退出）

`agent-lab-backend` 的日志起点是 09-29T16:42:16Z，其中 09-30T01:22:19Z 出现 `Received SIGTERM, exiting.` 与关停日志，但容器 `Up 14 hours`。C4 实测（宿主机时区是 **UTC**）：三个容器的 `Created` 都是 `2026-09-29T16:42:16Z`，而 `StartedAt` 对应 09-30 01:59:57Z（`docker logs --tail 5` 的最后几行就是那次 `Application startup complete`）。即：01:22:19 那次 SIGTERM 是部署的 `docker compose stop`，容器确实停了；**镜像没换**（Created 未变）又起来了一次，中间隔了约 37 分钟——看着像那次部署失败过一次、第二次重跑才成功。定论：与排空/接手无关，不影响验收 5 的预期；顺带记下一条现存脆弱性：旧流程在「停旧 → 迁移」之间失败会把服务留在停止状态（新流程把迁移放在停旧之前，正好消掉这条）。
