- **面板清理完成**：老板在面板里删掉了旧的 compose 项目，它把那三个 `Exited` 容器一并移除了（`docker inspect agent-lab-backend` → `no such object`）。所以「旧容器留着」这条只能部分兑现：**旧编排文件、`.env` 与镜像都还在，退路改为用 `docker compose -f docker-compose.yml up -d` 重建普通容器**（重建出来的是当前的 `backend-latest`；「退回旧部署方式」指的是部署方式，不是代码版本）。这一条的真实验证放在工单 11。
- **上一版镜像仍在本地**（只是不再挂仓库标签）：`docker images` 里以 `placeholder:v1  2915f9b8b668` 出现（那是探针脚本打的标签），所以 `docker image inspect <仓库>@sha256:2915f9b8…` 会报 No such image。另记一笔：工单 09 的秒级回滚**不依赖它**——回滚目标是服务定义里钉住的摘要（下次部署后即本次的 `5d756f4e…`），摘要不可变，本地没有也能按摘要从 ACR 拉回。
- **一个现场教到的操作坑（要进工单 10 手册）**：在图形界面里对**任务容器**做「重启」会留下**孤儿容器**——Swarm 把那个任务判成 Complete/Shutdown 并另建新任务，但旧容器自带 `restart: any` 策略继续活着且不再归编排管。症状是「服务层干净（`docker service ps` 只有一行 Running、`REPLICAS 1/1`），但节点上多出一个同名容器在跑」，对 Beat 而言就是**两个调度器同时活着**（正是用户故事 11 要防的）。处置：`docker rm -f <孤儿容器名>`。**正确做法是重启服务**：`docker service update --force <服务名>`，或在界面里的**服务**那一层操作。已实测：`--force` 后服务收敛到 1 个任务，但孤儿仍在，需手动删。后续同一次现场还留下了一个 `已退出（代码 0）` 的旧任务容器（`…ljpzlybd…`），也是那次手动重启的残渣。
- **待 07 验证的一条预期**：正常滚动更新时，旧任务的**容器**由 agent 移除，`docker service ps` 里留下的只是任务历史（不带容器），所以多次部署**不会累积已退出的容器**；先起后停期间会短暂同时看到新旧两个容器，旧的那个停止后被移除。这条在工单 07 那次真部署后用 `docker ps -a --filter name=agent-lab_` 实测确认。
