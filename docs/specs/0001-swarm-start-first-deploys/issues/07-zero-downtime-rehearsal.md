# 07: 验收：零中断 + 排空接手复验（演练 2、5）

**要交付什么：** 一次真部署上同时量两件事：用户侧没有任何感知（持续请求零失败、延迟不出现数量级劣化），以及部署期间正在跑的那条多轮长回答被新进程接着跑完、界面不报错、会话历史里那一轮不是未完成。这是「尽可能零停机」这条承诺的唯一凭据，数据要留在工单里。

**被谁阻塞：** 06: 首次改造：停机一次把服务切上 Swarm（演练 1）

**状态：** 已完成

- [x] 部署窗口内持续请求的失败数为 0，且延迟分布与部署前相比不出现数量级劣化（保留原始数据）
- [x] 部署期间正在跑的多轮长回答在部署后完整结束：内容完整、界面没有错误提示、会话历史里那一轮不是未完成
- [x] 排空耗时以秒计并记录实测值
- [x] 若出现失败或明显变慢，记录能定位到「哪个请求、哪一段」的证据，而不是只知道「部署期间出了错」

### 验收记录（2026-10-01 实测，服务器 `instance-20260723-1451`）

**负载器**：`output/swarm-07-load.sh`（宿主上起一个 `--network host` 的容器，每 100ms 打一次
`http://127.0.0.1:18000/health`，每 2 秒加一次 `/ready`；原始记录落在 `swarm-work/load.json`）
在第二次 CI 部署（推 `23157df`，运行 `36812454904`）期间跑了 10 分钟。

```text
记录 6032 条（含每 2 秒一次的 /ready），失败 0 次
延迟 ms：p50=4 p90=5 p99=9 max=86
最慢的 5 个 10 秒桶：
  03:59:10  请求  98  失败 0  最慢  86ms     ← 手动 --force 换任务
  03:55:20  请求 100  失败 0  最慢  81ms     ← CI 部署换任务的时刻（11:55:13 = 03:55:13 UTC）
  03:50:20  请求  12  失败 0  最慢  49ms     ← 负载起步的不完整桶
```

**结论：验收题 1（零中断）通过。** 6032 次请求零失败；延迟分布（p50/p90/p99 = 4/5/9ms）与部署前
无差别，两个最慢的桶（81ms / 86ms）与两次换任务的时刻对应——那是个别请求在建连接，不是分布
移位（p99 仍是 9ms）。日志也侧证：新容器里能看到负载经由 ingress 打进来的 `GET /health 200` /
`GET /ready 200`。

**在途运行与接手：场景已触发，但细粒度证据被清理掉了。** 手动 `docker service update --force
--update-monitor 5s agent-lab_backend` 期间发出的一条带工具调用的提问，在旧任务容器里的日志是：

```text
84:INFO agent_lab.api.agent_chat Agent 对话开始 thread_id=d268fe75-… run_id=e7106795-…
90:INFO:     Received SIGTERM, exiting.
```

**这两行之间没有任何「运行收尾」**，即 SIGTERM 到达时那条运行还在跑（验收要的就是这个场景）；
而且那个旧任务当时呈 `Up 6 minutes (healthy)`——它在排空（等一个 superstep 结束、把运行交给
新进程），随后变成 Exited。教训：取日志的命令与清理命令写在同一块里、且取得太早（排空还没
结束），所以「接手」那行与排空耗时都没留下；重做时改成「轮询等旧任务变 exited、再用
`docker logs -t` 取带时间戳的两边日志」。

**顺带一条实现事实**：每次强制更新都会把旧任务容器停掉但**留在节点上**（`Exited (0)`），
部署多次会累积；已给工作流加了一步「成功后清掉本栈已退出的任务容器」，手册也会留手动命令。

### 在途运行被接手：实测成功（第三次尝试）

前两次尝试都只走到「排空」或「运行自己跑完」，第三次把问题的目标从 2 个提到 5 个（多个工具
调用会被重试，运行因此足够长），才把 SIGTERM 落在运行中段：

```text
04:22:47.361  Agent 对话开始 thread_id=ea957b8d-… run_id=3e5f00ac-…
04:23:04.086  Received SIGTERM, exiting.                     ← 提问开始后 16.7 秒，运行还在跑
04:23:36.391  Agent 运行已排空，等待接手 thread_id=ea957b8d-… run_id=3e5f00ac-…
04:23:36.391  Agent 运行收尾 … stopped=False drained=True
```

**排空耗时 = 04:23:36.486（容器退出）− 04:23:04.086（SIGTERM）= 32.4 秒**（另一次是 14.4 秒；
两次都在「等一个 superstep、上限 120 秒」的设计之内）。

**用户侧（浏览器）**：那条被排空的提问最终**回答完整**、**界面无报错**、会话列表里**已完成**——
说明接手真的发生了（`drained=True` 意味着旧进程没有发终态事件就退出了，回答只能是新进程接着跑完的）。

**两次没走成接手的原因（值得记下来）**：若 SIGTERM 落在运行的**最后一步**（正在生成最终回答），
排空等它返回后它直接到终态，于是 `drained=False`、不需要接手；要让排空真正发生，**SIGTERM 必须
落在运行的早/中段**，即提问本身必须有足够多的步骤（多轮的多个工具调用）。
