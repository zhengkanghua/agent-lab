# 公共任务组件与任务管理重构

状态：待实施。建立日期：2026-09-11。需求与架构依据为 ADR 0019 的已确认重构方向。

本 spec 是后续开发的施工规格与进度记录。本轮只生成规格；勾选准备工作不表示对应功能已经实现。实施期间逐项更新进度、验证结果和剩余问题。

## 问题陈述

老板希望项目新增业务领域时，都能使用同一套周期任务和一次性后台任务能力，不再为每个业务分别实现调度、提交、查询、重试和恢复。

当前已有任务类型注册、执行记录和写资源协调，但后台工作仍分散在独立 scheduler、API 进程和文档消费者中。手动 Pipeline 等待业务完成后才返回，任务管理主要围绕周期配置，配置修改、历史保留和异常恢复也沿用早期规则。这些边界不适合作为后续业务共同依赖的组件。

重构需要同时解决配置体验与执行可靠性：任务受理后不能因重启或 Redis 消息丢失而消失，也不能因重复请求或消息重新投递而重复开始业务。已有文档待办、完成标记、跨存储恢复和 UTC 存储约定必须继续发挥作用。

## 解决方案

建立项目内部公共任务组件，周期到点、人工触发和业务直接提交共用受理、执行记录、查询、重试及取消能力。业务开发者注册任务类型、参数和处理函数，业务状态与资源规则仍由所属业务管理。

采用 Celery Beat 负责周期触发，Celery Worker 承担后台执行，Redis 传递任务消息，PostgreSQL 保存配置、已受理执行、结果与恢复依据。已有三类定时任务、文档后台处理和 HTTP 手动 Pipeline 本次统一迁入 Worker。

后台入口改为“任务管理”，提供周期配置与任务执行两个视图。老板可以选择常用周期或填写 cron，查看等待原因和失败结果，执行“立即执行／重试”，取消尚未开始或等待重试的执行。批量恢复复用已有业务待办，只有无法确认安全继续时才提示核实。

## 实现决策

1. **公共职责与业务依赖。** 公共组件提供任务类型注册、受理、调度、投递、执行状态、操作和查询。业务提供参数模型、普通处理函数、结果摘要、可安全重试的错误分类，以及必要的恢复判断。通过装配注册，公共核心不依赖知识库或 Agent 的具体实现；不从数据库加载业务代码。前端业务表单与结果展示通过显式适配接入。

2. **数据身份与快照。** 保留 `ScheduledJob` 表达周期配置、`JobRun` 表达任务执行的概念。执行可不关联周期配置；关联过配置的执行保留稳定来源身份和必要快照，删除配置不级联删除执行。持久化受理参数、任务类型及必要版本、来源、操作主体、执行策略、状态、尝试次数、投递及可开始时间、领取身份、结果和恢复信息。新增或调整唯一约束以保护请求去重、同周期事件受理和同配置的未结束执行上限，不能只靠进程内检查。

3. **受理与消息可靠性。** 同一 PostgreSQL 事务保存执行、原请求去重回执及投递依据，事务成功后才返回已受理。执行记录自身承载投递状态，不增加独立通用消息平台。提交后尝试发布，Beat 维护循环有间隔地补投已到时间但尚未领取的执行；发布成功也不能成为永久停止核对的依据。Redis 消息只携带执行编号和投递代次，消息重发不增加业务尝试次数。Worker 按状态、代次及时间条件原子领取，迟到或重复消息不能再次开始业务，结果按领取代次条件写回。

4. **请求去重。** 去重身份包含提交主体、业务操作和请求标识。相同请求重发返回原编号；同一标识换请求内容返回冲突；不同标识不因参数相同合并。比较原请求内容，不能因周期配置后来修改而把原请求重发判成新操作。周期事件以稳定配置编号和计划 UTC 时刻识别，配置版本变化不产生同一时刻的第二个周期事件。

5. **Beat 与 cron。** 单个 Celery Beat 通过项目的 PostgreSQL 适配器读取动态配置，原子完成版本及启用复核、受理或记录重叠跳过、推进下一计划时刻。启动和恢复只安排未来周期，保留现有正常投递误差边界，不补停机期间的周期。现有 `CronTrigger` 仅保留为五段式 cron 计算依赖，校验、预览和调度共用相同计算入口；移除 APScheduler 调度器与 API 内调度来源。不能直接套用默认静态 Beat 配置或 Django 专用管理组件。

6. **配置并发与生效。** 修改、停用、删除和周期受理通过数据库事务协调先后顺序。允许启用或执行期间修改配置，之后受理的执行使用新配置，已经受理的执行及自动重试使用原快照。停用、删除只阻止未来周期，停用配置仍允许人工立即触发。同配置在排队、等待资源、执行中和等待重试期间占据同一个并发名额；新周期跳过，不同的人工请求明确返回冲突及当前执行编号。

7. **执行状态与 HTTP 契约。** 契约需区分排队、资源等待、业务执行中、等待自动重试、待核实，以及成功、失败、已取消和周期跳过；实际编码在后端 schema 与 OpenAPI 中统一，前端由此生成类型。受理接口返回 HTTP 202、执行编号及当前状态，不能把排队描述为业务已开始。提供独立于周期配置的执行列表、详情、取消和人工重试能力。HTTP 手动 Pipeline 改为同样的受理和查询方式，最终统计及业务错误通过执行详情表达；原参数校验、权限和错误脱敏继续有效。

8. **自动重试与人工操作。** 任务类型判断错误是否可安全重试，默认在初次尝试之外最多自动重试三次，间隔逐渐增加。次数和下次尝试时刻保存在 PostgreSQL，由 Beat 到期投递，不另外启用 Celery `autoretry` 形成第二套计数，也不把长期等待交给 Redis 中的 `ETA/countdown`。自动重试沿用原编号、参数和策略；人工重试使用原失败参数，新建执行并关联原记录，采用新受理时生效的策略。普通失败释放占用，耗尽只结束本次执行，下一正常周期有独立额度。

9. **资源等待与取消。** 业务资源正常占用时持久保存等待原因和再次检查时间，释放 Worker 执行位置，资源可用后继续同一次执行，不消耗业务重试次数。尚未开始业务的资源等待属于可取消范围，等待自动重试也可取消；正在进行的业务尝试不提供取消。取消与开始业务通过同一状态条件竞争，取消成功后旧消息失效。需要核实的旧占用不视为普通资源竞争，更不能因心跳过期自动解锁。

10. **异常恢复。** 从未开始的已受理执行补投；已开始的只有在业务持久依据、旧执行者状态及远端核验支持安全继续时才自动恢复，自动再次尝试仍受原额度约束。证据不足时保留待核实和写占用，详情说明阻塞原因及核实步骤，异常处置复用现有维护入口。业务结束但结果保存失败时，只重试保存或核对结果，不能直接重做业务。待核实不能按普通失败释放并发保护、启动下一次冲突写入或裁剪历史。

11. **业务迁移与批次交接。** 迁移 `freshrss_sync`、`index_pending`、`prune_old_documents` 及其手动触发、文档后台处理、HTTP 手动 Pipeline，继续复用现有业务用例与 `DocumentProcessingBatch`。文档待办与对应执行受理同事务保存；正常批次完成后仍有可处理待办时，本批完成与必要下一批受理在同一短事务提交，避免交接中断导致待办无人处理。没有可继续处理的待办时不续建，任务执行失败、取消或待核实也不自动续建；单篇文档异常仍按业务规则保留，不阻断其他正常资料。文档处理由业务待办驱动，不要求用户配置 cron，不保留常驻消费者占用 Worker 执行位置。

12. **业务完成依据。** 清理复用已有删除待办、原件引用和逐项确认。已完整完成的目标不会重新选中，未完成步骤按业务依据继续；远端成功但本地未记确认时允许安全地重复核对或请求，不能声称当前批次跨存储整体回滚。同步、索引及清理的互斥范围继续沿用，CLI 维护入口也参加原有协调。本次不改变清理资格、KnowledgeBase 范围、人工审核、已采用版本和正式检索可见性规则。

13. **时区与策略。** 全局调度时区默认 `Asia/Shanghai`，页面标明时区并预览未来执行时刻。具体计划、受理、开始、结束、重试和过期时间均按带时区 UTC 持久保存，保持 `DATABASE_TIMEZONE=UTC`。默认重试次数、间隔和历史天数由超级用户网页管理并保留修改记录；每次受理冻结策略，后续修改不追溯影响旧执行。任务配置仍由任务自己的持久模型承载，不复制进全局字典，也不把其他尚未完成的全局管理能力作为本次实施前提。

14. **历史与关联。** 普通已结束记录按结束时间及受理时的保留策略清理，默认三十天。未结束、待核实和恢复依据受保护；人工重试所关联的原失败记录在关联执行仍保留期间也受保护。普通详情过期后继续保留最小去重回执，包括主体、请求身份与摘要、原执行编号，不保留参数和结果正文；原请求重发返回原编号并说明详情过期，不能创建新执行。已清理参数快照的历史不提供重试能力，使用当前配置需重新提交。业务待办按业务规则保留，不能随任务历史清理。

15. **页面与权限。** “任务管理”分别提供周期配置和任务执行视图，接入一次性执行和按编号独立查询。展示任务类型、来源、状态、时区时间、尝试次数、等待或失败原因，以及适用的立即执行、取消和重试操作。常用周期选择与原始 cron 输入共用一个值和同一预览。离页不取消任务，恢复查询不依赖最近历史列表；超时保持原请求身份，不用新标识盲目重发。未知类型和未知结果保留可识别信息，部分失败不显示为全部成功。全局管理仍限超级用户，业务页面沿用所属业务权限。

16. **Worker 与 Redis。** API、单个 Beat 和 Worker 使用同一后端镜像、不同进程入口，首期一个业务队列，Worker 可增加进程或实例。生产采用 Linux prefork，子进程在 fork 后惰性建立独立持久事件循环及数据库依赖，按执行创建业务 Runtime；不继承 API 的异步池，不跨事件循环复用旧连接。Windows 开发使用 Docker 或 WSL。消息完成后确认，预取量保持较小，Worker 丢失与可见性超时产生的重投必须经过数据库领取和恢复判断；不能靠无限增大超时解决长任务问题。Redis 使用 AOF、持久数据盘和 `noeviction`，连接、容量及告警放部署配置，凭据不进入前端构建、消息或执行快照。状态与结果只由 PostgreSQL 保存，不启用 Celery result backend。

17. **迁移与运行维护。** 迁移现有配置、执行身份、关联和必要状态，核验旧记录可用的参数与恢复依据，不删除业务待办，不用最新配置伪造旧执行快照。老板说明开发阶段任务均已停止，实际切换前仍需核对旧执行与占用。停用旧调度器和消费者后再切换新执行入口，禁止无保护混跑；同时更新安装、配置、OpenAPI、能力导航、执行流程及恢复说明。至少能观察 Beat 推进、投递失败、Worker 领取、业务等待与待核实。正常停机停止新领取并等待当前工作，强制中断按已定义的恢复规则处理。

## 测试决策

以“通过公开入口受理任务，再按执行编号查询状态和结果”为主要测试接缝，沿用已定稿 ADR 的验收范围。取消、重试、配置变更和权限通过同一组公开入口验收。cron 使用受控时间验证公开计算结果；真实队列与跨存储故障补充在现有集成边界上，避免为了测试给每个私有方法增加接口。

好测试验证用户可观察的状态、业务数据和失败后的去向。不会固定私有函数名、无语义的内部调用顺序、CSS 类名或完整页面文案。可用无外部副作用的测试任务贯通公共受理与执行，扩展性通过注册新类型后仍能完成周期及一次性执行验证。

已有先例可以直接复用其结构：

- `create_offline_app`、`TestAuthGate`、`test_trigger_returns_202_with_run_receipt` 和 `test_validate_cron_returns_utc_and_local`：HTTP 权限、受理回执与时间表达；调整旧回执固定为执行中的断言。
- `isolated_database`、`child`、`test_http_workers_conflict_and_cron_skip_preserve_receipt`：随机 PostgreSQL schema、独立子进程连接和并发受理；保留隔离设施，业务实际执行改由 Worker。
- `test_crashed_owner_requires_explicit_recovery`、`test_cleanup_waits_for_index_and_blocks_new_sync`、`test_terminal_save_failure_never_repeats_business_or_reports_confirmed_success`：资源互斥、旧占用保护和结果保存失败边界。
- `test_batch_keeps_review_failures_and_adoptions_distinct`、`test_batch_does_not_drain_unbounded_work_or_retry_failures`：文档批次上限、待审核与失败分开、失败候选不无限重领。
- 任务管理页面已有的重复点击、离页后按原回执查询、超时不盲目重发和未知类型可见测试，以及文档管理页面的在途轮询测试：扩展一次性执行、等待、取消、重试和配置删除后的查询。

旧测试锁定的“必须先停用才能编辑”“有活动执行不能删除配置”“按条数保留历史”“HTTP Pipeline 等待最终结果并返回 200”“常驻消费者自行轮询”需随新需求调整。保留原参数校验、权限、业务结果统计、逐项失败和资源收尾的保护。不能为了保持旧测试通过而恢复已经取消的旧行为，也不能仅删除旧断言而遗漏新行为验证。

验收项目如下；实施时在工程记录中登记对应证据：

| 编号 | 验收边界 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | 公共任务接入 | 新注册的任务类型无需修改公共核心，即可由周期或一次性入口受理、执行和查询；一次性任务无需周期配置，业务状态仍由业务管理。 |
| T02 | HTTP 与权限 | 受理返回 202 和真实状态，执行按编号独立查询；未登录、非超级用户和业务范围越权得到原有拒绝；Pipeline 最终统计从执行详情读取，错误与参数保持脱敏。 |
| T03 | cron 与时间 | 历史五段式表达式的星期、月份、组合规则和分钟精度保持；北京时间 09:00 对应同日 UTC 01:00，00:30 对应前日 UTC 16:30；预览与实际计划一致，恢复不补历史周期。 |
| T04 | 请求去重 | 同请求重发返回原编号；配置在两次请求之间修改也不新建；相同标识换内容报冲突，不同操作的相同参数不合并；并发请求不突破唯一受理。 |
| T05 | 持久受理与投递 | 数据库提交失败不报告已受理；提交后发布前退出、发布失败、Redis 消息丢失均可补投原执行；重复或迟到消息不会并发启动同一业务尝试，不增加业务重试次数。 |
| T06 | 配置竞争与重叠 | 排队、等待资源或重试中的同配置新周期跳过，新的人工请求返回冲突；修改、停用、删除与受理按事务先后使用正确快照；旧版本回调不受理新执行，删除后已有执行继续。 |
| T07 | 自动与人工重试 | 默认初次加三次自动重试，间隔增加，耗尽后失败但下一周期独立执行；自动重试保留原参数和策略，人工重试用旧参数、新受理策略、新编号并可追溯原失败。 |
| T08 | 取消竞争 | 排队、尚未开始的资源等待及等待重试可取消；取消成功后旧消息不调用业务，Worker 已经开始业务则拒绝取消；取消与开始之间没有两边都成功的结果。 |
| T09 | 业务资源等待 | 多执行争用资源时原因可见，让出 Worker 执行位置且不消耗重试次数；释放后继续同一次执行；同步、索引、清理及 CLI 仍遵守原互斥范围。 |
| T10 | 崩溃与不确定结果 | 在领取前、开始后、远端成功后和终态保存时中断，分别进入补投、安全恢复或待核实；心跳过期不自动抢占；结果保存失败不能直接重做已经完成的业务。 |
| T11 | 文档批次持久交接 | 待办与受理同事务，本批完成与必要下一批受理同事务；任一交接处退出后仍有推进依据；无可处理待办时不空转续建，执行失败、取消或待核实不绕过限制续建。 |
| T12 | 现有业务不回退 | 文档处理不依赖用户 cron，单篇异常不阻断其他正常资料，待审核不算已采用；已采用正文与索引可见性、清理资格和知识库范围保持，批次完成标记保留。 |
| T13 | 跨存储部分成功 | PostgreSQL、Qdrant、原件存储各步骤失败或确认丢失后仅继续未完成工作，远端成功不被误称为回滚；普通历史清理及配置删除不丢失删除待办。 |
| T14 | 历史和策略 | 普通记录按结束时间及受理时策略过期；调整默认值不追溯旧执行；保护未结束、待核实和原失败关联；详情过期后旧请求仍返回原编号且不新建，已清理快照不能人工重试。 |
| T15 | 页面完整流程 | 两个视图覆盖周期与一次性执行，周期选项和原始 cron 一致，时区明确；离页后续查、删除后查询、等待原因、取消、重试和未知结果均正确，权限与原导航行为保持。 |
| T16 | 真实进程和 Redis | 使用真实 Redis、Beat 和多个 Worker 进程验证受理到结果、重投、连接恢复及关停；异步资源没有跨进程或跨循环复用，Redis 持久化重启及长任务超时重投遵守相同领取规则。 |
| T17 | 迁移与就绪 | 隔离数据迁移后配置、旧执行和恢复依据可解释；新旧调度与消费者不混跑，API 不直接执行本次迁移的后台工作；能区分调度、投递、领取和业务阻塞，实际切换结果单独记录。 |

离线测试默认不得访问真实依赖，沿用现有离线应用和连接阻断机制。前端 HTTP 替身只证明页面行为，Celery eager 模式也不能证明进程隔离、真实消息确认或恢复。

真实 PostgreSQL 及 Qdrant 验证优先复用随机 schema、Collection、Alias 和合成数据的隔离设施。新增 Redis／Beat／Worker 集成夹具同样隔离队列和测试进程，只清理本次创建的资源。共享开发 Redis 不可为了故障验证整体重启或清空；重启和消息丢失实验使用明确授权的隔离服务或隔离实例。

现有部分文档测试的 Qdrant 默认是内存实例，现有 PostgreSQL／Qdrant 清理组合测试的原件存储仍有替身；独立真实 S3 测试只证明原件接口本身。T13 必须分别记录哪些存储真实参与，发布所需的完整跨存储恢复另做真实组合验收，不能把已有测试名当作三个真实存储全部验证的证明。真实服务访问、数据库写入与故障操作在获得对应环境授权后执行。

## 超出范围

- 本轮 spec 生成不实施业务代码、依赖安装、数据库迁移或真实服务切换。
- 不同时接入 RabbitMQ 或 RocketMQ，不建设通用事件总线、多业务工作流引擎或动态插件系统。
- 不新增通用批次进度、批次续执行平台或独立人工恢复页面；不把现有整次资源占用改成按批次释放。
- 不提供正在进行的业务尝试的取消，不自动补执行错过的周期，不根据心跳过期强制释放旧写资源。
- 不启用第二套任务结果存储，不承诺跨存储操作恰好一次或统一回滚，不用 Redis 锁替代已有业务写入保护。
- 不改变文档解析与审核规则、索引规格、正式可见性和业务数据保留规则；不迁移所有 CLI 或 Agent 对话。
- 不把全局字典、FreshRSS 管理和模型连接管理等其他待实施能力并入本次重构，也不引入第二套任务配置来源。
- 不预建多队列或多 Beat 的高可用体系，不因本次页面改名增加重复管理入口。
