# 文件资料的接收、审核、采用与删除

超级用户在 `/admin/files` 选择启用 KnowledgeBase，上传 MD 或 TXT。入口先校验格式和大小，在 PostgreSQL 保存独立 Document 身份与接收意图，再向 MinIO/S3 保存并核对原件，确认待办后返回。同名上传互不覆盖；原始字节保留，解码或解析异常进入处理记录。

确认业务待办时，在同一个 PostgreSQL 事务中受理必要的文档处理批次；消息投递失败仍保留推进依据。Celery Worker 处理有界批次，生成解析正文、结构和 Chunk 预览，不需要用户创建 cron。正常结果自动进入采用，可检测的异常保留给人工处理；首次采用前，普通全文、检索和 Agent 均不可读取候选。上传回执只证明原件与待办已保存，不能显示成已经可检索。FreshRSS 接收后复用同一流程，来源同步边界见 [新闻接收](news-to-searchable.md)。

正常批次结束时，本批完成和必要下一批受理在同一短事务中保存；交接中断会一并提交或回滚。没有可处理待办时不续建，失败、取消或待核实的任务执行也不自动重建下一批。单篇资料异常留在业务记录中，其他正常资料继续；执行等待及恢复原因可在任务管理查询，文档页面仍按原业务处理状态轮询。

`/admin/documents` 统一显示已采用版本、人工草稿和最新来源。超级用户可以对照原件、修改 Markdown 或纯文本、重新生成结构和 Chunk 预览。修改使旧预览失效；轮询不覆盖本地编辑，并发冲突需明确选择后才能继续保存。采用确认针对当时的候选和预览，迟到结果不能覆盖较新编辑。

采用先冻结确切正文、元数据和 Chunk 清单，后台向独立索引实例写入向量并回读核验；成功后才条件切换 PostgreSQL 正式版本。切换前和准备失败时旧已采用版本继续可用。检索核验当前可用实例，候选不能提前出现，同一文档不会混合新旧 Chunk；旧向量回收不删除已采用历史。

替换从明确的 Document 发起，携带正式及管理修订，保留身份和知识库归属；相同来源资料保持幂等，新资料另建候选。已有人工草稿或已采用人工版本时，来源更新进入复核；人工决定是否换用。冲突后页面保留所选文件，刷新后重新确认；请求超时先核对状态，不自动重传。

拒绝停止整篇资料的后续检索、Agent 取用及普通全文读取，保留原件、已采用历史和审核结论供修正。明确删除才开始完整清理：先停止使用并保存删除依据，再清除相关索引实例及原件，最后删除 PostgreSQL 中的资料、候选、历史和审核记录。远端或数据库收尾失败时保留待办，从同一目标继续；定时清理只处理范围内符合保留期的已采用资料，待审核、失败、拒绝及尚有候选的资料不自动清理。

| 失败位置 | 可观察结果与恢复 |
| --- | --- |
| 文件格式或大小不合法 | 接收前拒绝，既有文档不变 |
| 原件存储失败或写入回执不确定 | 不返回保存成功；保留接收依据供核对 |
| 任务消息丢失或 Worker 暂不可用 | 已提交的业务待办和任务受理保留，恢复后补投原执行 |
| 解码、解析或 Chunk 质量异常 | 原件保留，管理页可检查、修正和重试 |
| 未登录或非超级用户 | 服务端拒绝管理与原件请求 |
| 目标知识库停用 | 禁止新增、替换和普通读取，管理记录仍可维护 |
| 并发保存、旧预览或旧采用确认 | 冲突可见，不覆盖新草稿或误用失效预览 |
| 新索引准备失败 | 候选不可见，旧已采用版本保留；人工可重试或重新预览 |
| 任一删除阶段未确认 | 停止使用，保留对象及索引引用和待办供继续清理 |

接口与错误码以 OpenAPI、`api/file_documents.py` 和 `api/document_review.py` 为准。验证入口为后端 `test_document_processing.py`、`test_document_review_api.py`、`test_document_review_integration.py`、`test_document_deletion_integration.py`，以及前端 `DocumentManagementPage.spec.ts`、`DocumentPreview.spec.ts`、`FileDocumentDirectory.spec.ts`。隔离数据库、向量库和浏览器替身验证各自有明确范围，不能相互代替。
