# Agent 的运行范围、证据引用与回看

页面保存当前会话的 KnowledgeBase 选择。发送前，后端先校验会话归属，再解析启用目录并冻结本次范围；新会话默认所有启用库，旧会话迁移保留 news。SSE 的 `run_started` 将会话 ID、运行 ID 和实际范围交给页面。运行期间保存的新选择只影响下一次提问。

主模型接收 checkpoint 里的整份上下文记录——历史提问、历史回答、历史 Tool 结果和历史摘要。范围只是工具的参数：它决定工具能取到什么、哪份 Tool 结果算本次证据，不决定模型能说什么。所以旧内容可以留在对话里供理解意图，但不能充当本次证据；送出去的那一份会剥掉旧引用标识。`search_documents` 可按用户要求缩小范围，`read_document` 同时核验允许范围和知识库启用状态；已知 Document ID 不能越界。资料不足时不能自动扩大页面选择。

工具与普通检索、全文共用已采用版本的可见性规则：新候选准备期间旧版本仍可用，拒绝或删除后停止后续取用。管理页保留的历史和原件不通过 Agent 工具开放。

Tool 返回实际读到的片段及应用分配的引用标识，证据关系随消息写入 checkpoint。模型引用这些标识作答。结束时，服务端从持久状态得到最终答案、完成状态、有效与无效引用，作为 Done 返回；前端校正临时 token，并同步最新保留的问答。回放使用同一套关联规则，工具调用仅在所属问答内配对。

一次运行由服务端自己驱动，不挂在浏览器连接上：请求受理后由后台驱动者把事件流读到结束并收尾，SSE 响应只是它的一个订阅者。关页面、断网、切走会话都只减少订阅者，运行照旧跑完并落进历史；要真的停下它，走 `POST /agent/stop`（带会话 id 与运行 id，幂等）。同一个会话同时只允许一次运行，再来一次返回 409 `agent_run_in_progress`（界面据此说「正在生成」，不引导重发）。刷新页面时如果上一轮还在跑，回放响应里的 `active_run_id` 让界面显示「正在生成」、禁用发送，并每隔几秒重读历史直到服务端不再上报——前端不设放弃上限，因为失活判定会结束服务端的上报。删除一个正在运行的会话时先请求停下它并等它释放占位，再清历史、再删归属，避免运行在历史清空之后继续写回。

用户点击行内引用或引用列表，阅读器按引用给出的文档归属与来源打开当前全文。原文变化时同时保留旧依据和新内容；删除、停用、服务不可用分别提示。无法从索引文本可靠映射到 Markdown 原文时不猜测高亮。原始 Cosine score 只表示检索相似度。

| 失败或生命周期边界 | 用户看到 |
| --- | --- |
| 目录加载失败、空选或目标失效 | 提问前失败，不退化为无过滤搜索 |
| Tool 试图越界 | 明确失败，不能凭已知 ID 绕过范围 |
| 模型生成未知或旧运行引用 | 引用无法核验提示，不提供伪造阅读入口 |
| 上游重试产生临时文字 | Done 用已保存答案校正，回看与终态一致 |
| 达到模型预算、上游截断或流中断 | 已有内容留在会话里，状态如实标成未完成；界面不加结局标签 |
| 浏览器断开（关页面、断网、切会话） | 运行不受影响，照旧跑完并落进历史 |
| 用户点停止 / 上游失败 / 超时 | 运行收尾，已推出去但未落库的那段文本补写进会话，状态标成未完成 |
| 刷新后这一轮还在跑 | 显示「正在生成」、发送键不可用，等到服务端不再上报后自动换成最终内容 |
| 删除正在运行的会话 | 先请求停止并等它释放占位（上限 10 秒），再清历史、再删归属 |
| 部署时上一轮还在跑 | 旧进程收到退出信号后把在途运行排空到 superstep 边界、写下「等接手」标记再退出，集群里任一进程扫到标记后抢下所有权接着跑完。连接会断一次，界面短暂显示「正在生成」（可停止），随后拿到完整答案；改过图状态结构的发布、以及强杀/OOM/断电不在此列 |
| 连接被部署切断 | 界面不显示错误：断流后**重读回放**（最多 5 次、约 30 秒，跳停-起切换那段不可达窗口）；服务端仍报有在途运行就进入「正在生成」等待态，不再上报之后按回放渲染这一轮。等待/重连状态贴在对话最底部，且等待期间不重建对话（否则滚动会被反复重置）。停止键用回放给出的在途运行 id，在途 id 为空时不出现 |
| 结束后历史同步失败 | 保留本次页面内容并提供同步重试 |
| 较早问答被压缩 | 模型看到的是摘要加近期的原文；被清掉那段的工具正文显示为占位文字。完整回看由会话历史业务表承载（设计已定、尚未实施），分界处届时如实标出 |

**正常部署不丢在途运行，无收尾机会的故障会丢。** 这条边界由「有没有收尾的机会」划分（见 [ADR 0040](../adr/0040-run-handover-on-deploy.md)）：进程收到退出信号、能在 ASGI 生命周期收尾里动作时，它把在途运行排空到可交接的边界、写下标记，由别的进程续跑；强杀、OOM、断电没有任何代码被执行，那一轮按未完成收尾（见 [ADR 0036](../adr/0036-interrupted-run-keeps-emitted-answer.md)），只能靠用户重新提问。续跑能覆盖什么，还取决于两次部署之间**图状态结构**没变：改了形状的发布接手时可能抛错（按未完成收尾），静默改变合并规则的那种检测不出来，只能靠发布纪律（改形状的发布挑没人在跑的时刻发）。

**硬杀留下的在途标记是已知边界，不掩盖。** 进程被强杀（崩溃、OOM、超过停止宽限）时没有任何清理动作会执行，``active_run_id`` 这个在途标记只能等失活判定自动释放。这不是可以修掉的缺陷，而是「无法区分进程已死与运行很慢」的必然结果——不要为它加快速失活检测，也**不要**在进程启动时把在途标记一律清掉：API 有多个副本（2 个，每个容器一个进程）、以后还可能有滚动部署，启动时清标记无法区分「那个进程死了」与「那个进程还在另一个进程里跑」，会把活着的占位抹掉，于是两次运行同时写一个会话的历史（静默覆盖）。**排空标记（``drained_at``）不适用这条禁令**：它由收到退出信号、正在收尾的进程写下，含义没有歧义（那次运行确实停在边界、等别人接），接手者用一条条件写入判非空并置空来抢所有权，不是「启动时一律清」。真要缩短强杀后的窗口，应改的是续期间隔与失活阈值这两个常量（代价是更频繁的活跃时间写入、以及更短的事件循环卡顿容忍度），不是加一条「谁有权清在途标记」的规则。删除正在运行且等待窗口内没停下来的会话另有一条已确认的代价：那次运行随后仍可能把收尾内容写回，留下一条查不到也删不掉的孤儿会话，靠运维命令清理。

压缩只在新提问开始时执行，触发取模型窗口的 80%、压缩后保留 30%；触发后先按「换内容、不删消息」清掉较旧的 Tool 结果正文，够用就不调摘要模型，因此不切断正在使用的证据链。摘要此后随历史一起送给模型，它是模型对被压缩那一段的唯一记忆。退出可回看状态不等于旧 checkpoint 已物理清除。设计取舍见 [ADR 0045](../adr/0045-model-sees-whole-session-history.md)；跨层验证见 `backend/tests/test_agent_evidence_scope.py`、`backend/tests/test_agent_runs.py`（运行生命周期与停止）和 `frontend/src/pages/AgentChatPage.spec.ts`。
