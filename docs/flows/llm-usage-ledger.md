# 一次模型调用到用量可查

这条链路回答一件事：一次模型调用消耗了多少 token，怎么变成本人能查到的账。

## 谁负责哪一段

| 位置 | 负责 |
| --- | --- |
| `agent/runtime.py` | 装配时把主模型与备用模型各包一层，采集器从这里注入（缺省是空实现，什么都不记） |
| `agent/usage_recording.py` | 包装层：包在模型的**公开调用方法**外面，每次调用装成一条契约交给采集器 |
| `usage/` | 用量子包：契约、采集器、仓储、用量表、装配。它不导入 Agent、知识库或任何业务 ORM 模型 |
| `api/usage.py` | 三个面向当前账号的只读查询接口：明细、汇总、模型名列表 |
| `api/dependencies.py` | 从 `app.state` 取用量库的短会话工厂 |
| `main.py` | lifespan 里读用量库配置、装配 Engine 与采集器、注入 Agent；退出时排空并释放 |
| `alembic_usage.ini` + `usage_migrations/` | 用量库自己的迁移环境（独立的 ini、env 与版本目录） |

## 顺序

1. 一次运行开始时，`api/agent_chat.py` 把当前账号、会话 id 与运行 id 放进运行上下文。
2. 模型被调用。模型节点、备用模型与**历史摘要压缩**走的都是那个被包住的实例——摘要压缩发生在中间件内部，不在模型节点上。
3. 无论正常返回还是抛异常（含被取消），包装层都装一条契约交给采集器，异常原样再抛。取不到运行身份只把账号／会话／运行记成缺失并留一条日志，不把这次调用判成失败。
4. 采集器把记录放进有界队列就返回（不等待、不抛异常），后台任务按刷写间隔批量落库。队列满丢新记录并记日志；写入失败按规则重试后丢弃该批，不重新入队。
5. 查询接口从同一处拿短会话，按当前账号过滤，读明细、汇总与模型名列表。

## 终态有哪几种

- **正常**：一次调用一条记录；成功与失败只体现在状态字段上，失败的 token 记 0、来源记缺失。
- **用量库不可达**：对话照常——排队不挡调用方，故障期只有日志；库恢复后新记录继续落库，不需要重启进程。
- **进程关停**：尽力排空队列，上限一次刷写间隔；没写完的条数写进日志，不让关停被一个坏掉的库拖住。
- **查询时用量库不可用**：三个接口返回稳定的 503，**不返回空列表、不返回零汇总**——把「查不到」渲染成 0，会让「这个月没花钱」这种结论建立在故障上。

## 为什么这么切分

- **记账点为什么在包装层。** 只按模型节点的产出累加，会把中间件内部发起的调用（历史摘要压缩）整段漏掉，而那正是长会话里最烧钱的部分；LangChain 的回调能盖住全部调用，但拿不到这次调用属于哪个账号、哪次运行。包装层是唯一同时满足两件事的位置，见 [ADR 0031](../../docs/adr/0031-usage-recorded-by-wrapping-chat-model.md)。
- **为什么另开一个库和一个子包。** 这块数据将来可能整块搬走，模块只吃一个纯数据结构（UUID、数字、字符串枚举与时间），业务表一行都不碰，见 [ADR 0032](../../docs/adr/0032-usage-data-in-separate-database.md) 与 [ADR 0033](../../docs/adr/0033-usage-module-independent-of-domain.md)。
- **为什么配置缺失要启动失败、连不上只降级。** 前者改了配置就能好，静默降级只会让「用量统计悄悄没在工作」难以发现；后者是次要库的故障，不该升级成主要功能不可用。
- **为什么包在公开方法外而不是实现生成钩子。** 框架先看子类有没有覆写 `_stream` / `_astream` 来判断「支不支持流式」，覆写它们会真的把流式关掉。代价是 `bind_tools` / `bind` 必须把底层产出的绑定重新挂回包装（否则工具丢了，或者记账丢了），模型的可观测属性必须逐项手工委托。
- **用量表为什么不能出现在业务 metadata 里。** 业务库的 `alembic check` 会把外来的表当成多余的表删掉，或者把它当成业务库缺的表建出来。两套迁移链各读自己的 metadata。

## 已知边界

- **Worker 不记账。** 采集器只在 API 进程装配；将来若有定时任务开始调生成式模型，那条链路上的调用不会被记录，也不报错。
- **`stream` / `astream` 入口只转发、不记账。** 本期的取数路径是模型节点的 `invoke` / `ainvoke`；直接调这两个入口的链路不在账本里。
- **同一次调用被重新受理会多一行。** 调用标识挡的是「同一条记录被重复写入」，不挡重放；本期没有去重机制。
- **查询有一秒左右的延迟**（队列按秒刷写），且偏移量分页在翻页期间有新写入时可能重复或跳过一次。
- **两处旧描述已过时，别照着它们排查。** [ADR 0031](../../docs/adr/0031-usage-recorded-by-wrapping-chat-model.md) 把摘要调用被漏掉归因于「框架把中间件内部的调用从流里删掉」——真正的成因是旧实现只按模型节点的产出累加，而摘要调用不在模型节点上；它关于「来源标签」的结论本期也不再适用（不记录主模型／备用模型／摘要压缩这类标签）。[ADR 0033](../../docs/adr/0033-usage-module-independent-of-domain.md) 关于队列容量定标的说法也要跟着「不做精确计数与守恒」复核。这两份文件与术语表只能在专门的访谈流程里改（写入受门禁约束）。
